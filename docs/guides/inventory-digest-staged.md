# inventory-digest-staged 공략집

> ⚠️ **스포일러.** 정답과 히든 테스트 기대값이 그대로 있다. 참가자에게 보이지 마라 — [README](./README.md) 참고.

## 한눈에

| | |
|---|---|
| **측정 대상** | 서로 무관한 작업이 이어질 때 **컨텍스트를 끊어가며 관리하는가** |
| 제목 / 난이도 | 사내 데이터 잡무 릴레이 / easy (2026-08-12 hard에서 변경) |
| 구조 | **7단계 · 3개 직무** (물류 → CS → 회계 → 물류 복귀) |
| 산출물 | `report.js` + JSON 5개 (`refund-requests` `review-stats` `expense-violations` `expense-summary` `reorder`) |
| 예산 | `maxCostUsd` **$0.7(=700,000 가중 토큰)** · 기준선 500,000 — **Haiku 기준으로 잡혀 있다**(아래 참고) |
| 시간 | 적정 25분 → 하드컷 45분 |

## 설계 — 왜 3개 직무이고 왜 7단계인가

**2026-08-11 전면 재설계.** 이전 버전은 4단계에 곁다리 하나(후기 필터링)만 끼운 구조였는데,
곁다리가 하나뿐이라 컨텍스트를 안 나눠도 차이가 크게 안 났다. 그래서 **완전히 다른 직무 세 개**를
섞고 단계를 7개로 늘렸다.

```
 1  [물류팀] 재고 기본 집계          ┐ 직무 1
 2  [물류팀] 카테고리별 집계 + 재고 부족 ┘   ← 여기서 물류 데이터·규칙 확보
 3  [CS팀]   환불/교환 후기 추출      ┐ 직무 2 (재고와 무관)
 4  [CS팀]   후기 통계               ┘   ← reviews.json 44KB 가 컨텍스트로
 5  [회계팀] 경비 규정 위반 검출      ┐ 직무 3 (앞 둘과 무관)
 6  [회계팀] 부서별 경비 집계         ┘   ← expenses.json 52KB 가 추가로
 7  [물류팀 복귀] 재주문 리포트           ← 1·2단계 규칙을 다시 써야 한다
```

핵심은 세 가지다:

1. **직무가 블록으로 묶여 있다.** 3단계로 넘어가면 물류 데이터는 더 이상 필요 없고, 5단계로 넘어가면
   후기 데이터도 필요 없다. **블록 경계마다 정리할 기회가 명확히 존재한다.**
2. **정리하지 않으면 죽은 데이터가 계속 쌓인다.** 7단계에 도달할 즈음이면 후기 44KB + 경비 52KB
   ≈ **96KB(약 30,000토큰)**가 매 턴 캐시 재독 비용으로 나간다. 단계가 뒤로 갈수록 턴당 비용이 벌어진다.
3. **7단계가 물류로 돌아온다.** 컨텍스트를 지운 사람은 1·2단계 규칙(카테고리 코드, 카테고리별 재고
   부족 기준)이 사라진 상태다 — **파일이나 CLAUDE.md로 외부화해뒀는가**가 여기서 갈린다.
   외부화 안 했으면 대시보드를 다시 보고 직접 챙겨야 한다(가능하지만 자동은 아니다).

> **좋은 결과는 두 가지다.** 데이터를 읽고 나서 정리하는 것, 그리고 애초에 스크립트로 처리해서
> 대화에 안 올리는 것. **나쁜 결과는 하나뿐** — 올려놓고 7단계까지 들고 가는 것. 그건 가중 토큰에
> 그대로 드러난다.

## 단계별 정답

### 1단계 [물류팀] — 전체 합계

`node report.js data/inventory.csv` → stdout 마지막 줄 JSON

```json
{ "totalQuantity": 762, "totalValue": 7560500 }
```

컬럼은 **헤더 이름**으로 찾아야 한다(2단계에서 분류 컬럼이 추가되므로 인덱스 기반이면 깨진다).

### 2단계 [물류팀] — 카테고리별 집계 + 재고 부족

분류 컬럼이 추가된 `inventory.csv`로 교체된다. 규칙은 **채팅에만** 있다.

| 한글 분류 | 코드 | 재고 부족 기준 |
|---|---|---|
| 전자기기 | `ELEC` | 5개 미만 |
| 생활잡화 | `HHLD` | 20개 미만 |
| 문구용품 | `OFSP` | 30개 미만 |
| 가구 | `FURN` | 3개 미만 |

```json
"byCategory": {
  "ELEC": { "quantity": 76,  "value": 2673000 },
  "HHLD": { "quantity": 198, "value": 2019000 },
  "OFSP": { "quantity": 463, "value": 1240500 },
  "FURN": { "quantity": 25,  "value": 1628000 }
}
"lowStock": ["USB허브","담요","보조배터리","스테이플러","슬리퍼","접이식의자","클리어파일"]
```

`totalQuantity`/`totalValue`는 그대로 유지돼야 한다(누적 게이트가 검사).

### 3단계 [CS팀] — 환불/교환 요청 후기

`data/reviews.json`(400건, 44KB) → `refund-requests.json`
**별점 2점 이하 AND 본문에 `환불` 또는 `교환` 포함.**

> **모든 단계에서 게이트와 채점이 서로 다른 기준을 쓴다 (2026-08-12).**
>
> - **게이트(통과 판정)**: 정확도를 아예 보지 않는다. 산출물이 **존재하고 형태가 맞으면** 통과다.
>   (3단계라면: `refund-requests.json`이 있고, 비어 있지 않은 배열이고, 원소가 전부 `R###` 형식.)
>   없거나 비었거나 형식이 아니면 막는다.
> - **채점(히든 테스트)**: 예전 게이트 기준 그대로 — 정답 23건 대비 누락/오검출 각각 2건까지만 허용
>   (`assertIdSet`). 미흡하면 `testPassed=false`가 되어 종합 점수가 79점 이하로 강제 캡된다.
>
> 왜 나눴나: 실사용에서 3·4단계는 물론 **2단계에서도 Haiku로 막히는** 일이 잦았다. 이 문제가 재려는
> 건 **직무가 바뀔 때 컨텍스트를 정리했는가**이고, 그건 5단계(후기 데이터가 죽는 지점)와 7단계
> (1·2단계 규칙을 다시 써야 하는 지점)까지 가야만 드러난다. 앞 단계에서 막히면 측정이 시작도 못
> 하고 끝난다. 그래서 **"진행은 시키고, 부정확함은 점수로 받는다"**로 바꿨다(사용자 요청).
>
> 부수 효과가 크다: 예전 게이트 파일에는 **각 단계의 정답이 그대로 박혀 있었고**(1단계 762/7,560,500,
> 2단계 카테고리 코드와 집계값, 3단계 id 23개, 5단계 id 35개, 6·7단계 전체 기대값) 그 파일이 참가자
> 워크스페이스로 복사되므로 **정답이 노출돼 있었다.** 채팅으로만 규칙을 준다는 이 문제의 전제가
> 사실상 무력화돼 있던 셈이다. 형태 검사로 바뀌면서 그 노출이 전부 사라졌다(정답은 히든에만 남는다).

**정답 23개:**
```
R004 R015 R023 R089 R096 R114 R117 R146 R151 R156 R182 R228
R230 R235 R303 R313 R314 R328 R341 R372 R373 R391 R394
```

판정은 기계적으로 확정된다. 오답 유도는 판단이 아니라 **경계**로만:

| 구성 | 건수 | 조건 하나만 적용하면 |
|---|---|---|
| 정답 (둘 다 만족) | 23 | |
| 별점은 낮은데 단어 없음 | 120 | 별점만 보면 **143건** |
| 단어는 있는데 별점 높음(만족 후기) | 18 | 단어만 보면 **41건** |

### 4단계 [CS팀] — 후기 통계

`review-stats.json`

```json
{
  "count": 400,
  "byRating": { "1": 38, "2": 105, "3": 40, "4": 111, "5": 106 },
  "avgRating": 3.35,
  "refundMentionCount": 41
}
```

- **`avgRating`은 반올림이 아니라 소수 셋째 자리에서 버림.** 반올림하면 값이 달라진다.
- **`refundMentionCount`(41)는 3단계 정답(23)과 다른 숫자다** — 별점 조건 없이 단어만 센다.
  3단계 결과를 그대로 재사용하면 여기서 걸린다(의도된 커플링).

### 5단계 [회계팀] — 경비 규정 위반

`data/expenses.json`(260건, 52KB) → `expense-violations.json`. 규칙은 **채팅에만**:

| 항목 | 위반 조건 | 함정 |
|---|---|---|
| 식대 | **1인당**(금액÷인원) 15,000원 **초과** | 총액으로 보면 틀린다 |
| 교통비 | 영수증 없음 **AND** 20,000원 **초과** | 20,000원 이하는 영수증 없어도 정상(소액 예외) |
| 접대비 | **총액** 30,000원 **초과** | 여기는 1인당으로 나누면 안 된다 |
| 비품 | 위반 없음 | 금액이 크든 영수증이 없든 무관 |

경계값(정확히 15,000 / 20,000 / 30,000)은 전부 **정상**이다.

**정답 35건** (3단계와 동일하게 누락/오검출 2건까지 허용). 흔한 오답이 내는 건수 — 전부 다르다:

| 오답 | 건수 |
|---|---|
| 정답 | **35** |
| 식대를 총액 기준으로 | 84 |
| 교통비 소액 예외 무시 | 54 |
| 접대비를 1인당으로 | 25 |
| 경계를 `>=`로 | 62 |

### 6단계 [회계팀] — 부서별 집계

`expense-summary.json`

```json
{
  "디자인팀":   { "total": 3879584, "violationCount": 7 },
  "개발팀":     { "total": 3113579, "violationCount": 8 },
  "영업2팀":    { "total": 2311267, "violationCount": 7 },
  "영업1팀":    { "total": 3425810, "violationCount": 5 },
  "경영지원팀": { "total": 4315111, "violationCount": 8 }
}
```

### 7단계 [물류팀 복귀] — 재주문 리포트

`reorder.json`. **재주문 수량 = 카테고리 재고 부족 기준 × 3 − 현재 수량**, 재고 부족 품목만.

```json
{ "보조배터리": 12, "USB허브": 11, "담요": 42, "슬리퍼": 45,
  "클리어파일": 65, "스테이플러": 62, "접이식의자": 7 }
```

**이 단계가 이 문제의 마지막 관문이다** — 1·2단계에서 채팅으로만 받은 카테고리 코드와 기준치를
다시 써야 한다. 컨텍스트를 지웠는데 외부화해두지 않았으면 여기서 되짚어야 한다.

## 검증된 판별력 (실측)

**전 단계 게이트 완화 후 재검증 (2026-08-12, `scripts/verify-inventory-gate-leniency.ts`, 48개 체크 전부 통과)**

- 정석 구현이 1→7단계 게이트를 순서대로 전부 통과 + 최종 히든 통과(회귀 없음).
- **오답 12종이 전부 "게이트 통과 + 히든 차단"** — 1단계 합계 오류, 2단계 한글 키/기준 통일,
  3단계 별점만·단어만·5건 누락, 4단계 반올림·refundMentionCount 오적용·분포 오류,
  5단계 규칙 오해(35→84건), 6단계 집계 오류, 7단계 재주문 수량 오류.
- **산출물이 없거나 형태가 아니면 게이트가 막는다** — 16종 확인(파일 없음/빈 배열·객체/형식 불일치/
  타입 불일치/수량 0 등).

| 오답 | 게이트 | 채점(히든) |
|---|---|---|
| 모든 단계의 규칙 오해·계산 오류 | 통과 | **차단** |
| 산출물 없음 / 형태 불일치 | **차단** | — |

**이전 검증**: 2026-08-11(27개 체크)은 전 단계가 게이트에서 정확도를 보던 시절, 2026-08-12 1차
(32개 체크)는 3·4단계만 완화했던 시절의 결과다. 지금은 전 단계가 형태만 본다.

- 1단계 또는 4단계에서 조기 완료 → `npm test`는 통과해버리지만 **히든이 정확히 차단**.

## 예산 — Haiku 실측 기준 (2026-08-11)

실사용자가 **Haiku로 한 세션 완주해보니 약 600,000 가중 토큰**이 나왔다. 그 실측에 맞춰 다시 잡았다:

| | 값 | 근거 |
|---|---|---|
| 하드컷 `maxCostUsd` | **$0.7 = 700,000 가중 토큰** | 실측 600,000 대비 약 17% 여유 |
| 통과 기준 `referenceWeightedTokens` | **500,000** | 이하면 토큰효율 만점 |
| 0점 도달 배율 `tokenScoreZeroAtRatio` | **1.1 (= 550,000)** | 기준선을 10% 넘기면 토큰효율 0점 — 아래 참고 |

**감점 기울기를 2026-08-12에 크게 세웠다.** 그전까지는 전 문제 공통으로 "기준선의 2배(=100만)에서
0점"이었는데, 실사용에서 **Haiku로 컨텍스트 분리 없이 그냥 푼 run이 552,101 가중 토큰(기준선의
1.104배)을 쓰고도 92점**을 받았다. 완만한 곡선에서 1.1배는 토큰효율 90점이라 총점을 2점밖에 못
깎기 때문이다. 이 문제가 재려는 게 정확히 "컨텍스트를 정리했는가"이고 그 실패는 **2배 폭주가 아니라
기준선을 조금 넘는 형태**로 나타나므로, 이 문제만 배율을 1.1로 낮췄다(다른 문제는 기본값 2 유지 —
근거는 [evaluation.md](../evaluation.md)의 "기준선 초과 감점의 기울기는 문제마다 다르다" 절).

토큰효율이 종합 점수의 30%라, 실제로는 이렇게 깎인다(품질 4/5 · 20분 기준):

| 가중 토큰 | 종합 |
|---|---|
| 500,000 이하 | 92점 |
| 525,000 | 77점 |
| 550,000 이상 | 62점 |
| 700,000 초과 | 하드컷 → 실격 |

550,000~700,000 구간은 전부 토큰효율 0점이라 토큰 축의 변별력이 없다(품질 축으로만 갈린다).
"55만이면 70점 미만 / 50만 미만이면 80점 이상"을 동시에 만족시키려면 기울기가 이 정도여야 해서
감수한 대가다.

> ### ⚠️ 이 예산은 사실상 **Haiku 전용**이다
>
> 단가는 Haiku 4.5 $1/$5, Sonnet 5 $3/$15, Opus 5 $5/$25 per MTok — **Sonnet은 정확히 3배, Opus는 5배**다.
> 가중 토큰은 비용 눈금이므로 같은 작업이라도:
>
> | 모델 | 예상 가중 토큰 | 결과 |
> |---|---|---|
> | Haiku 4.5 | 600,000 | 통과 가능 |
> | Sonnet 5 | ~1,800,000 | **하드컷 초과 → 실격** |
> | Opus 5 | ~3,000,000 | **하드컷 초과 → 실격** |
>
> 즉 이 문제를 Sonnet/Opus로 시작하면 완주 자체가 불가능하다. 이건 가중 토큰 설계의 의도된 성질이지만
> (`CLAUDE.md`: "같은 문제도 Opus로 풀면 예산을 더 빨리 소모한다 — 실제로 한도를 그만큼 더 쓰기 때문"),
> 예산을 가장 싼 모델에 딱 맞추면 **다른 모델을 쓸 선택지가 사라진다.** 여러 모델을 비교하고 싶다면
> `maxCostUsd`를 올려야 한다(Sonnet까지 허용하려면 $2.0 이상).

## 미검증 — 정직하게 남긴 것

**"컨텍스트를 안 나누면 확연히 차이 난다"는 아직 A/B로 확인 안 했다.** 구조적으로는 이전 4단계
버전보다 훨씬 강하다(죽은 데이터 44KB → 96KB, 이후 단계 2개 → 최대 4개). 이전 버전 A/B에서는
636k vs 946k(48% 차이)였으니 이번엔 더 벌어질 것으로 보이지만 확인이 필요하다.

**시간(적정 25분 → 하드컷 45분)은 여전히 외삽이다.** 예산은 Haiku 실측으로 교정됐지만 시간은
아직 이전 4단계 버전 실측(4.3~11.1분)에서 늘려 잡은 값이다.

> 참고: **`/clear`는 새 세션마다 시스템 프롬프트·도구 정의를 캐시 쓰기 가격으로 재적재해서 54% 더
> 비싸다**는 실측이 있다([problem-set.md](../problem-set.md)). 이 문제 규모(죽은 데이터 96KB)에서는
> 그 재적재 비용을 넘어설 가능성이 높지만, `/compact` 쪽이 더 안전한 답일 수 있다.

## 채점

- **테스트**: 위 기대값 전부(히든 이식 후 7단계 전체).
- **rubric 5개** — 다시 돌릴 수 있는 형태로 남겼는가, 세 직무 로직이 뒤엉키지 않았는가, 채팅으로만
  받은 비관습 규칙 반영, 7단계에서 앞 코드를 재사용했는가, 가독성.
- **시간**: 25분 초과부터 감점, 45분 실격.
- **게이트(통과 판정)와 채점 기준이 다르다** (2026-08-12):
  - **전 단계(1~7)**: 게이트는 산출물의 **존재와 형태만** 본다. 정확도는 일절 보지 않는다.
  - **정확도는 완료 시점 히든 테스트에서만** 판정한다(id 목록은 누락/오검출 2건까지 허용).
  - 즉 어느 단계가 미흡하든 **진행은 되지만 `testPassed=false`가 되어 종합 점수가 79점 이하로 캡**된다.

## 진행 전략 (효율 관점)

- **블록 경계(2→3, 4→5, 6→7)가 정리 지점이다.** 특히 4→5 시점에는 후기 데이터가 완전히 죽는다.
- 정리하기 전에 **1·2단계 규칙을 워크스페이스 파일로 외부화**해라 — 7단계에서 반드시 다시 필요하다.
  대화에만 있으면 지우는 순간 사라진다.
- 세 직무를 한 파일에 몰아넣지 마라. rubric 항목이기도 하고, 실제로 단계마다 다른 파일을 건드리게
  되어 재작업이 줄어든다.

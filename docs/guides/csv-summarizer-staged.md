# csv-summarizer-staged 공략집

> ⚠️ **스포일러.** 정답과 히든 테스트 기대값이 그대로 있다. 참가자에게 보이지 마라 — [README](./README.md) 참고.

## 한눈에

| | |
|---|---|
| **측정 대상** | 워크스페이스의 참고 문서(`RULES.md`)를 실제로 읽고 정확히 반영했는가 |
| 난이도 / 분류 | medium / cli-tool |
| 산출물 | `summarize.js` — `node summarize.js <파일경로>` 실행, stdout에 JSON 한 줄 |
| 예산 | `maxCostUsd` $2.0 · 기준선 900,000 가중 토큰 |
| 시간 | 적정 15분 → 하드컷 25분 |
| 실측 완료 시간 | 1.3 ~ 13.1분 (9건) |

출력 형식은 4단계 내내 고정이다. **필드 이름을 바꾸면 전 단계가 깨진다.**

```json
{ "total": 0, "counted": 0, "skipped": 0 }
```

## 이 문제의 성격 — 유일하게 "문서를 주는" 문제다

다른 문제들은 규칙을 채팅으로만 주지만, 이 문제는 **2단계부터 `RULES.md`가 워크스페이스에 풀린다.**
1단계 시점에는 문서가 없고 채팅 요구만 있다.

그래서 측정 대상이 "사람이 Claude에게 그 문서를 읽고 반영하게 만들었는가"다. 문서가 파일로 있다는 건
Claude가 알아서 찾아 읽을 수도 있다는 뜻이라 판별력이 다른 문제보다 약하다 — **`report-xlsx-staged`
이후 만든 문제들이 규칙을 채팅으로만 주는 쪽으로 바뀐 게 이 한계 때문이다**([problem-set.md](../problem-set.md)의
"단계형 문제" 절).

## 단계별 요구와 함정

### 1단계 — 기본 합계

`data/sales_basic.csv`를 읽어 `amount` 합계. 문서 없이 채팅만 보고 만든다.

- 기대값: `{ total: 400, counted: 3, skipped: 0 }`
- 출력 키가 **정확히** `total`/`counted`/`skipped` 세 개여야 한다(히든 테스트가 키 집합 자체를 비교).

### 2단계 — 구분자 확장 + **컬럼 순서 함정**

`.tsv`(탭), `.psv`(파이프) 추가. `RULES.md`가 여기서 처음 풀린다.

| 함정 | 내용 |
|---|---|
| **컬럼 인덱스로 찾으면 죽는다** | 파일마다 컬럼 **순서가 다르다.** 반드시 **헤더 이름이 정확히 `amount`**인 컬럼을 찾아야 한다 |
| 구분자 판정 | 내용 추측이 아니라 **확장자**로: `.csv`=`,` `.tsv`=`\t` `.psv`=`\|` |

- 기대값: `sales_dept_a.tsv` → `{1665, 3, 0}`, `sales_dept_b.psv` → `{1400, 3, 0}`

> **여기가 이 문제의 주 판별점이다.** 1단계를 인덱스 기반(`cols[2]`)으로 짜면 1단계는 통과하지만
> 2단계에서 컬럼 순서가 바뀌어 소급 무효화된다. 누적 게이트가 정확히 이걸 잡는다.

### 3단계 — RFC 4180 따옴표

- 큰따옴표로 감싼 칸 안에는 **구분자와 개행이 그대로 들어갈 수 있다** — 감싼 상태에서는 분리하면 안 된다.
- 감싼 칸 안의 큰따옴표는 `""`로 이스케이프.
- 기대값: `sales_quoted.csv` → `{3626, 4, 0}`

`line.split(",")` 류의 순진한 파싱이 여기서 깨진다. 상태 기계(state machine)로 다시 짜야 한다.

### 4단계 — 더러운 값 판정 + **반올림 함정**

여기가 비관습 규칙이 몰려 있는 곳이다.

| 값 | 판정 | 이유 |
|---|---|---|
| `1,200` | **유효 → 1200** | 천단위 쉼표는 제거하고 숫자로 |
| `₩1,200`, `$50` | **skip** | 통화 기호가 붙으면 무효 |
| `-500` | **유효(합산 포함)** | 환불/차감 건 |
| `-` (단독) | **skip** | 부호만 있고 숫자가 없음 |
| 빈 칸, `N/A`, `TBD` | skip | |

- **반올림**: 소수점 셋째 자리에서 반올림하되 **경계값(0.005)은 항상 올림**. JS의 `Math.round`는
  음수에서 이 규칙과 어긋나므로 그냥 쓰면 틀린다.
- 헤더 행은 `counted`/`skipped` 어디에도 세지 않는다.
- 기대값: `sales_dirty.csv` → `{ total: 934.01, counted: 3, skipped: 6 }`

## 정답 요약

```
파싱:  확장자 → 구분자 결정 → RFC4180 상태기계로 분리 → 헤더에서 amount 위치 찾기
판정:  쉼표 제거 → /^-?\d+(\.\d+)?$/ 매치 → 통과하면 합산, 아니면 skip
집계:  합계는 셋째 자리 반올림(경계 올림) 후 둘째 자리까지
```

## 흔한 실패 패턴

| 증상 | 원인 |
|---|---|
| 1단계 통과 → 2단계 실패 | 컬럼을 인덱스로 찾음 (**가장 흔함**) |
| 2단계 통과 → 3단계 실패 | `split(구분자)` 순진 파싱 |
| 4단계 total만 1~2원 어긋남 | 반올림 경계 처리 (`Math.round` 그대로 씀) |
| 4단계 skipped 개수가 다름 | `1,200`을 skip 처리했거나 `-500`을 제외함 |
| 전 단계 실패 | 출력 키 이름을 `sum`/`count` 등으로 바꿈 |

## 채점

- **테스트**: 위 기대값 전부(히든 이식 후 4단계 전체).
- **rubric**: 단계 요구 반영, `RULES.md` 비관습 규칙 반영, 확장 가능한 구조(파싱/판정/합산 분리), 가독성.
- **시간**: 15분 초과부터 감점, 25분 실격.

## 진행 전략 (효율 관점)

- `RULES.md`는 단계마다 **갱신**된다. 2단계에서 읽은 내용이 4단계에서 그대로일 거라 가정하면 틀린다.
- 파싱/판정/합산을 처음부터 분리해두면 3·4단계가 순수 추가가 된다 — 매 단계 전면 재작성하면
  그만큼 턴이 늘고 토큰이 나간다(rubric에도 이 항목이 있다).

## 모든 문제에 공통인 것

### 단계 게이트

**단계 수는 문제마다 다르다(2~10).** 4단계가 기본값이 아니다 — 새 문제를 만들 때 4에 맞추지 마라.
단계 수는 문제의 성격이 정한다([problem-set.md](../problem-set.md)). `inventory-digest-staged`가
7단계인 건 **서로 무관한 직무 세 개를 블록으로 끼워야** 컨텍스트를 끊을 기회와 안 끊었을 때의 대가가
같이 커지기 때문이다.

대시보드의 "이 단계 제출"을 누르면 그 단계의 게이트 테스트만 돌고
**통과/실패만** 알려준다 — 어떤 assert가 깨졌는지는 절대 안 알려준다. 통과해야만 다음 단계의
리소스(데이터/문서)가 워크스페이스에 풀리고 요구사항 텍스트가 화면에 이어붙는다.

게이트는 **누적**이다(`stage1.test.js stage2.test.js ...`). 뒤 단계 작업이 앞 단계 동작을
깨뜨리면 그 자리에서 바로 빨개진다 — 이게 여러 문제에서 판별력의 핵심이다.

**예외 하나 — `calculator-web-staged`는 게이트가 아무것도 안 잡는다.** 모든 단계의
`gateTestCommand`가 `node -e ""`라 워크스페이스 상태와 무관하게 무조건 통과하고, 채점은 완료 시점
히든 한 번뿐이다. 안전망을 **일부러** 없앤 것이며(그래야 "새 기능 얹다가 앞 기능을 깼는가"가 마지막에
드러난다), 다른 문제의 기본형과 반대라는 걸 알고 봐야 한다.

### 조기 완료가 이득이 안 되는 이유

`hiddenTestsPath`가 지정돼 있어서, "완료"를 누르는 순간 **전체 단계 테스트**가 워크스페이스에
덮어써진 뒤 채점된다. 2단계까지만 풀고 일찍 끝내면 `npm test`는 통과해도 최종 채점에서
나머지 단계가 정확히 실패한다.

### 점수 구조

```
품질   = 테스트 통과(40%) + LLM 루브릭 채점(60%)
본점수 = 품질 × 0.7 + 토큰효율 × 0.3
최종   = 본점수 − 시간감점        (테스트 실패 시 79점으로 강제 캡)
통과   = 80점 이상
```

- **토큰효율**: `referenceWeightedTokens` 이하면 만점, 2배면 0점, 사이는 선형.
- **시간감점**: 적정 시간까지 0점, 하드컷까지 선형으로 **최대 20점**. 빨리 끝내도 가산점은 없다.
- **rubric에는 자동 테스트가 이미 검증하는 항목을 넣지 않는다.** 겹치면 신호는 안 늘고
  채점자가 확정된 사실을 뒤집는 오판만 는다(실측 사고, [evaluation.md](../evaluation.md)).

### 하드컷 (넘으면 즉시 종료 + 실격, 부분 점수 없음)

- `maxCostUsd` — 화면에는 **가중 토큰**으로 표시된다(100만 가중 토큰 = $1).
- `maxDurationMs` — 사람이 읽고 생각하고 타이핑한 시간까지 전부 포함된 벽시계 시간.
- `maxTokens` — 폭주 백스톱. 정상 동작에서는 먼저 걸리지 않는다.

가중 토큰이라 **같은 작업도 비싼 모델로 풀면 예산을 더 빨리 쓴다.** 버그가 아니라 의도다 —
실제로 구독 한도를 그만큼 더 쓰기 때문이다.

## 문제를 고칠 때 지킬 것

- **함정 값은 비관습적으로 고른다.** "합리적인 개발자라면 이렇게 했을 것"과 달라야, 문서를
  안 읽고 지어낸 스펙이 우연히 맞는 일이 없다.
- **정답/naive 양쪽을 실제로 돌려서 확인한다.** naive가 *어느 단계에서* 걸리는지까지.
- **참가자 노출 텍스트에 메타 힌트를 넣지 않는다.** 문제 `id`도 워크스페이스 폴더명이 되어
  VS Code 제목에 뜨므로 노출 대상이다.

자세한 설계 원칙은 [problem-set.md](../problem-set.md), 채점은 [evaluation.md](../evaluation.md),
실행 메커니즘은 [manual-mode.md](../manual-mode.md).

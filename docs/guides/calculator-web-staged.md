## 이 문제만 다른 점 — 게이트가 아무것도 안 잡는다

다른 문제는 **매 단계 게이트가 통과를 확인**해서 3단계 작업이 1단계를 깨면 그 자리에서 잡는다.
**이 문제는 정확히 그 반대다.**

- 모든 단계의 `gateTestCommand`가 `node -e ""` — **워크스페이스 상태와 무관하게 무조건 통과**한다.
  "이 단계 제출"은 게이트가 아니라 **"손님이 확인만 하고 넘어가는" 넛지**다.
- `unlockPath`는 전부 `null`. 중간에 풀리는 리소스가 없다 — 요구사항은 오직 채팅(`promptAddition`)으로만
  도착한다.
- 채점은 **완료 시점 히든 테스트 한 번**뿐이다. 1~6단계 요구가 **동시에 살아있는지**를 여기서 처음이자
  마지막으로 본다.

그래서 **재는 게 달라진다**: 대충 하는 사람은 방금 요청한 것만 고치고 앞걸 회귀시켜 마지막에 우수수
떨어지고, 꼼꼼한 사람은 매번 전체를 다시 확인한다. 바이브 코딩의 가장 흔한 실패 모드다.

> **정직한 한계(브리프 §0 그대로)**: 계산기는 프롬프트 한 방으로도 풀리므로 **하네스 엔지니어링 기술은
> 여기서 안 갈린다.** 그건 결함이 아니라 의도다(워밍업/기준선). 변별은 회귀 여부 + 엣지케이스에서만
> 미세하게 난다.

## 시작 상태

`problems/starters/calculator-web-staged/` = `index.html`(Hello World + 빈 `#result`) + `calc.js`(스텁)
+ `server.js` + `package.json`.

`autoStartCommand: "npm start"`라 **워크스페이스를 열면 서버가 자동으로 뜬다**(포커스는 안 뺏는다 —
사람이 타이핑할 곳은 claude 세션 터미널이다). 참가자는 `http://localhost:5173`에서 Hello World를 바로 본다.
포트가 물려 있으면 `server.js`가 5183까지 하나씩 올려가며 잡는다.

`calc.js` 스텁이 못박는 건 **구조뿐**이다 — 함수명·반환타입(문자열)·연산자 ASCII 표기(`+ - * /`).
괄호/에러/소수점/나머지/루트/로그는 **전부 채팅으로만** 도착한다(검증에서 확인).

## 단계별 요구와 히든 기대값

| 단계 | 채팅으로 도착하는 요구 | 히든 test 이름 | 기대값 |
|---|---|---|---|
| 1 (`prompt`) | 사칙연산 + 클릭 버튼 | `1단계: 사칙연산` | `2+3`→`5`, `6-2`→`4`, `4*3`→`12`, `8/2`→`4` |
| 2 | 키보드 입력 | (없음 — rubric에서만 본다) | 키 입력 경로까지 규약으로 못박지는 않았다 |
| 3 | 괄호 + 곱셈 우선 | `3단계: 괄호와 연산 우선순위` | `(2+3)*4`→`20`, `2+3*4`→`14`, `2*(3+4)-5`→`9` |
| 4 | ÷0·잘못된 식 → `Error` | `4단계: 0으로 나누기와 잘못된 식은 Error` | `5/0`, `2+*3`, `(2+3` → 전부 `"Error"` |
| 5 | 표시용 숫자 정리 | `5단계: 표시용 숫자 정리` | `0.1+0.2`→`0.3`, `4/2`→`2`, `1.5*2`→`3`, `10/4`→`2.5` |
| 6 | `%` / `sqrt` / `log`(상용) | `6단계: 나머지 연산` · `6단계: 루트` · `6단계: 상용로그` | `7%3`→`1`, `sqrt(9)`→`3`, `sqrt(-1)`→`Error`, `log(100)`→`2`, `log(0)`→`Error` |

**모든 기대값은 채팅 질문 안에 못박혀 있다.** 브리프 §6의 원칙 — 확인 질문은 캐주얼하지만 히든이
의존하는 규약(표기 `7%3`/`sqrt(9)`/`log(100)`, 상용로그, `Error` 문자열, `2.0` 아니고 `2`)은 질문 문장에
그대로 들어간다. "측정 축이 아닌 곳에서 결과가 흔들리면 문제가 목적을 잃는다".

## 화면도 결정론적으로 잰다 (2026-08-14, 실사용 사고 후 추가)

처음엔 브리프 §5대로 **화면은 rubric으로만** 봤다. 그게 실사용에서 무너졌다 — run `c3f5bfff`는
`ui.js`의 `document.querySelectorAll("#pad button[data-insert]")`가 `#pad`만 덮어서 **`#sciPad`에 있던
괄호·√·log·% 버튼이 전부 클릭 무반응**이었는데(키보드 타이핑만 됐다), `calc.js`는 정말 정확해서 히든
7/7 통과 → **90점**이 나왔다. 소스를 읽는 LLM 채점자는 rubric을 콕 집어 고쳐도 **두 번 다** 못 잡았다
(오히려 "괄호/루트/로그 화면 입력 가능"에 5점). 자세한 경위는 [evaluation.md](../evaluation.md).

그래서 히든에 `tests/ui.test.js` + `tests/chrome.js`를 넣었다. **설치된 Chrome(없으면 Edge)을 헤드리스로
띄워 버튼을 진짜로 클릭**하고 `#result`를 읽는다. 의존성 0 — Node 24 내장 `fetch`/`WebSocket`으로 CDP를
직접 말하고, 워크스페이스는 채점기가 자체 서버로 서빙한다(참가자가 `server.js`를 손대도 화면 채점이
흔들리지 않게).

**화면 규약(채팅으로 못박음, 마크업/프레임워크/디자인은 자유)**:

| 규약 | 도착 시점 |
|---|---|
| 결과는 `id="result"` 요소 안에 값만 텍스트로 (스타터 `index.html`에 빈 요소로 자리 잡아둠) | 1단계 `prompt` |
| 버튼에 `data-key`: 숫자 `0`~`9`, `.`, `+ - * /`, `=`, `clear` | 1단계 `prompt` |
| `(` `)` | 3단계 |
| `%` | 6단계 |

**화면에서 재는 것**(애매함이 없는 것만 — 루트/로그는 "9 누르고 √"인지 "√ 누르고 9"인지가 구현마다
갈려서 `calc.js` 쪽에만 남겼다):

| 클릭 순서 | 기대 `#result` |
|---|---|
| `( 2 + 3 ) * 4 =` | `20` |
| `7 % 3 =` | `1` |
| `5 / 0 =` | `Error` |
| `0 . 1 + 0 . 2 =` | `0.3` |

**버튼은 `data-key` → 없으면 라벨 텍스트 순으로 찾는다(2026-08-14, 실사용 실패 후 추가).** 첫 실사용에서
`data-key`를 하나도 안 달고 키패드를 배열에서 동적으로 그려낸 산출물이 나왔는데 **계산기는 멀쩡히
동작했다.** 그대로 두면 "화면은 잘 되는데 계속 실패"가 되고, 그건 화면이 동작하는가가 아니라 속성
이름을 지켰는가를 재는 것이다 — 측정 축이 아닌 곳에서 결과가 갈리면 안 된다. 그래서 사람이 하듯
**버튼에 쓰인 글자로도** 찾는다(`×`/`*`, `÷`/`/`, `−`/`-`, `AC`/`C`/`clear` 등 관습 표기 전부 수용).
검증에도 "data-key 없이 라벨만 있는 화면도 전부 통과한다"를 넣었다.

⚠️ **채점 머신에 Chrome/Edge가 있어야 한다.** 없으면 이 테스트는 조용히 건너뛰지 않고 **명시적으로
실패**한다 — 조용히 넘어가면 깨진 화면이 만점으로 통과해버리기 때문이다. `CHROME_PATH`로 경로를
지정할 수 있다.

## 정답 경로

표현식 파서(재귀 하강)로 가면 자연히 다 통과한다. 검증 스크립트의 `REFERENCE_CALC`가 그 형태다:
토큰화 → `expr`(+,-) → `term`(*,/,%) → `unary` → `atom`(괄호·`sqrt`·`log`·숫자), 표시는
`String(Number(n.toPrecision(12)))`(부동소수점 잔재 제거 + 불필요한 `.0` 제거를 한 줄로 해결),
예외/비유한값은 전부 `"Error"`.

**위험 경로**: 버튼 누적식으로 왼쪽부터 계산하는 순진한 계산기로 시작하면 3단계 괄호에서 전면
재작성이 필요해지고, 그 과정에서 앞 기능을 깨기 쉽다. 게이트가 안 잡아주므로 완료 시점에 한꺼번에
드러난다 — 이게 이 문제가 노리는 지점이다.

**실사용에서 나온 또 하나의 오답**: 공학용 계산기 관습대로 `%`를 **퍼센트**로 구현하고 나머지는
` mod ` 표기로 둔 산출물(`evaluate("7%3")` → `"0.21"`). 6단계 채팅이 `7%3` 표기로 나머지를 못박았으므로
정확히 그 항목에서 떨어진다.

## rubric (이제 진짜로 테스트가 못 재는 것만)

마우스/키보드 둘 다 동작 / `calc.js`↔`index.html` 분리 / 가독성. **산술 정확성은 넣지 않았다** —
node-test가 이미 결정론적으로 재므로 겹치면 신호는 안 늘고 오판만 는다(`docs/evaluation.md` 실측 교훈).

## 검증 (`scripts/verify-calculator-web-staged.mjs`, 18개 체크 전부 통과)

- **게이트 무력화** — **빈 디렉터리로도 6단계 전부 통과**한다(이 문제의 정체성).
- **정답** — 정석 구현(계산 + 화면)이 히든 8/8 통과.
- **스텁 그대로면 7/8 실패** — 스텁이 항상 `"Error"`라 4단계 항목 하나만 공짜로 통과한다(무해).
- **방법 중립** — `data-key` 없이 라벨(`×`, `÷`, `AC` …)만 있는 화면도 전부 통과한다.
- **실사용 사고 재현** — `calc.js`는 정석 그대로 두고 리스너 셀렉터만 한쪽 컨테이너로 좁힌 페이지
  (= run c3f5bfff의 상황)를 넣으면 **화면 테스트만 정확히 실패**한다. 이게 이 축을 추가한 이유 그 자체다.
- **회귀 검출 4종** — 한 군데씩만 깬 구현이 **정확히 그 test만** 실패: 우선순위 되돌림→3단계,
  부동소수점 정리 누락→5단계+화면, ÷0 가드 제거→4단계+화면, 자연로그→6단계 상용로그.
- **시작 상태** — 서버가 실제로 Hello World를 응답하고 페이지가 `calc.js`를 import 한다.
- **말끔함** — 스타터에 2~6단계 함정 키워드가 없고, 참가자 노출 텍스트에 내부 용어/파일명이 없다.
- 실제 VS Code 창에서 **자동 태스크 2개(claude 세션 + `npm start`)가 같이 뜨는 것**까지 확인
  (`scripts/verify-autotask-launch.ts`, 서버는 5173에서 Hello World 응답).

## 예산/시간 상향 (2026-08-14, 첫 실사용 직후)

처음엔 $1.0 / 기준선 400,000 / 적정 5분 → 하드컷 15분으로 잡았는데, **실제로 풀어보니 토큰도 시간도
모자랐다**(사용자 보고). 워밍업 문제는 실격을 유도하면 목적 자체가 무너지므로 —기준선 역할을 하려면
정상적으로 시도한 사람이 전부 완주해야 한다— 예산을 **3배**($3.0 / 기준선 1,200,000 / 백스톱 6,000,000),
시간을 **적정 10분 → 하드컷 20분**으로 올렸다.

계산기가 "쉬운 과제"라는 건 코드 난이도 얘기지 **턴 수 얘기가 아니었다**는 게 여기서 드러난다 —
요구사항이 6번에 나눠서 도착하고 매번 화면까지 손보므로 턴이 계속 쌓인다(저장소 실측 기준 턴당 약
42,300 가중 토큰). 새 문제의 예산을 코드 난이도로 어림하면 안 된다는 교훈.

## 점수 눈금 재보정 (2026-08-14, 실사용 run `ef6e1ffc` 기준)

소넷으로 "공학용 계산기 만들어줘" 한 번 던진 run이 rubric 4.67 / 723,019 가중 토큰 / 5.1분으로
**97점**을 받았고, 사용자 판단이 "그 정도면 90점"이었다. 두 가지를 바꿨다:

- **기준선 1,200,000 → 1,000,000** (하드컷 $3.0 = 3,000,000 가중 토큰은 유지)
- **루브릭 눈금을 전역 재보정** — 평균 3.5 이하 = 0%, 5.0 = 100%(`JUDGE_SCORE_FLOOR`).
  자세한 근거와 소급 영향은 [evaluation.md](../evaluation.md).

결과 (테스트 통과 · 적정 시간 내):

| rubric \ 가중 토큰 | 40만 | 70만 | 100만 | 140만 | 200만 |
|---|---|---|---|---|---|
| **5.00** | 100 | 100 | 100 | 88 | 70 |
| **4.80** | 94 | 94 | 94 | 82 | 64 |
| **4.67** | 91 | **91** ← 그 run | 91 | 79 | 61 |
| **4.50** | 86 | 86 | 86 | 74 | 56 |

토큰은 기준선을 넘길 때만 깎인다.

## ⚠️ 아직 검증 안 한 것

- **상향한 예산/시간도 실측 분포가 아니라 한 번의 실사용에 맞춘 값이다.** run이 몇 건 쌓이면 실제
  분포로 다시 조인다.
- **"회귀시키는 사람이 실제로 있는가"** 는 라이브 데이터가 필요하다. 여기서 아무도 안 떨어지면 이
  문제는 순수 온보딩용으로만 기능하는 것이고, 그것도 그 자체로 유효한 결과다.

# access-audit-staged 공략집

> ⚠️ **스포일러.** 정답과 히든 테스트 기대값이 그대로 있다. 참가자에게 보이지 마라 — [README](./README.md) 참고.

## 한눈에

| | |
|---|---|
| **측정 대상** | 채팅으로만 전달된 비관습 규칙을 정확히 반영하고, 단계가 쌓여도 앞 규칙을 안 깨뜨리는가 |
| 난이도 / 분류 | hard / log-analysis |
| 산출물 | `audit.js` — `node audit.js data` 실행, stdout **마지막 줄**에 JSON 한 줄 |
| 예산 | `maxCostUsd` $2.0 · 기준선 900,000 가중 토큰 |
| 시간 | 적정 15분 → 하드컷 25분 |
| 실측 완료 시간 | 1.6, 9.2, 10.1분 (3건) |

로그 형식(파이프 구분):

```
시각|사용자ID|메서드와경로|상태코드|응답시간|User-Agent
```

## ⚠️ 원래 의도와 실제 측정 대상이 다르다

이 문제는 **"스킬을 써야 토큰을 아껴서 통과할 수 있는 문제"**로 만들어졌다. 전제는 "로그가 크니까
(누적 299KB) 원본을 컨텍스트에 올리면 비싸고, 스킬/스크립트로 오프로딩해야 통과한다"였다.

**실측으로 그 전제가 반증됐다**([problem-set.md](../problem-set.md)의 "스킬은 토큰 절약 수단이 아니다"):

- 비용은 바이트가 아니라 **턴**에서 나온다 — 저장된 run 8건(247턴) 분해 결과 **턴당 $0.0423**.
- 4-arm A/B 결과 **스킬 쪽이 한 세션에서 20%, 새 세션에서도 12% 더 비쌌다** — 스킬을 찾고 SKILL.md를
  읽는 도구 호출로 **배치당 +2.3턴**이 붙기 때문.
- 손익분기: 매번 재입력해야 하는 지시문이 **약 16,450토큰(≈56KB) 이상**이어야 스킬이 본전이다.
- 스킬이 실제로 이긴 곳은 비용이 아니라 **정확도**였다(A/B에서 스킬 arm만 18/18 만점).

그래서 예산 근거($1.50)가 무너져 다른 문제와 같은 $2.00으로 되돌렸고, rubric에서 관련 항목도 교체했다.

**미해결**: 산출물이 코드라서 규칙이 `audit.js`에 박히면 **코드 자체가 규칙 저장소**가 된다 — 컨텍스트를
비워도 규칙을 안 잊어버리므로 품질 축에서도 스킬이 개입할 여지가 없다. 제대로 측정하려면 코드에 안 박히는
판단 작업이 단계에 섞여야 한다(`inventory-digest-staged` 2단계 같은 형태). 아직 반영 안 됨.

**지금 검증된 측정 대상은 위 "한눈에"에 적은 것**이고, 그 부분은 정상 동작한다(naive는 1단계에서 탈락).

## 비관습 규칙 — 전부 채팅으로만 준다

워크스페이스에 규칙 문서가 **없다.** 관습대로 짜면 1단계부터 값이 갈린다.

### ① 성공 판정

| 상태 코드 | 판정 | 관습 |
|---|---|---|
| 2xx | 성공 | 같음 |
| **499** (클라이언트가 먼저 끊음) | **성공** | 보통 실패로 침 |
| **3xx** | **실패** | 보통 성공 취급 — "리다이렉트는 라우팅이 잘못됐다는 뜻" |
| 그 외 | 실패 | 같음 |

### ② 봇 제외 — User-Agent를 믿지 마라

- 판정 기준은 UA가 아니라 **같은 사용자ID가 어느 시점이든 1초(1000ms) 이내에 3건 이상** 요청한 적이 있는가.
- 걸리면 **그 사용자의 요청을 전부** 집계에서 뺀다(일부만 빼는 게 아니라 통째로).
- **미끼**: UA에 `curl`, `GoogleBot`이라고 대놓고 적힌 줄을 의도적으로 섞어뒀다. UA로 거르면 틀린다.
- 봇 제외는 **2·3·4단계 전부에 동일하게** 적용된다.

### ③ 반올림이 아니라 **버림**

`successRate`는 백분율, **소수점 첫째 자리까지 버림**(예: 69.98 → 69.9).

## 단계별 요구와 정답

데이터가 **단계마다 하루치씩 늘어난다.** `audit.js`는 `data` 폴더 안 로그를 **전부** 훑어야 한다
(파일명 하드코딩 금지). 누적 데이터가 커지므로 앞 단계 기대값도 단계마다 달라진다 — 각 unlock 디렉터리에
그 시점 기준으로 다시 계산한 `stage1..stageN` 테스트가 전부 들어 있다.

### 1단계

```json
{ "totalRequests": 2120, "successRate": 69.8 }
```

> naive(관습 규칙)는 여기서 즉시 탈락한다 — 총 요청 549 vs naive 540, 성공률 69.9 vs 75.4처럼
> **모든 단계에서 값이 갈린다.**

### 2단계 — 세션 (**경계값 함정**)

`sessionCount` 추가. 같은 사용자의 인접한 두 요청 간격이 **7분을 초과**하면 세션이 끊긴다.

- **정확히 7분(420초)이면 아직 같은 세션.** 초과여야 새 세션이다.
- 관습적인 30분이 아니라 7분이고, 6분59초/7분1초 데이터를 의도적으로 심어뒀다.
- 사용자별 세션 수의 총합. 봇은 세션도 안 센다.
- 기대값: `sessionCount: 692` (`totalRequests: 2120`, `successRate: 69.8` 유지)

### 3단계 — p90 (**계산 방식 함정**)

`p90ByEndpoint` 추가. 키는 로그의 '메서드와경로' 문자열 그대로.

**nearest-rank + 버림, 보간 금지**: 오름차순 정렬 후 `ceil(0.9 × 건수)`번째 값(1부터 세는 순번).

```json
"p90ByEndpoint": {
  "DELETE /api/orders/{id}":  1617,
  "GET /api/inventory":       1602,
  "GET /api/orders":          1681,
  "GET /api/orders/{id}":     1602,
  "GET /api/reports/daily":   1637,
  "POST /api/auth/login":     1592,
  "POST /api/orders":         1563,
  "PUT /api/inventory/{sku}": 1599
}
```

### 4단계 — 이상 사용자 (**두 조건 모두**)

`anomalousUsers` 추가. 조건은 **AND**:
- 세션 수 **5개 이상**, **그리고**
- 그 사용자의 성공률이 **70% 미만**(정확히 70%면 해당 없음)

성공률은 ①의 규칙(2xx·499 성공 / 3xx 포함 나머지 실패)을 사용자별로 적용. 봇은 제외.

**정답 13명:**
```
u_00402 u_00404 u_00407 u_00410 u_00412 u_00413 u_00420
u_00422 u_00423 u_00426 u_00430 u_00431 u_00432
```

## 흔한 실패 패턴

| 증상 | 원인 |
|---|---|
| 1단계부터 값이 안 맞음 | 3xx를 성공으로 처리했거나 499를 실패로 처리 (**가장 흔함**) |
| 총 요청 수가 살짝 많음 | UA로 봇을 걸렀거나, 봇의 일부 요청만 제외 |
| successRate가 0.1 차이 | 버림 대신 반올림 |
| 2단계 sessionCount 근소하게 다름 | 7분 **경계**를 `>=`로 처리 |
| 3단계 p90이 한두 개 다름 | 보간(interpolation) 방식 사용 |
| 뒤 단계에서 앞 단계가 깨짐 | `data` 폴더를 다시 안 훑고 파일명을 하드코딩 |

## 채점

- **테스트**: 위 기대값 전부(히든 이식 후 4단계 전체).
- **rubric**: 사내 집계 규칙 정확 반영, 채팅으로만 전달된 규칙 유지, 뒤 단계가 앞 규칙을 안 깨뜨림,
  확장 가능한 구조, 가독성.
- **시간**: 15분 초과부터 감점, 25분 실격.

## 진행 전략 (효율 관점)

- 규칙이 4단계 내내 계속 필요하다. **워크스페이스 파일(CLAUDE.md 등)에 규칙을 박아두면**
  컨텍스트가 날아가도 살아남는다 — 다만 위 A/B가 보여주듯 그게 토큰을 아껴주지는 않는다.
- 로그를 `Read`로 컨텍스트에 올리지 말고 **스크립트로 집계**하는 게 맞다. 다만 실측상 양쪽 다
  그렇게 하기 때문에 이 문제에서 실제 비용 차이로는 잘 안 나타난다.
- 봇 판정은 **사용자별 전체 요청을 시간순으로 훑는 사전 패스**가 필요하다. 스트리밍으로 한 번에
  집계하려다 재작업하는 경우가 많다.

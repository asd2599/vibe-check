## v1은 실측으로 반증됐다 (2026-08-13, run cd85075a · de559ff8)

v1의 전제는 "naive 단일 세션이 비싸서 예산을 터뜨린다"였는데, 실제로 두 번 돌려보니 틀렸다.

| run | 모델 | 결과 | 가중 토큰 |
|---|---|---|---|
| cd85075a | Haiku | 7단계 완주 | 423,104 = **$1.0 예산의 42%** |
| de559ff8 | Sonnet 5 | 1단계에서 멈춤 | 592,527 (대부분 `handover.md` 한 번 적재하는 cache_write) |

기믹 자체는 기계적으로 작동했다 — Haiku run은 `handover.md`를 통째로 Read해서 상주시켰고,
turn당 cache_read가 16,669 → 83,848로 **단조 증가**했으며 **raw 토큰의 96%가 상주 재독**이었다.
그런데도 안 아팠다. **Haiku의 cache_read 단가가 $0.10/1M이기 때문이다.**

그리고 Haiku의 탈락 사유는 토큰이 아니라 **품질**이었다 — `handover.md`와 무관한 단계에서
이벤트명 정규화를 틀렸다(`addcart`를 `add_cart`로, `pageview`를 `page_view`로 안 합침).

**여기서 나온 결론 두 개가 v2 설계의 뼈대다:**

1. **cache_read가 input보다 10배 싸서**, 큰 자료를 이고 가는 벌점은 싼 모델에선 거의 안 느껴진다.
   "끊어가면 아낀다"는 **Sonnet 이상에서만 체감된다.**
2. **적재 비용(cache_write)은 두 경로가 똑같이 낸다.** 끊어서 아끼는 건 오직 **"적재 후 이고 간
   턴"의 cache_read**뿐이다 — 1단계에서 멈춘 Sonnet run에 차이가 안 난 이유가 이것이다.

### 왜 Sonnet에서 갈리나

| | cache_read (상주 재독) | cache_write 1h (적재) | output |
|---|---|---|---|
| Haiku | $0.10/1M | $0.20/1M | $0.40/1M |
| **Sonnet 5** | **$0.30/1M (3×)** | **$6/1M** | $15/1M |

> 끊어서 아끼는 가중 토큰 ≈ (상주 블록 raw 토큰) × 0.30 × (이후 남은 턴) − 재적재 오버헤드(~114K/회)

Sonnet은 재독이 3배 비싸서 같은 기믹이 Haiku의 3배로 아프다. **여기가 "체감"의 원천이다.**

## v2 구조 — 무거운 블록 3개 + 이후 턴 확보

v1의 7단계 3직무 릴레이 골격은 그대로 두고, **각 직무 블록을 "무거운 자료 적재 + 여러 턴 작업"**으로
살찌웠다. 데이터는 여전히 **산문/반정형**이다 — 표로 주면 스크립트로 접혀서 상주 자체가 안 생긴다
(v1이 `inventory-digest`에서 배운 것).

| 블록 | 단계 | 직무 | 무거운 자료 | 이후 죽은 무게 |
|---|---|---|---|---|
| A | 1~2 | 인프라 | `handover.md` **≈35,722 토큰** | — |
| B | 3~4 | 결제 | `payments/tickets.md` **≈38,021 토큰** (티켓 323건) | A |
| C | 5~6 | 데이터 | `data/access-requests.md` **≈40,125 토큰** (신청서 278건) | A·B |
| 복귀 | 7 | 인프라 | — | A·B·C 전부 |

**3블록 누적 피크 상주 ≈ 113,868 토큰** — v2 문서 2절이 지정한 auto-compact 안전선(~120K) 아래다.
생성기가 이 값을 매번 계산해서 넘으면 경고한다.

각 블록은 **자기 직무에서만 필요**하고 다음 블록과 무관하다 → 끊을 지점이 명확하다.
7단계에서 A·B에서 확정한 값을 **교차 참조**시켜 복귀 턴을 만든다.

> **정직한 한계**: 숙련 참가자는 끊는 대신 **필요한 부분만 grep**해서 상주를 피할 수도 있다.
> 그것도 유효한 관리다. 이 문제는 "끊기 OR 타겟팅" 둘 다 저비용 경로로 인정하고,
> **단일 세션 wholesale-read가 고비용 경로**임을 잰다. 끊기를 유일 정답으로 강제하려면 블록 전체가
> 반드시 상주해야 하는 작업이어야 하는데, 그건 스크립트화(비상주) 또는 판단작업(운)으로 흘러서
> 저장소 원칙과 충돌한다 — 그래서 강제하지 않는다.

## 함정은 3가족만 — 개수가 아니라 격차다

함정을 쌓으면 단계별 통과 확률이 곱해져서 **Haiku만이 아니라 Sonnet도 같이 깎인다**:

| 함정 개수 | Haiku 전부 통과 | Sonnet 전부 통과 |
|---|---|---|
| 4개 (Haiku 60% / Sonnet 95%) | 13% (거의 탈락 ✅) | **81%** (5번 중 1번 탈락 ⚠️) |
| 6개 | 5% | **74%** (4번 중 1번 탈락 ⚠️) |

그래서 **Haiku-miss와 Sonnet-miss의 격차가 큰 함정 3가족**만 쓰고, **4·6단계는 앞 단계 결과를
집계만 하는 무함정 단계**로 둬서 턴만 늘린다(효율 축을 위해 필요하고, 품질 위험은 안 늘린다).

### 함정 ① override 체인 (1·2·7단계, 블록 A)

각 스테이징 값이 문서 안에서 **정확히 3번** 나오고 **뒤가 최신**이다. 문서 머리말이 그 규칙을 명시한다.
**마지막 언급에 "최종/확정" 같은 표식은 일부러 안 넣었다** — 표식이 있으면 그 단어만 찾아도 답이 나온다.

| 키 | ① | ② | **정답 ③** |
|---|---|---|---|
| `stagingPort` | 8080 | 8443 | **7443** |
| `dbSchema` | `staging_v2` | `stg_core` | **`stg_core_v3`** |
| `retryLimit` | 3 | 5 | **2** |
| `stagingHost` | `stg-web-01.internal` | `stg-web-02.internal` | **`stg-edge-07.internal`** |
| `healthPath` | `/health` | `/healthz` | **`/__alive`** |
| `cacheTtlSeconds` | 300 | 900 | **45** |
| `rollbackTag` (7단계) | `rel-2024-11` | `rel-2025-03` | **`hotfix-0217`** |

운영 값은 **1번씩만** 나온다(체인 없음): 포트 `443` / 스키마 `prod_core_r2` / 재시도 `6` /
호스트 `prod-edge-01.internal` / 헬스 `/health-check` / 캐시 `1800`. 로컬은 `localhost`·`3000`.

> **v1에서 바꾼 점**: 운영 값을 "틀리게 만드는 미끼"로만 쓰지 않고 **2단계에서 실제로 요구**한다
> (`prod-config.json`). 1단계에서는 여전히 미끼로 작동하지만, 읽어야 할 정보로 겸용해서
> Sonnet 위험을 안 키우면서 블록 A의 필요 턴은 늘렸다.

### 함정 ② 다변형 정규화 병합 (3단계, 블록 B) — Haiku 킬러

v1 실측에서 Haiku가 **정확히 이 지점에서** 틀렸다(소문자화만 하고 구분자 변형은 안 합침).
같은 원인이 **띄어쓰기·하이픈·밑줄·대소문자만** 다른 6가지 표기로 흩어져 있다:

```
CARD_LIMIT / card_limit / card-limit / cardLimit / Card Limit / CARDLIMIT
```

정식 코드 5개(`CARD_LIMIT` `EXPIRED_CARD` `NETWORK_ERR` `AUTH_FAIL` `NO_FUNDS`)는 **채팅으로** 준다.
구분자를 없애고 대소문자를 무시하면 각 표기가 정확히 하나로 대응한다 — **모호함 0, 판정은 기계적**.

**정답**: `CARD_LIMIT` 55 · `EXPIRED_CARD` 60 · `NETWORK_ERR` **116** · `AUTH_FAIL` 49 · `NO_FUNDS` 43
**소문자화만 하면 20가지로 갈라진다.**

### 함정 ③ 다단 조건 + 경계값 (5단계, 블록 C)

규칙이 **순서대로** 적용되고 예외가 맨 앞에 온다. 경계는 "초과"와 "이상"을 **일부러 섞었다**.

1. 목적이 `사내통계`면 다른 조건과 무관하게 **승인** (여기서 끝)
2. 개인정보 포함 + 승인자 `팀장급` → **반려** (`본부장급`·`임원`은 통과)
3. 조회 기간 **90일 초과** → 반려 (정확히 90일은 통과)
4. 보관 기간 **180일 이상** → 반려 (정확히 180일도 반려)
5. 그 외 승인

**정답 187건.** 흔한 오답: 사내통계 예외 무시 **234** / 보관을 "초과"로 오해 **180** /
조회를 "이상"으로 오해 **193** / 승인자 직급 무시 **180**.
경계값 분포: 조회 90일 28건 · 91일 25건 · 보관 179일 35건 · 180일 20건.

## 게이트는 형태만 본다

게이트 파일은 참가자 워크스페이스로 복사되므로 **기대값을 적으면 문서를 한 줄도 안 읽고 베낄 수 있다.**
그래서 값은 전부 히든에만 있다. 부작용으로 **오답 구현도 게이트 7개를 전부 통과하는데 의도된 동작이다**
— 앞에서 막으면 측정 대상인 3~7단계를 아예 못 밟는다. 부정확함은 완료 시점 히든이 잡아
`testPassed=false`로 종합 점수를 79점에 캡한다.

## 검증 결과 (`scripts/verify-handover-relay-staged.mjs`)

정석 solver는 **상수를 베끼지 않고 워크스페이스 파일에서 직접 값을 뽑아낸다** — 그래야 "데이터가
정답을 유일하게 결정하는가"까지 같이 검증된다.

- **A** 정석 1→7단계 게이트 전부 통과 + 히든 7/7 통과
- **B** 단계 오프셋 — 시작 시점에 블록 B·C 자료가 없고, 3단계에 B만, 5단계에 C가 풀린다
- **C** 게이트가 산출물 없음/빈 객체/타입 불일치/`prod-config.json` 누락을 막는다
- **D** 오답 10종이 **의도한 단계의 히든에서만** 실패:

  | 오답 | 실패 단계 |
  |---|---|
  | `firstMention` — override 무시 (앞 값 사용) | 1, 2, 7 |
  | `useProd` — 스테이징 자리에 운영 값 | 1, 2, 7 |
  | `lowerOnly` — 소문자화만 (구분자 안 없앰) | 3, 7 |
  | `noMerge` — 표기 변형을 서로 다른 원인으로 셈 | 3, 7 |
  | `noExempt` — 사내통계 예외 무시 | 5, 6 |
  | `retentionGt` — 보관을 "초과"로 오해 | 5, 6 |
  | `lookupGte` — 조회를 "이상"으로 오해 | 5, 6 |
  | `ignoreRank` — 승인자 직급 무시 | 5, 6 |
  | `https` — 체크리스트 URL을 https로 | 7 |
  | `staleRollback` — 롤백 태그를 옛 값으로 | 7 |

- **E** 조기 완료 차단 (2단계까지만 → 3~7 실패 / 4단계까지 → 5~7 실패)
- **F** 말끔함 0건 + 문제 파일 스키마
- **G** 블록 크기·누적 상주·override 체인 3회·병합 후 5코드·경계값 분포

### 검증 중에 실제로 잡은 문제

**문서 자체가 모호했다.** 승인자 이름 풀에 `박팀장`이 있는데 직급 어휘도 `팀장`이라, 정석 구현조차
5·6단계에서 틀렸다. 사람이 읽어도 헷갈리는 지점이고, **측정 축이 아닌 곳에서 결과가 갈린다.**
직급을 `팀장급`/`본부장급`/`임원`으로 바꾸고 블록 C 이름 풀을 직급 낱말 없는 이름으로 분리해 고쳤다.

## ⚠️ 아직 검증 안 한 것 — 이 문제의 합격선이 여기 있다

v2 개정안 6절이 **합격선으로 지정한 것**은 아래 셋인데, 전부 **라이브 모델 실행이 필요해서 안 돌렸다.**

1. **Sonnet 2-arm 토큰 A/B (합격선)** — (a) 각 블록 wholesale Read + 단일 세션 vs
   (b) 블록마다 값만 외부화 후 끊기. **두 arm이 히든을 똑같이 통과하면서 가중 토큰이 ≥30% 갈려야**
   이 문제가 목표를 이룬 것이다. 안 갈리면 블록을 키우거나 이후 턴을 늘려 재조정해야 한다.
2. **Haiku ×5 전탈락 (0/5) / Sonnet ×5 전통과 (5/5)** — 통과하는 Haiku run이 있으면 격차 큰 함정을
   하나 더 넣고, 탈락하는 Sonnet run이 있으면 **그 원인 함정을 뺀다**(더 세게 깔지 않는다).
3. **auto-compact 무발생** — naive arm에서 3블록 상주가 자동 압축을 유발하지 않는지. 계산상
   113,868 토큰이라 안전선 아래지만 실제 확인은 안 했다.

**그래서 예산도 잠정값이다.** 개정안은 `maxCostUsd`를 "A/B 후 두 arm 사이"에 놓으라고 했고
**이상형은 단일 세션 실격 / 끊으면 통과**다. 지금은 실측이 없어서 **안전형($3.0)**으로 뒀다 —
조여놨다가 틀리면 정상 시도까지 전원 실격시키기 때문이다(이 저장소가 `csv-summarizer`,
`inventory-digest`에서 두 번 겪은 실패). **A/B 후 반드시 이상형으로 조일 것.**

시간(적정 35분 → 하드컷 60분)도 외삽이다.

## 이 문제는 사실상 Sonnet 전용이다

`inventory-digest-staged`가 Haiku 전용이었던 것의 **정반대**다. 예산은 Sonnet 가중 토큰으로 잡고,
**Haiku는 예산이 아니라 품질(함정 ②·③)에서 걸러진다.** 두 실패를 **다른 축**으로 분리한 건
서로 간섭하지 않게 하려는 의도다(v2 개정안 1절, 사용자 확정).

## 리소스 재생성

```
node scripts/gen-handover-relay-staged.mjs     # 결정론적 — 같은 시드면 같은 결과
node scripts/verify-handover-relay-staged.mjs  # 약 4분
```

생성기가 `docs/guides/handover-relay-staged.answers.json`에 정답을 같이 떨어뜨린다.
**시드를 바꾸면 3~7단계 기대값이 전부 바뀐다** — 이 문서의 숫자도 같이 고쳐야 한다.

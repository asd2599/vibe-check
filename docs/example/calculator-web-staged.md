# 문제 설계 브리프 — 웹 계산기 (기초 워밍업 · "안전망 없는 스펙 누적" 측정)

> 이 문서는 **완성 문제가 아니라 "문제 저자 브리프"** 다. Claude Code(또는 `new-problem` 스킬)가 읽고
> `problems/calculator-web-staged.json` + `problems/starters/calculator-web-staged/`(+ 히든 테스트)를
> 스캐폴딩할 수 있게 필요한 걸 다 담았다.
>
> 이 문제는 기존 문제들과 **성격이 다르다** — 함정·비관습 규칙을 숨기는 게 아니라, **누구나 통과하는
> 쉬운 과제**로 (1) 참가자가 실행 흐름을 익히고, (2) 본인의 기준선(시간·토큰)을 만들게 하는 게 목적이다.

---

## 0. 이 문제의 자리 & 무엇을 재는가

현재 문제 세트는 전부 "함정 있는 고난도 단계형"이라 **처음 온 사람이 몸 풀 문제가 없다.** 이 문제가
그 자리를 채운다. 두 가지를 노린다:

1. **온보딩/기준선**: 문제 고르기 → 워크스페이스가 **이미 웹페이지가 떠 있는 상태**로 열림 → 계산기를
   만들고 → "완료" → 시간/토큰 확인. 이 흐름을 가볍게 익히고, 쉬운 과제에서의 raw 시간·토큰을 재둬서
   나중에 어려운 문제와 비교할 잣대를 만든다.
2. **안전망 없는 스펙 누적(측정 축)**: 기존 문제는 **매 단계 게이트가 통과를 확인**해서 3단계가 1단계를
   깨면 즉시 잡는다. **이 문제는 그 반대다** — 중간엔 아무것도 안 잡고, 요구사항을 **손님이 물어보듯
   확인 질문으로만** 하나씩 던지고, **최종에 한 번만** 전부 검사한다. 그래서 재는 게 달라진다:
   **"새 기능을 얹으면서 앞 기능을 안 깨뜨리고 끝까지 유지하는가."** 게이트가 안 잡아주니, 대충 하는
   사람은 방금 요청한 것만 고치고 앞걸 회귀시켜 마지막에 우수수 떨어지고, 꼼꼼한 사람은 매번 전체를
   다시 확인한다. 바이브 코딩의 가장 흔한 실패 모드다.

> **정직한 한계**: 계산기는 프롬프트 한 방으로도 풀 수 있어 "하네스 엔지니어링 기술"은 여기서 **안
> 갈린다.** 그건 결함이 아니라 이 문제의 의도다(워밍업/기준선). 변별은 **회귀 여부 + 엣지케이스**에서만
> 미세하게 나온다.

## 1. 핵심 메커니즘 — 게이트 없이 "확인만", 최종에만 채점

기존 `stages` 스키마를 그대로 쓰되 **게이트를 무력화**한다(스키마 변경 없음):

- 각 단계 `gateTestCommand`를 **항상 통과하는 no-op**으로 둔다 (예: `node -e ""`). 그러면 "이 단계 제출"이
  **워크스페이스 상태와 무관하게 무조건 다음 단계를 연다** = "결과 안 보고 확인만 하고 넘어감".
  (스키마가 `gateTestCommand` 생략을 허용하면 생략해도 됨 — 스캐폴딩 시 `loadProblem` 확인.)
- 각 단계 `promptAddition`은 **손님이 슬쩍 물어보는 확인 질문 톤**으로 쓴다("괄호 넣은 식도 되나요?").
  참가자는 이 질문을 하네스에 답하는 게 아니라 **Claude에게 반영**한다 — 즉 강제 게이트가 아니라 넛지.
- `hiddenTestsPath`가 **완료 시점에 딱 한 번, 누적된 요구사항 전부**를 검사한다. 이게 유일한 채점이며,
  일찍 끝내는 게 이득이 안 되게 막는 backstop이다(`docs/problem-set.md`의 조기 완료 차단 원칙 그대로).

## 2. 시작 상태 — Hello World가 떠 있는 스타터

```
calculator-web-staged/
├── index.html     # 지금은 "Hello World"만 표시 (페이지가 실제로 뜬다는 것만 증명)
├── calc.js        # 계산 로직 스텁 — 참가자가 여기 evaluate()를 구현
├── server.js      # 의존성 없는 정적 서버 (game-tactics-staged 패턴 재사용)
└── package.json   # "test": "node --test" , type: module
```

- **워크스페이스가 열리면 페이지가 바로 떠 있게** 한다 — 자동 실행 태스크로 `node server.js`를 띄우고
  참가자가 `localhost:PORT`에서 Hello World를 즉시 본다(자동 태스크는 `writeVsCodeAutoRunTask` 흐름에
  맞춰 스캐폴딩 — 서버 기동 + 안내). 무거운 브라우저 자동화는 안 쓴다.
- **`calc.js` 스텁**(구조적 최소 힌트, 이게 채점 접점이라 반드시 필요):
  ```js
  // 계산 로직을 이 함수로 구현하세요.
  // 입력: 사용자가 만든 수식 문자열(expr), 반환: 화면에 그대로 표시할 "문자열".
  export function evaluate(expr) {
    return "Error";
  }
  ```
  → **함정값(괄호/÷0/로그 등)은 스텁에 없다.** 구조(함수명·반환타입)만 준다. 실제 요구사항은 전부
  4번의 확인 질문으로만 도착한다.
- README 등 부가 설명 파일은 두지 않는다(스텁 주석이 유일한 구조 안내).

## 3. 시나리오 프롬프트 (`prompt` = 1단계) — 설명 없이

```
[슬랙 DM - 이대리]
어? 페이지는 잘 뜨네요 👍 여기다 계산기 하나 만들어 주실 수 있어요?
숫자 버튼 눌러서 계산되는 거요. 일단 그거부터 부탁해요!
```

- 사칙연산 + **클릭 버튼**만. 세부 규칙·필드명·엣지케이스는 **일절 안 준다.** "계산기"라는 단어만.

## 4. 단계 설계 (`stages`) — 확인 질문 6개, 전부 게이트 없음

| 단계 | 확인 질문(`promptAddition`, 캐주얼 톤) | 최종 검사 반영 | 채점 |
|---|---|---|---|
| 1 | (위 `prompt`) "계산기 만들어줘" | 사칙연산 + 클릭 버튼 | node-test + rubric |
| 2 | "아 그리고 버튼 말고 **키보드로도** 숫자랑 연산 입력되면 좋겠어요" | 키보드 입력 | rubric |
| 3 | "**괄호** 넣은 식도 계산돼요? 예를 들면 (2+3)×4 같은 거요" | 괄호/연산 우선순위 | node-test |
| 4 | "**0으로 나누면** 어떻게 나와요? 이상한 값 말고 그냥 에러로 떠주면 좋겠네요" | ÷0 → `"Error"` | node-test |
| 5 | "0.1+0.2 같은 것도 **0.3**으로 깔끔하게 나오죠? 지저분한 소수점 나오면 안 돼요" | 부동소수점 정리 | node-test |
| 6 | "마지막으로 **나머지 연산(%)**이랑 **루트·로그**도 되면 좋겠어요. 로그는 상용로그(log10)로요!" | %, sqrt, log10 | node-test |
| 완료 | — | **1~6 전부 한 번에** | 히든 |

**핵심**: 2~6단계에서 아무도 안 잡아주다가, **완료에서 1~6이 동시에 살아있는지** 검사 → 뒤 기능 넣다가
앞걸 깬 사람은 여기서 처음 걸린다. (예: 순진한 "버튼 누적식" 계산기로 시작했다가 3단계 괄호에서 우선순위
때문에 전면 재작성 → 이 과정에서 앞 기능 회귀 위험. 표현식 평가/파서로 간 사람은 자연히 다 통과.)

## 5. 채점 (`testCommand` + 히든 + `rubric`) — 겹치지 않게 분리

`testCommand`: `npm test` (히든 테스트가 워크스페이스의 `calc.js`에서 `evaluate`를 import).

### 결정론(node --test, `calc.js`의 `evaluate`) — 산술 전부 여기서
`evaluate(expr)`는 **화면에 표시할 문자열**을 반환한다(그래서 부동소수점 "정리"까지 결정론 검사 가능):

- [ ] 사칙: `evaluate("2+3")==="5"`, `"6-2"→"4"`, `"4*3"→"12"`, `"8/2"→"4"`
- [ ] 괄호/우선순위: `"(2+3)*4"→"20"`, `"2+3*4"→"14"`
- [ ] ÷0·무효식 → 정확히 `"Error"` (`"5/0"`, `"sqrt(-1)"`, `"log(0)"`, `"log(-5)"` 등)
- [ ] 부동소수점 정리: `"0.1+0.2"→"0.3"`, `"4/2"→"2"`(불필요한 `.0` 없음)
- [ ] 나머지: `"7%3"→"1"`, `"10%4"→"2"` (양수만 테스트 — 음수 모호성 회피)
- [ ] 루트: `"sqrt(9)"→"3"`, `"sqrt(16)"→"4"`
- [ ] 상용로그: `"log(100)"→"2"`, `"log(1)"→"0"`

### `rubric` (LLM 채점) — 테스트가 못 재는 것만
```
- 버튼 클릭(마우스)과 키보드 입력이 둘 다 동작하도록 구성됐는가
- 계산 로직과 화면(index.html)이 뒤섞이지 않고 분리돼 있는가(evaluate로 로직 오프로딩)
- 코드 가독성
```
> ⚠️ **산술 정확성은 rubric에 넣지 않는다** — node-test가 이미 결정론적으로 재므로 겹치면 신호는 안 늘고
> 오판만 는다(`docs/evaluation.md`의 실측 교훈). 마우스/키보드는 DOM 상호작용이라 node-test로 재기
> 번거로워 rubric으로만 본다(jsdom 의존성 추가 안 함).

## 6. 결정론을 위해 확정(pin)할 규칙

확인 질문은 캐주얼하지만, **히든 테스트가 의존하는 값·규약은 질문 안에 살짝 못박아** 모호성을 없앤다
("측정 축이 아닌 곳에서 결과가 흔들리면 문제가 목적을 잃는다" 원칙):

- 무효/에러(÷0, 음수 sqrt, log(≤0), 파싱 불가) → **정확히 문자열 `"Error"`**
- 로그 = **상용로그 log10** (질문에 명시), 루트 = 제곱근
- 나머지 = 양수 기준(`a%b`), sqrt/log 인자 표기는 `sqrt(x)`/`log(x)`
- 표시 규칙: 불필요한 소수점 이하 0 제거 + 부동소수점 오차 제거(예 `0.1+0.2`→`"0.3"`)

수식 표기(버튼으로 만들든 입력창으로 만들든)는 자유. `evaluate`가 **최종 표시 문자열**만 규약대로 내면 됨.

## 7. 한도 (`maxCostUsd` / `maxDurationMs` / `targetDurationMs`)

**워밍업이라 넉넉하게** — 모두 통과해야 기준선 역할을 한다. 예산을 조여 실격을 유도하지 않는다.

| 필드 | 초기값 | 근거 |
|---|---|---|
| `maxCostUsd` | 1.0 (= 1,000,000 가중토큰) | 쉬운 과제라 여유. 실측 후 조정 |
| `maxDurationMs` | 900000 (15분) | 하드컷은 여유롭게 |
| `targetDurationMs` | 300000 (5분) | 적정 시간 — 넘으면 진행막대 주황 경고(감점은 `docs/evaluation.md` 규칙) |

## 8. 스캐폴딩 후 검증 체크리스트

1. **게이트 무력화 확인**: 각 단계 "제출"이 워크스페이스 상태와 무관하게 다음 단계를 여는가(빈
   워크스페이스로도 6단계까지 진행되는가). 이게 이 문제의 정체성.
2. **정답 검증**: 표준 구현(표현식 평가 + 규약대로 표시)이 **완료 시 히든 전부 통과**.
3. **회귀 검출 검증**: 일부러 6단계 기능을 넣으며 3단계(괄호)를 깬 구현이 **완료에서 정확히 그 항목만
   실패**하는가(안전망 없는 스펙 누적이 실제로 잡히는지).
4. **엣지 검증**: ÷0/음수 sqrt/log(≤0)가 `"Error"`, `0.1+0.2`가 `"0.3"`으로 정확히.
5. **시작 상태**: 워크스페이스 열자마자 Hello World 페이지가 실제로 뜨는가(서버 자동 기동 + 안내).
6. **말끔함**: `prompt`/`promptAddition`/스타터에 히든 기대값(구체 케이스 값)이 새지 않았는가. 구조
   힌트(evaluate 시그니처)만 스텁에 있고 함정값은 채팅에만.

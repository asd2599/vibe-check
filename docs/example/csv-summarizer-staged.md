# 문제 설계 브리프 — 매출 CSV 합산기 (단계적/커브볼 형식)

> 이 문서는 **완성 문제가 아니라 "문제 저자 브리프"** 다. Claude Code가 읽고
> `problems/csv-summarizer-staged.json` + `problems/starters/csv-summarizer-staged/`(참고 문서 + 샘플 데이터,
> **코드는 없음**)를 스캐폴딩할 수 있게 필요한 걸 다 담았다. 포맷은 `docs/problem-set.md`를 따른다.
>
> 실행 방식은 **방식 B**: 단계를 프롬프트에 순서대로 전부 노출한다(점진적 공개 아님). 파일 하나로 끝나므로
> 러너·대시보드를 손댈 필요가 없다. 단계를 미리 봐도 변별은 그대로 작동한다 — **1단계를 대충 짜면 3·4단계에서
> 손해**보기 때문.

## 0. 이 문제가 노리는 변별 축

**"빈 프로젝트 → 단계적으로 요구가 쌓임"** 형식. 정답 스펙은 하나지만, **어떻게 쌓았느냐**가 비용을 가른다.

- **초기 설계 품질 → 후반 비용 (단계 간 결합).** 뒤 단계가 앞 단계 결정을 소급해서 무효화한다.
  - 대충 `line.split(',')`으로 시작 → 3단계(따옴표 안 구분자)에서 **전면 재작성**
  - 파서를 한 겹 추상화해서 시작 → 3단계는 **한 군데만 수정**
- **컨텍스트 위생 (세션이 길수록 증폭).** 단계가 4개라 세션이 길다. 매 단계 "지금 코드 다시 보여줘"로
  전부 재탐색하는 naive는 토큰이 누적 폭증, 국소적으로 다루는 기술은 절약.
- **문서 함정 (correctness 보조).** `SPEC.md`에 비관습적 값(합산 컬럼을 **헤더 이름**으로 찾기, 출력 필드명,
  더러운 값 판정 규칙)을 심어서, 안 읽고 관습대로 하면 히든 테스트에서 떨어지게 한다.

### 커브볼 지점 (핵심 재료)

| 단계 | 순진한 지름길 | 뒤에서 소급 무효화하는 요구 |
|---|---|---|
| 1 | `split(',')` + `parseFloat` | — |
| 2 | 구분자만 파라미터로 | (아직 버팀) |
| **3** | — | **따옴표로 감싼 칸 안에 구분자가 들어있음** → `split()` 완전히 깨짐 |
| **4** | `parseFloat(x)` 그대로 | **더러운 금액값 판정 + 건너뛴 개수 보고** → `parseFloat`는 조용히 틀린 값 반환 |

## 1. 시나리오 프롬프트 (`prompt` 필드) — 방식 B, 단계 전부 노출

실무 슬랙 톤. 단계가 순서대로 들어오는 대화처럼 쓴다.

```
[슬랙 DM - 정팀장]
안녕하세요! 매출 정산 자동화가 필요해서요, 단계별로 부탁드릴게요 🙏

① 일단 매출 CSV 파일 하나 읽어서 금액 컬럼 합계 내주세요. 샘플은 워크스페이스에 넣어뒀어요.
② 부서마다 포맷이 달라요 — 어떤 데는 TSV(탭), 어떤 데는 파이프(|)로 줘요. 그것도 되게 해주세요.
③ 아 그리고 금액이나 메모에 쉼표가 들어가서 따옴표(")로 감싼 칸이 종종 있더라고요. 그거 때문에
   숫자가 깨지면 안 돼요.
④ 마지막으로, 금액 칸이 비었거나 이상한 값(예: N/A, ₩1,200 같은 거)인 행이 섞여 있어요. 그런 행은
   합산에서 빼고, 대신 몇 개나 건너뛰었는지 같이 알려주세요.

정확한 출력 형식이랑 "어떤 컬럼을 합산하는지" 규칙은 SPEC.md에 정리해뒀으니 꼭 그대로 맞춰주세요!
파일마다 컬럼 순서가 달라서 그 부분 특히 주의 부탁드려요 🙏
실행은 node summarize.js <파일경로> 형태면 됩니다. 오늘 중으로만 되면 감사해요!
```

## 2. 스타터 워크스페이스 (`starterFiles`) — 코드 없음, 문서 + 샘플 데이터만

`problems/starters/csv-summarizer-staged/`:

```
csv-summarizer-staged/
├── SPEC.md                    # ★ 반드시 읽어야 하는 함정 문서 (3장)
└── data/
    ├── sales_basic.csv        # 1단계용: 헤더 있는 기본 CSV, amount 컬럼
    ├── sales_dept_a.tsv       # 2단계용: 탭 구분, 컬럼 순서가 basic과 다름
    ├── sales_dept_b.psv       # 2단계용: 파이프(|) 구분
    ├── sales_quoted.csv       # 3단계용: 따옴표 안에 쉼표/구분자가 들어간 칸 포함
    └── sales_dirty.csv        # 4단계용: 빈칸, 'N/A', '₩1,200', '1,200'(유효), 음수 등 섞임
```

### 샘플 데이터가 반드시 포함해야 할 트릭 (스캐폴딩 시 반영)

- **컬럼 순서 변주**: `sales_basic.csv`는 `date,amount,memo` 순, `sales_dept_a.tsv`는 `memo,region,amount` 순
  → **인덱스로 amount를 찾으면 틀린다.** 헤더 이름으로 찾아야만 맞음.
- **따옴표 안 구분자**: `sales_quoted.csv`에 `2024-01-03,"1,250","점심, 회식비"` 같은 행 →
  `split(',')`으로 세면 컬럼이 밀려서 amount가 깨진다. RFC 4180식(따옴표 감싸기, `""`로 이스케이프,
  따옴표 안 개행 가능) 파싱이 필요.
- **더러운 값**: `sales_dirty.csv`에 아래를 섞는다 (SPEC의 판정 규칙과 정확히 연결):
  - `` (빈칸) → skip
  - `N/A`, `-`, `TBD` → skip
  - `₩1,200`, `$50` (통화기호 포함) → skip
  - `1,200` (순수 천단위 쉼표) → **유효, 1200으로 처리** (parseFloat는 1로 잘못 읽음)
  - `-500` (음수 환불) → **유효** (SPEC상 포함)
  - `1234.567` → 유효 (반올림 규칙 적용 대상)

## 3. `SPEC.md` — 함정 문서 (비관습적 값)

```markdown
# 매출 합산 규칙

## 합산 대상 컬럼
- 합산할 컬럼은 **헤더 이름이 `amount`** 인 컬럼이다. 컬럼 위치(인덱스)로 찾지 말 것 —
  파일마다 컬럼 순서가 다르다. 헤더가 없거나 `amount` 컬럼이 없는 파일은 처리 대상이 아니다.

## 구분자
- 확장자로 판단한다: `.csv` = 콤마, `.tsv` = 탭(\t), `.psv` = 파이프(|).

## 따옴표 규칙 (RFC 4180 준용)
- 칸은 큰따옴표(")로 감쌀 수 있고, 그 안에는 구분자와 개행이 포함될 수 있다.
- 감싼 칸 안의 큰따옴표는 `""`(두 개)로 이스케이프한다.

## 유효 금액 판정
- 유효한 금액 = 선택적 부호(-) + 숫자 + 선택적 소수점. **천단위 쉼표(예: 1,200)는 제거 후 유효로 처리**한다.
- 음수(-500 등, 환불)는 **합산에 포함**한다.
- 그 외(빈칸, 문자 포함, 통화기호 포함: N/A, ₩1,200, $50 등)는 **건너뛴다(skip)**.

## 출력 형식 (표준출력에 JSON 한 줄)
- 필드명을 반드시 아래 그대로 쓴다 (sum/rows 아님):
  { "total": <합계>, "counted": <합산에 포함된 행 수>, "skipped": <건너뛴 행 수> }
- `total`은 **소수점 2자리에서 반올림**(반올림 방식: 0.005는 올림)한 숫자.
- 헤더 행은 counted/skipped 어디에도 세지 않는다.
```

> ⚠️ 함정 요약: (1) 컬럼을 **헤더명**으로 찾기(인덱스 하드코딩 탈락), (2) 필드명 `total/counted/skipped`
> (관습적 sum/count 아님), (3) `1,200`은 유효인데 `₩1,200`은 skip (`parseFloat` 그대로 쓰면 둘 다 틀림).

### 문서에도 없어 "맥락 판단"해야 하는 요소 (스펙-대신-써줘 우회 차단)

- ④단계에서 "이상한 값은 빼라"고 했지만 **음수(-500)를 이상한 값으로 볼지 유효 환불로 볼지**는 슬랙에도
  애매하게만 있고 SPEC에만 "포함"으로 명시 → SPEC을 실제로 안 읽으면 판단이 갈린다.
- (선택) `amount` 컬럼 자체가 없는 파일이 인자로 들어왔을 때의 처리(에러? 빈 결과?)는 SPEC에 "처리 대상
  아님"으로만 적고 정확한 출력은 안 정함 → 스스로 합리적으로 결정해야 함.

## 4. 채점 (`testCommand` + 누적 히든 테스트)

`testCommand`: `npm test`. 히든 테스트는 응시자에게 공개하지 않는다(평가 시점에 워크스페이스로 복사).
**최종 상태 하나에 대해 1~4단계 요구를 전부 한 번에 검증**한다(단계별로 나눠 채점하지 않는다).

히든 테스트 항목:

- [ ] `sales_basic.csv` → 올바른 total/counted/skipped (기본 합산)
- [ ] `sales_dept_a.tsv`(탭) / `sales_dept_b.psv`(파이프) → 구분자 처리 + **컬럼 순서 달라도** amount 정확
- [ ] `sales_quoted.csv` → 따옴표 안 쉼표/구분자가 있어도 amount 안 깨짐 (RFC 4180)
- [ ] `sales_dirty.csv` → `1,200`은 유효(1200), `₩1,200`/`N/A`/빈칸은 skip, `-500`은 포함,
      `skipped` 개수 정확
- [ ] 반올림: `1234.567` 포함 시 total이 소수 2자리 반올림으로 나옴
- [ ] 출력 필드명이 정확히 `total`/`counted`/`skipped` (sum/count/rows면 실패)
- [ ] 헤더 행이 counted/skipped에 안 세짐

> 이 테스트들은 **누적적**이라, 3단계 파서를 제대로 안 만든 사람은 앞 단계는 통과해도 quoted/dirty에서
> 떨어진다 — 커브볼이 채점에 그대로 반영된다.

### `rubric` (LLM 채점)

```
- SPEC.md의 비관습적 규칙(헤더명으로 컬럼 찾기, 출력 필드명 total/counted/skipped)을 정확히 반영했는가
- 따옴표(RFC 4180) 처리를 별도 split이 아니라 제대로 된 파싱으로 구현했는가
- 더러운 값 판정(1,200 유효 vs ₩1,200 skip, 음수 포함)을 정확히 구현했는가
- 단계가 쌓이며 코드가 재작성 없이 확장 가능한 구조인가(파싱/판정/합산 관심사 분리)
- 코드 가독성
```

## 5. 한도 (`maxTokens` / `maxDurationMs`)

빈 프로젝트에서 코드를 처음부터 쌓는다. `docs/problem-set.md`의 "턴당 1만~1.5만 토큰" 기준.

- 예상 왕복: SPEC 읽기(1) + 샘플 데이터 훑기(1~2) + 파서/합산 작성(3~5) + 구분자 확장(1~2) +
  따옴표 대응(2~4) + 더러운 값 대응(2~3) + 테스트 돌려 고치기(3~5) ≈ **15~22턴**.
- 기술 접근(구조 잡고 국소 수정) 기준 대략 **20만~28만 토큰**. naive(단계마다 전체 재탐색 + 3단계 재작성)는
  **35만+** 로 튈 수 있음.

권장 초기값 (실측 후 조정):

| 필드 | 값 | 근거 |
|---|---|---|
| `id` | `csv-summarizer-staged` | |
| `difficulty` | `medium` | |
| `category` | `cli-tool` | |
| `testCommand` | `npm test` | |
| `maxTokens` | **300000** | 기술 접근은 통과, 3단계 재작성까지 하는 naive는 실격 위험 → 효율이 통과/실격을 가름 |
| `maxDurationMs` | **2400000** (40분) | 빈 프로젝트 4단계 + 사람 판단/타이핑 포함, medium 기준 넉넉히 |

> 랭킹형으로 하고 싶으면 maxTokens를 400k로 올려 둘 다 통과시키고 토큰 수로 줄세운다.
> 게이팅형으로 하려면 스캐폴딩 후 naive가 실제로 300k를 넘겨 실격되는지 실측하고 조정.

## 6. 스캐폴딩 후 필수 검증 (통과 못 하면 폐기)

1. **정답 검증**: 구조 잡은 정석 구현으로 히든 테스트 전부 통과.
2. **naive 실패 검증**: `split(',')` + `parseFloat`로 대충 시작 → quoted/dirty 테스트에서 떨어짐.
3. **스펙-대신-써줘 우회 검증**: SPEC 안 보여주고 "알아서 해줘" → 필드명/음수 포함/`1,200` 판정에서 떨어짐.
4. **토큰 스프레드 검증**: naive(단계마다 재탐색+3단계 재작성) vs 기술(구조+국소수정) 토큰 실측,
   **2배 이상** 벌어지는지 확인. 특히 **3단계 재작성 비용**이 스프레드의 핵심 — 안 벌어지면 quoted 데이터의
   트릭을 더 강하게(따옴표 안 개행 등) 만든다.

네 개 다 통과하면 "정답은 하나지만 어떻게 쌓았느냐가 점수를 가르는" 단계적 문제의 표준 템플릿이 된다.

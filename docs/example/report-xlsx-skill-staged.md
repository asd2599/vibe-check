# 문제 설계 브리프 — 매출 엑셀 리포트 생성 (공식 스킬 라이브러리 "자발적 발견" 측정)

> 이 문서는 **완성 문제가 아니라 "문제 저자 브리프"** 다. Claude Code(또는 `problem-author` 서브에이전트)가
> 읽고 `problems/report-xlsx-skill-staged.json` + `problems/starters/report-xlsx-skill-staged/`(샘플
> 데이터만, **스킬도 스킬에 대한 언급도 전혀 없음**)를 스캐폴딩할 수 있게 필요한 걸 다 담았다.
>
> ⚠️ **이 브리프 자체도 참가자에게 노출되면 안 된다.** `prompt`/`starterFiles`/`stages`의 `promptAddition`
> 어디에도 스킬, 라이브러리, GitHub, `npx`, "공식", "설치" 같은 단어가 들어가면 안 된다 — 아래 4번 참고.

---

## 0. 방향 전환 — 이전 초안(두 변형 JSON)을 폐기하고 단일 문제로 바꾼 이유

**이전 초안**은 `report-xlsx-with-skill-staged.json` / `report-xlsx-no-skill-staged.json` 두 개를 만들어서
스킬을 **문제 저자가 starterFiles에 미리 얹어주는 방식**이었다. 사용자가 원하는 그림은 다르다:

> 참가자가 **스스로** 공식 스킬 라이브러리(`https://github.com/anthropics/skills`)를 찾아서
> `npx skills add https://github.com/anthropics/skills --skill xlsx --agent claude-code` 같은 명령으로
> **직접 설치해서 활용했을 때** 더 좋은 성과(퀄리티/토큰)가 나오는가를 측정하고 싶다. 우리가 스킬을
> 제공하거나 그 라이브러리의 존재를 힌트로 주는 일은 절대 없다.

즉 측정 변수가 "우리가 스킬을 줬는가"가 아니라 **"참가자가 자기 지식/판단으로 외부 공식 스킬 생태계를
찾아 쓸 줄 아는가"**로 바뀐다. 이건 `CLAUDE.md`의 핵심 원칙 — "참가자가 워크스페이스 안에서 직접 구성한
하네스는 측정 대상 그 자체" — 에 이전 초안보다 오히려 더 정확히 들어맞는다. 이전 초안처럼 우리가 스킬을
starterFiles에 심어주면, 그건 참가자의 하네스 엔지니어링 능력이 아니라 "옆에 이미 놓인 걸 집어 썼는가"만
재는 것이었다.

**그래서 이번엔 문제 파일이 하나다.** 두 조건(A/B)을 우리가 config로 강제하지 않는다 — 대신 **여러
참가자가 이 문제를 풀면서 자연스럽게 갈리는 행동**(스스로 `npx skills add`류를 찾아 설치했는지, 처음부터
직접 라이브러리 API를 짜 내려갔는지)을 나중에 run 기록(트랜스크립트 + 워크스페이스 diff)에서 비교
분석한다. 이건 러너/스키마를 안 건드리는 순수 관찰(observational) 설계라 `CLAUDE.md`의 "새 문제는 파일
하나로 끝나야 한다" 원칙과도 맞는다.

## 1. 이 문제가 노리는 변별 축

포맷은 이전 결정대로 **XLSX 유지**(결과 파일을 다시 열어 셀 값/서식/수식/병합/틀고정을 스크립트로
결정론적으로 검사할 수 있어서, PPTX/PDF보다 히든 테스트 채점에 유리).

트랩의 성격도 이전과 동일 — **문서를 읽었는가가 아니라 라이브러리(exceljs/openpyxl류)를 정확히 다뤘는가**:

- 통화 값을 문자열로 포맷팅해서 셀에 박기 vs 숫자값 + `number_format` 지정
- 시트 간 합계를 하드코딩된 숫자로 쓰기 vs 살아있는 수식(`formula`) + 캐시값
- 병합 범위의 마스터 셀이 아닌 칸에 값 쓰기(무시/에러) vs 마스터 셀에만 쓰기
- freeze pane API를 좌표/인덱스 규칙 착각해서 잘못 호출하기 vs 정확히 호출

이 함정들은 실제로 각 라이브러리 문서를 안 읽고 "그럴듯하게" 짜면 걸리기 쉬운, 실무에서도 자주 나오는
비직관적 지점들이다 — **바로 이 지점들이 공식 스킬(예: 위 GitHub 저장소의 `xlsx` 스킬)이 존재하는
이유이기도 하다.** 그래서 가설은: 이 함정들과 실제로 맞닥뜨렸을 때, "이건 이미 누가 잘 정리해놨을 법한
문제다"라고 판단하고 공식 스킬 생태계를 찾아보는 참가자는 시행착오 없이 한 번에 맞히고, 그렇지 않은
참가자는 실행→에러/오답→수정을 반복한다(=턴/토큰 증가, 히든 테스트 탈락 위험 증가).

**참고 (`access-audit-staged` 실측, `docs/problem-set.md`)**: 판단 규칙을 기억해두는 용도의 스킬은
토큰을 안 아꼈다(스킬 조회 자체가 턴을 늘림). 이번 스킬은 성격이 다르다 — **라이브러리 API 오용으로 인한
시행착오 루프를 원천적으로 없애는 용도**라서 방향이 반대(토큰도 아낄 가능성)일 수 있다. 다만 이것도
가설일 뿐이니 7번 "필수 검증"에서 먼저 확인한다.

## 2. 시나리오 프롬프트 (`prompt` 필드) — 스킬 언급 절대 금지

평범한 업무 요청 톤 그대로, **"라이브러리", "스킬", "공식", "설치", "패키지", "GitHub" 같은 단어를 일절
쓰지 않는다.** 이전 초안과 문구 자체는 거의 동일하게 가되, 검수 시 이 단어들이 안 섞였는지 반드시
확인한다.

```
[슬랙 DM - 김대리]
안녕하세요! 이번 달 매출 정리해서 엑셀 리포트 하나 만들어주실 수 있을까요?
데이터는 워크스페이스에 sales.csv로 넣어놨어요 (날짜, 카테고리, 상품명, 수량, 단가).

바라는 형태는:
- "상세" 시트에 원본 데이터 쭉 나열
- "요약" 시트에 카테고리별 합계 (상세 시트 값이 바뀌면 요약도 같이 바뀌게, 하드코딩 숫자 말고 수식으로요!)
- 금액 칸은 통화로 보기 좋게, 헤더는 한눈에 띄게 병합해서 제목처럼
- 스크롤해도 헤더 행은 고정되게

output/report.xlsx 로 만들어주시면 됩니다. 감사해요!
```

이 요청 자체는 비개발자가 실제로 할 법한 자연스러운 부탁이고, "수식으로요", "병합해서", "헤더 고정" 같은
표현이 구현 난이도(라이브러리 함정)로 이어지는 게 전부다. **참가자가 이 요구를 보고 "아 이거 Claude
공식 스킬 중에 xlsx 있지 않았나?"를 스스로 떠올리는지가 측정 대상**이다.

## 3. 스타터 워크스페이스 (`starterFiles`) — 데이터만, 그 외엔 아무것도 없음

```
report-xlsx-skill-staged/
└── data/
    └── sales.csv
```

- `.claude/` 디렉터리 자체를 아예 안 둔다(스킬 폴더는 물론, CLAUDE.md도 안 둔다 — CLAUDE.md에 "필요하면
  스킬을 찾아보라"는 식의 메타 힌트조차 금지).
- `sales.csv`: 3개월치, 5개 카테고리, 약 120행. 카테고리별 합계가 뚜렷이 다르게 나오도록 금액 구성(합계
  검증용).
- README나 주석 등 어떤 부가 파일에도 스킬/라이브러리 관련 텍스트를 넣지 않는다.

## 4. 단계 설계 (`stages`) — 라이브러리 함정을 순서대로 쌓기 (이전 초안과 동일)

방식 B(단계 전부 프롬프트에 노출) — 이 문제는 정보 은폐가 아니라 라이브러리 정확성이 변별축이라 점진적
공개 게이트가 꼭 필요하진 않지만, 단계별 게이트를 두면 "어느 요구에서 얼마나 헤맸는지"가 run 기록에
남아 분석하기 좋다.

| 단계 | 요구 | 라이브러리 함정 |
|---|---|---|
| 1 | `sales.csv` 읽어서 "상세" 시트에 원본 나열 | (워밍업, 거의 안 갈림) |
| 2 | "요약" 시트에 카테고리별 합계를 **살아있는 수식**으로 | 값 하드코딩 vs 실제 수식 셀(+캐시값) |
| 3 | 금액 칸 통화 서식, 상품명 긴 칸도 안 잘리게 | 문자열 포맷팅 vs 숫자값+`number_format` |
| 4 | 제목 행 병합(A1:E1) + 헤더 행 고정(freeze pane) | 병합 마스터 셀 규칙, freeze pane API 좌표 규칙 |

게이트 테스트는 누적으로 짜서(`docs/problem-set.md` 원칙) 뒤 단계 작업이 앞 단계를 깨면 바로 잡는다.
`hiddenTestsPath`도 지정해 조기 "완료" 우회를 막는다.

## 5. 채점 (`testCommand` + 히든 테스트) — 이전과 동일

`testCommand`: `npm test` (히든 테스트가 `output/report.xlsx`를 exceljs로 다시 열어 검사).

- [ ] "상세" 시트에 `sales.csv` 전체 행 정확히 반영
- [ ] "요약" 시트 합계 셀이 **`cell.formula` 존재**(하드코딩 아님) + 캐시값이 실제 합계와 일치
- [ ] 금액 칸 `cell.value`가 **숫자 타입** + `cell.numFmt`가 통화/천단위 서식
- [ ] 제목 행이 지정 범위로 **병합**되어 있고 마스터 셀에 값이 정확히 있음
- [ ] 워크시트 `views`에 **freeze pane**(1행 고정) 설정 존재

### `rubric` (LLM 채점)

```
- 수식 vs 하드코딩 값 구분을 정확히 지켰는가
- 통화 서식을 숫자+서식으로 처리했는가
- 코드 가독성/재사용성
```

> "스킬을 활용했는가"를 rubric 항목으로 넣지 않는다 — 그걸 채점 기준으로 노출하는 순간 참가자에게
> 간접 힌트가 된다(rubric은 대시보드에 안 보이더라도, 이 문서가 참가자에게 새는 경로를 원천 차단하는
> 게 원칙). 스킬 활용 여부는 **채점과 무관하게, 사후에 트랜스크립트/워크스페이스 diff로만** 관찰한다.

## 6. 측정 방법론 — config가 아니라 사후 관찰

이 문제는 A/B용 별도 필드가 없다. 여러 참가자가 이 문제를 풀고 나면:

1. 각 run의 워크스페이스 diff에서 `.claude/skills/` 또는 `node_modules/`, `package.json`에 스킬 설치
   흔적(예: `skills` CLI가 만든 디렉터리)이 있는지 확인.
2. 트랜스크립트에서 `npx skills` / `github.com/anthropics/skills` 관련 Bash 호출이 있었는지 확인.
3. 위 두 신호로 run을 "스킬 활용" / "직접 구현" 두 그룹으로 사후 분류하고, 토큰(가중토큰)/턴수/히든
   테스트 통과율/LLM rubric 점수를 비교한다.

**지금은 자동화하지 않는다** — run 수가 아직 적어서 수동으로 몇 건 비교해보는 걸로 충분하고, 표본이
쌓이면 그때 대시보드에 "스킬 활용 여부" 태그를 자동 판별해서 보여주는 기능을 별도로 고려한다(지금
문제 스캐폴딩 범위에는 포함 안 함 — 러너/스키마 변경은 이 문제와 분리된 별도 작업).

## 7. 한도 (`maxCostUsd` / `maxDurationMs`)

**직접 구현(라이브러리 시행착오 포함) 경로도 통과 가능할 만큼 넉넉하게 잡는다** — 이 문제의 목적은
"스킬 안 쓰면 무조건 실격시키기"가 아니라 "스킬을 쓴 쪽이 실제로 더 낫다는 걸 자연스러운 결과 차이로
보여주기"다. 한도를 타이트하게 잡으면 직접 구현 참가자가 전부 실격돼서 애초에 비교할 데이터 자체가
안 모인다.

| 필드 | 초기값 | 근거 |
|---|---|---|
| `maxCostUsd` | **2.5** (= 2,500,000 가중토큰) | 다른 4단계 staged 문제(2.0)보다 살짝 여유를 더 줌 — 스킬 설치(네트워크 호출 포함) 자체도 몇 턴을 쓰고, 직접 구현 시 라이브러리 시행착오까지 흡수해야 두 경로 다 완주 가능해야 비교가 됨. 실측 후 조정 |
| `maxDurationMs` | **2400000** (40분) | 4단계 + 시행착오/스킬 탐색 여유, medium 기준 |

## 8. 스캐폴딩 후 필수 검증 (통과 못 하면 폐기 또는 재설계)

1. **정답 검증**: 정석 구현(직접 짜되 함정 4개 다 정확히 처리)이 히든 테스트 전부 통과.
2. **naive 실패 검증**: 통화 문자열 박기/합계 하드코딩 구현이 3·2단계에서 각각 떨어짐.
3. **⚠️ 최우선 — 스킬 설치 자체가 실제로 되는지 인프라 검증.** `docs/manual-mode.md`의 격리 방식(run마다
   `USERPROFILE`/`HOME`을 빈 "가짜 홈"으로 오버라이드)이 `npx skills add https://github.com/anthropics/skills
   --skill xlsx --agent claude-code` 같은 명령의 네트워크 접근/npm 캐시 생성/파일 쓰기를 막지는 않는지
   스캐폴딩 직후 헤드리스로 **직접 실행해서 확인**한다. 이게 막히면(네트워크 차단, npx 미설치, 캐시
   경로 권한 문제 등) 이 문제 전체의 전제가 성립하지 않으므로 다른 검증보다 먼저 확인해야 한다.
4. **가설 검증(헤드리스 A/B, QA 목적 한정)**: 실제 참가자에게 보여줄 `prompt`는 절대 안 건드리고,
   **QA 전용 프롬프트**를 따로 만들어 두 조건으로 헤드리스 실행:
   - (a) 정상 `prompt` 그대로 — 힌트 없이 알아서 하게 둠 (자연 상태 시뮬레이션)
   - (b) `prompt` + "만약 이 작업에 맞는 공식 skills 라이브러리가 있다면 찾아서 써봐" 같은 QA용 지시를
     덧붙인 버전 (스킬을 쓰는 참가자를 시뮬레이션)
   두 결과의 토큰/턴수/히든 테스트 통과율을 비교해서 실제로 차이가 나는지 확인한다. **여기서 차이가
   안 보이면 사람에게 넘기지 말고** 함정 강도를 더 높이거나(예: 병합+수식+서식을 한 셀에서 동시에
   요구), 라이브러리를 더 실수하기 쉬운 것으로 바꾸는 식으로 재조정한다.
5. **말끔함 검증**: `prompt`/`starterFiles`/`stages`의 모든 텍스트를 다시 훑어서 "스킬", "라이브러리",
   "공식", "GitHub", "설치", "npx" 등의 단어가 단 하나도 없는지 확인한다(사람 리뷰 필수 — 자동 검사로도
   보조 가능: 간단한 grep으로 이 키워드들이 `problems/report-xlsx-skill-staged.json`과
   `problems/starters/report-xlsx-skill-staged/`에 없는지 확인).

다섯 개 다 통과해야 "참가자의 자발적 하네스 탐색 능력을 실제로 재는 문제"로서 유효하다. 특히 3번(인프라
검증)을 건너뛰면, 애초에 참가자가 그 경로를 시도해도 성공할 수 없는 문제를 내놓고 "스킬을 안 써서
못했다"고 잘못 해석하게 된다.

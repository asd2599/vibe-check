# 문제 설계 브리프 — 인수인계 릴레이 (컨텍스트 관리 = 토큰 절약 측정)

> 이 문서는 **완성 문제가 아니라 "문제 저자 브리프"** 다. Claude Code(또는 `new-problem` 스킬 /
> `problem-author` 서브에이전트)가 읽고
> `problems/handover-relay-staged.json` + `problems/starters/handover-relay-staged/`(+ 히든 테스트,
> + 검증용 A/B 스크립트)를 스캐폴딩할 수 있게 필요한 걸 다 담았다.
>
> ⚠️ **이 브리프 자체도, `docs/guides/`의 공략집도 참가자에게 노출되면 안 된다.** 특히 이 문제는
> 측정 대상이 "컨텍스트 관리(세션 분리)"라서, `prompt`/`promptAddition` 어디에도 "컨텍스트", "토큰",
> "`/clear`", "세션 나눠", "압축" 같은 단어가 들어가면 안 된다 — 그 단어가 보이는 순간 참가자가
> 정답 기술을 직접 지시받는 게 되어 측정이 무의미해진다(8번 말끔함 검증 참고).

---

## 0. 이 문제가 노리는 것 + 왜 `inventory-digest-staged`로는 안 됐나

**측정하려는 명제**: *서로 무관한 업무를 한 세션에 계속 이고 가면, 앞 업무의 큰 컨텍스트가 매 턴
캐시 재독으로 나가서 토큰을 더 쓴다. 업무 사이에 컨텍스트를 정리(`/clear`)하거나 애초에 큰 원본을
대화창에 안 올리는 사람은 토큰을 덜 쓴다.* — 이 **기술 격차가 토큰 축에서 드러나는가**를 잰다.

**`inventory-digest-staged`(7단계 3직무 릴레이)가 이걸 못 보여준 이유**(실사용 실측, `docs/guides/`):
데이터를 **표(CSV/JSON)로 줬더니** 참가자(Haiku 단일 세션 포함)가 전부 `node report.js data/파일`
스크립트를 짜서 **파일을 디스크에서 읽었다.** 원본 바이트가 애초에 대화창에 안 올라오니, "정리 안 하고
이고 가면 비싸다"는 죽은 무게가 **생기지를 않았다.** 예산(하드컷 $0.7)도 "Haiku 단일 세션 완주값"에
맞춰 잡혀 있어서, 단일 세션이 통과하는 게 정의상 당연했다.

**설계의 근본 딜레마**(지금까지 계속 부딪힌 지점):

| | 결정론적 채점(운 배제) | 데이터가 대화창에 상주 |
|---|---|---|
| 표 데이터 + 집계 | ✅ | ❌ 스크립트로 접혀서 상주 안 함 |
| 판단/분류 작업 | ❌ "분류 운"으로 목적 상실 (2단계 재설계 교훈) | ✅ |

→ 이 둘을 **동시에** 만족시키는 게 이 문제의 핵심 트릭이다(1번).

## 1. 핵심 트릭 — "큰 산문 파일에서 결정론적 사실 조회"

데이터를 **표가 아니라 산문(prose) 덩어리**로 주고, 정답을 그 안에 **정확히 박힌 확정값**으로 둔다.

- **naive 경로**: 큰 문서를 통째로 컨텍스트에 올려(`cat` / Read 전체) 답을 찾는다 → **정답은 맞지만**
  그 40~60K 토큰이 이후 내내 상주 → 비쌈.
- **숙련 경로**: 필요한 부분만 range-read / grep 하고, 무관 업무로 넘어갈 때 `/clear` → **똑같이
  정답** → 쌈.

**둘 다 정답이라 품질(테스트 통과·rubric)은 동일하고, 토큰만 기술로 갈린다.** 채점에 운이 안 들어가고
측정축에서만 스프레드가 생긴다. **산문은 "통째로 읽는 게 자연스러운" naive 경로**라서, 표와 달리
전원이 스크립트로 접지 않는다 — 여기서 격차가 산다.

두 레버가 다 작동한다:
1. `handover.md`를 **통째로 vs 필요한 부분만** 읽었는가 (targeted reading / 오프로딩)
2. 인프라 업무가 끝나고 무관한 결제/데이터 업무로 갈 때 **`/clear`로 문서를 버렸는가** (세션 분리 —
   사용자가 원래 재고 싶었던 바로 그 기술)

> ⚠️ **override 체인으로 "전체 읽기"를 유도**: 조회 단계의 정답을 "문서 곳곳에 흩어져 있고, 뒤 절이
> 앞 절을 덮어쓰는" 구조로 두면, 최종 유효값을 내려면 순서대로 훑어야 해서 wholesale-read가 더
> 자연스러워진다. 단 **모호함은 0**이어야 한다 — "같은 키가 또 나오면 뒤가 이긴다"를 문서가 명시해서,
> 정답은 여전히 기계적으로 확정되게 한다(판단·운 개입 금지).

## 2. 시나리오 프롬프트 (`prompt` 필드) — 정답 기술 언급 절대 금지

퇴사자 인수인계라는 평범한 업무 톤. **"컨텍스트/토큰/세션/정리/`/clear`" 같은 단어 일절 금지.**

```
[슬랙 DM - 박팀장]
안녕하세요! 지난주 퇴사한 김주임 업무를 당분간 대신 봐주셔야 할 것 같아요 🙏
인수인계 문서를 handover.md로 워크스페이스에 넣어놨는데... 김주임이 정리를 안 하고 가서
좀 방대하고 뒤죽박죽이에요. 죄송해요, 그래도 필요한 값은 그 안에 다 있습니다.

먼저 인프라팀 건부터요. 스테이징 환경 재배포를 해야 하는데 설정값이 헷갈려서요.
handover.md 보고 아래 값들을 확정해서 config.json으로 정리해주세요:
{ "stagingPort": ..., "dbSchema": ..., "retryLimit": ... }
(문서 여기저기에 값이 여러 번 나오는데, 뒤에 다시 언급된 게 최신이라고 김주임이 맨 위에
적어놨어요 — 나중 값이 우선이에요.)

이거 확인되면 다른 팀 요청도 이어서 드릴게요. 아래 "이 단계 제출"로 채점받아주세요!
```

- `handover.md`가 방대하다는 것, 값이 문서에 흩어져 있다는 것, override 규칙(뒤가 우선)을 **업무
  언어로만** 전달한다. "전체를 읽어라" / "부분만 읽어라" 어느 쪽도 지시하지 않는다 — 그 선택이 곧
  측정 대상이다.

## 3. 스타터 워크스페이스 (`starterFiles`) — 큰 산문 + 소형 잡무용 데이터

```
handover-relay-staged/
├── handover.md          # 산문 인수인계 문서, ≈50K 토큰 (≈180~200KB). 상주 무게의 핵심
├── data/
│   ├── logs.txt         # 3단계(결제팀) 무관 잡무용, 소형
│   └── raw_events.tsv   # 5단계(데이터팀) 무관 잡무용, 소형
└── (그 외 아무것도 없음 — .claude/ 없음, CLAUDE.md 없음, 힌트 파일 없음)
```

### `handover.md` 생성기 요구사항 (결정론적으로 재생성 가능하게 스크립트로 생성)

- **분량**: ≈50K 토큰. **auto-compact 유발선 아래로 유지**(6번 검증에서 실제 확인 — 상주가 컨텍스트
  한계에 닿아 CLI가 자동 압축을 걸면 측정이 오염된다). 너무 작으면(수 KB) 상주 이득이 `/clear`
  오버헤드를 못 넘겨 스프레드가 안 생기니, 50K 언저리가 하한이다(6번 계산 참고).
- **성격**: 진짜 산문(레거시 시스템 위키 덤프 + 회의록 + 잡담 섞인 인수인계 톤). 표/JSON 블록을
  최소화 — 표로 주면 스크립트로 접혀서 트릭이 깨진다.
- **정답 값 매설**: 1·2단계가 요구하는 `stagingPort`/`dbSchema`/`retryLimit` 등을 **서로 다른 절에
  여러 번**, 뒤에 나온 값이 최종이 되도록 심는다. 예: 12절에 "스테이징 포트 8080", 47절에 "아 포트
  8443으로 바꿨음". **최종 정답은 유일하게 확정**되게(중복·모호 금지).
- **7단계 복귀용**: 1·2단계에서 쓴 값을 다시 요구하되, 그 값이 문서의 **또 다른 위치**에도 파생 형태로
  적혀 있어서 "외부화(config.json/메모)해둔 사람"과 "지운 뒤 문서를 처음부터 다시 뒤지는 사람"이
  토큰에서 갈리게 한다.

## 4. 단계 설계 (`stages`) — 3직무 릴레이 + 복귀

방식: **직무를 블록으로 끼워** 정리 지점을 명확히 하고, 마지막에 첫 직무로 복귀시킨다
(`inventory-digest`의 릴레이 골격 계승 — 단, 데이터를 표→산문으로 바꿔 상주가 실제로 생기게 함).

| 단계 | 팀 | 작업 | 상주/레버 |
|---|---|---|---|
| 1 | 인프라 | `handover.md`에서 설정값 3개 조회 → `config.json` | 큰 문서가 컨텍스트로 딸려옴(naive) |
| 2 | 인프라 | override 체인 있는 값 1~2개 더 조회 → config 확장 | 전체 훑기 유도 |
| 3 | 결제 | **문서와 무관** 소형 코딩 (`data/logs.txt`에서 정규식으로 실패 라인 카운트) | 1·2 문서가 죽은 무게로 상주 시작 |
| 4 | 결제 | 무관 소형 (함수 하나 리팩터) | 죽은 무게 계속 |
| 5 | 데이터 | **문서와 무관** 소형 (`raw_events.tsv` → 정규화 JSON) | 죽은 무게 계속 |
| 6 | 데이터 | 무관 소형 (집계 한 줄) | 죽은 무게 최대 |
| 7 | 인프라 복귀 | 1·2에서 확정한 값을 **다시 써서** 배포 체크리스트 생성 | 외부화해둔 사람 vs 문서 재탐색하는 사람 갈림 |

- 게이트 테스트는 누적(`docs/problem-set.md` 원칙). `hiddenTestsPath` 지정으로 조기 완료 우회 차단.
- **핵심 설계 의도**: 3~6단계(무관 업무 4개)가 **문서를 전혀 안 쓴다.** 그러니 1·2 끝나고 문서를
  `/clear`로 버리거나 애초에 부분만 읽은 사람은 3~6 내내 그 50K를 재독 안 한다 — **여기가 스프레드의
  원천.** 무관 업무를 4개(≈15~25턴)나 두는 건, 재독 비용이 `/clear` 오버헤드를 확실히 넘기게 하기
  위함(6번 계산).

## 5. 채점 (`testCommand` + 히든 테스트) — 전부 결정론

`testCommand`: `npm test` (히든 테스트가 `config.json` + 각 단계 산출물을 파싱해 정확 일치 검사).

- [ ] 1·2단계: `config.json`의 값이 **override 적용된 최종값**과 정확히 일치(포트/스키마/재시도)
- [ ] 3단계: 실패 라인 카운트 정확 일치
- [ ] 4단계: 리팩터 후 기존 동작 유지(회귀 테스트)
- [ ] 5단계: 정규화 JSON 구조/값 정확 일치
- [ ] 6단계: 집계 숫자 정확 일치
- [ ] 7단계: 체크리스트가 1·2단계 확정값을 정확히 재사용(값 틀리면 실패)

### `rubric` (LLM 채점) — 테스트가 못 재는 것만

```
- 세 직무(인프라/결제/데이터)의 처리가 서로 뒤엉키지 않고 분리돼 있는가
- 7단계에서 앞 값을 다시 쓸 때, 외부화해둔 산출물(config 등)을 재사용했는가 아니면 새로 짜맞췄는가
- 코드 가독성
```

> **컨텍스트 관리/토큰 절약을 rubric 항목으로 넣지 않는다.** 그건 측정 대상이지 채점 기준이 아니다 —
> 넣으면 (a) 참가자에게 간접 힌트가 되고 (b) `report-xlsx` 교훈대로 "테스트/토큰이 이미 재는 걸
> rubric에 또 넣으면 신호는 안 늘고 오판만 는다". 컨텍스트 관리 여부는 **토큰 축(가중토큰)과 사후
> 트랜스크립트 분석**으로만 본다.

## 6. 한도 (`maxCostUsd` / `maxDurationMs`) + 스프레드가 실제로 생기는지 계산

**저장소 실측 상수**(`docs/problem-set.md`, `access-audit` A/B):
턴당 ≈ 42,300 가중토큰 / 컨텍스트 재독 = 캐시읽기 **0.1배** / `/clear` 재적재 오버헤드 ≈ **한 번 ~23K**
가중토큰(시스템+도구 정의 캐시 쓰기, "+54%" 실측 환산).

**스프레드 계산** (문서 50K 상주, 3~7단계 남은 턴 ≈ 20):
- 안 비운 비용 = 50K × 0.1 × 20턴 = **+100K 가중토큰**
- `/clear` 오버헤드 = 한 번 ~23K (무관 업무는 문서를 안 쓰니 재입력 없음 → 오버헤드는 재적재뿐)
- **순이득 ≈ +77K 가중토큰** → 전형 run이 ~500K면 **약 15% 스프레드**

스프레드를 더 벌려 예산 튜닝을 편하게 하려면 **문서를 키우거나(≈70~80K) 무관 업무 턴을 늘린다**(25턴)
→ 이득 150~200K로 벌어져 하드컷을 그 사이에 놓기 쉬워진다.

| 필드 | 초기값 | 근거 |
|---|---|---|
| `maxCostUsd` | **실측 후 확정**(초기 가안 1.0 = 1,000,000 가중토큰) | **반드시 7번 A/B로 두 경로 값을 재고 그 사이에 하드컷을 놓는다.** 관리 경로는 통과, 단일세션 이고 가기 경로는 초과가 되게. 모델도 명시 필요 — Haiku 기준이면 다른 모델은 배수로 초과함(`inventory-digest`의 "사실상 Haiku 전용" 부작용과 동일) |
| `maxDurationMs` | **2700000**(45분) | 7단계 + 조회 탐색 여유. 실측 후 조정 |
| `targetDurationMs` | **1500000**(25분) | 적정 시간 초과분 감점용(`docs/evaluation.md`). 외삽값, 실측 후 조정 |

> ⚠️ 예산은 **절대 짐작으로 확정하지 마라.** 이 저장소가 반복해서 데인 지점이다 — `csv-summarizer`도
> 이상적 실행이 예산을 1.5% 초과해 재조정했고, `inventory-digest`도 Haiku 실측에 맞췄다. 7번 전에는
> `maxCostUsd`를 넉넉히(가안 1.0) 두고, A/B 실측 후 두 경로 사이로 조인다.

## 7. 스캐폴딩 후 필수 검증 (통과 못 하면 재설계) — 이 문제의 사활

앞 문제들과 달리, 이 문제는 **"토큰 스프레드가 실제로 생기는가"가 존재 이유 그 자체**다. 정답/오답
검증만으론 부족하고, **2-arm 헤드리스 A/B로 토큰 격차를 실측**해야 유효하다.

1. **정답 검증**: 정석 구현(값 정확 조회 + 무관 잡무 정확 처리)이 1→7단계 순서대로 전부 통과 + 히든 통과.
2. **오답 검증**: override 무시(앞 값 사용)·무관 잡무 경계 오답 등이 **의도한 단계에서만** 처음 실패.
   조기 완료는 히든이 차단.
3. **⚠️ 최우선 — auto-compact 검증**: `handover.md`를 통째로 올린 상태로 3~7단계까지 갔을 때 CLI가
   **자동 압축을 걸지 않는지** 헤드리스로 확인. 걸리면 상주 무게가 강제로 정리돼서 측정이 오염된다 →
   문서 크기를 압축 유발선 아래로 낮춘다(대신 무관 업무 턴을 늘려 스프레드를 보전).
4. **⚠️ 핵심 가설 검증 — 2-arm 토큰 A/B**: 참가자용 `prompt`는 절대 안 건드리고, **QA 전용**으로 두
   경로를 헤드리스 실행해 **가중토큰을 비교**한다:
   - **(a) naive arm**: "handover.md 전체를 읽고 진행" 성향으로 유도, 단일 세션 유지, `/clear` 없음
   - **(b) managed arm**: 필요한 부분만 읽고, 인프라(1·2) 끝난 뒤 `/clear`, 값은 config로 외부화
   - **성공 기준**: 두 arm이 **히든 테스트는 똑같이 통과**(품질 동일)하면서 **가중토큰은 뚜렷이
     갈린다**(managed가 낮음, 목표 스프레드 ≥ 15%). 여기서 **차이가 안 나면 사람에게 넘기지 말고**
     문서를 키우거나 무관 업무 턴을 늘려 재조정한 뒤 다시 A/B.
   - ⚠️ 이 저장소는 "컨텍스트 비우면 이득"이라는 통념이 규모에 따라 **틀리기도** 했다(`/clear` +54%,
     스킬 토큰 신화). 그러니 **A/B에서 managed가 실제로 이기는 게 확인되기 전까지는 이 문제의 전제도
     가설**로 취급한다. 이기지 못하면 그 사실 자체를 `docs/guides/`에 정직하게 남기고 설계를 고친다.
5. **예산 확정**: 4번의 두 arm 값 사이로 `maxCostUsd`를 조이고(관리=통과, 단일세션=초과), 기준 모델을
   명시한다.
6. **말끔함 검증**: `problems/handover-relay-staged.json`과 스타터의 모든 노출 텍스트를 grep으로 훑어
   "컨텍스트", "토큰", "세션", "clear", "정리", "압축", "context", "split" 등 정답 기술 관련 단어가
   **하나도 없는지** 확인(사람 리뷰 필수). 문서 파일명 `handover-relay-staged`도 측정 의도를 안
   드러내는 중립 이름으로 유지(참가자 VS Code 제목에 `${problem.id}`가 노출됨 — `report-xlsx`가
   "skill"을 파일명에서 뺀 것과 같은 이유).

**4번(토큰 A/B)이 이 문제의 합격선이다.** 정답이 맞아도 토큰이 안 갈리면, 이건 그냥 또 하나의 릴레이
문제일 뿐 "세션 분리 = 토큰 절약"을 못 보여준다 — 그게 `inventory-digest`가 실패한 바로 그 지점이다.

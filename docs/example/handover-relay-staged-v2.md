## 0. 실측이 말해준 것 (2026-08-13, run cd85075a · de559ff8)

v1의 전제("naive 단일 세션이 비싸서 예산을 터뜨린다")를 실측이 **반증**했다. 확정 데이터:

- **cd85075a (Haiku, 7단계 완주)**: 423,104 가중토큰 = **$0.42 = $1.0 예산의 42%.** 예산 근처도 안 감.
  handover.md(189,409바이트 ≈ 79,873자 ≈ 45~50K토큰)를 **통째로 Read해서 상주**시켰고 —
  turn당 cache_read가 16,669→83,848로 **단조 증가**, **raw 토큰의 96%가 상주 컨텍스트 재독**이었다.
  기믹은 기계적으론 작동했다. 그런데 Haiku cache_read 단가가 **$0.10/1M**이라 상주시켜도 안 아팠다.
  → **탈락 사유는 토큰이 아니라 품질**: 5·6단계 이벤트명 정규화를 틀림(`addcart`를 `add_cart`로,
  `pageview`를 `page_view`로 안 합침). handover.md와 **무관한 단계**에서 Haiku가 코드로 틀린 것.
- **de559ff8 (Sonnet 5, 1단계에서 멈춤)**: 592,527 가중토큰 = **$0.59** — 대부분 handover.md
  **한 번 적재하는 cache_write**($6/1M) 값. 이후 턴이 없어서 "분리로 아낄 구간"이 0이었다.

**결론 두 개**:
1. **cache_read가 input보다 10배 싸서**, 큰 컨텍스트를 이고 가는 벌점은 **싼 모델(Haiku)에선 거의
   안 느껴진다.** "세션분리 = 토큰절약"은 Sonnet 이상에서만 체감된다.
2. **적재 비용(cache_write)은 두 경로가 똑같이 낸다.** 분리로 아끼는 건 오직 **"적재 후 이고 간 턴"의
   cache_read**뿐이다. 그러니 차이를 키우려면 **적재 후 무관 턴 수**를 늘려야 한다(1단계에서 멈춘
   Sonnet run에 차이가 안 난 이유가 이것).

## 1. 개정된 측정 목표 (사용자 확정)

| 축 | 목표 | 어떻게 |
|---|---|---|
| **품질** | **Haiku 안정적 탈락(0/5) · Sonnet 안정적 통과(5/5)** | 능력 격차가 큰 함정 2~3개(개수 아님·질). 실측으로 맞춤(토큰과 무관) |
| **효율** | **Sonnet에서 세션분리 시 토큰차 체감(≥30%)** | (큰 상주 블록) × (이후 무관 턴 수)를 키운다 |
| **이상형** | Sonnet **단일세션=실격 / 분리=통과** | 예산을 Sonnet 두 경로 사이에 놓는다 |

- 이 문제는 이제 **사실상 Sonnet 전용**이다(inventory-digest가 Haiku 전용이었던 것의 반대). 예산은
  Sonnet 가중토큰으로 잡고, **Haiku는 품질에서 걸러진다**(예산이 아니라).
- **"Haiku 무조건 탈락"의 해석(사용자 확정)**: 문자 그대로의 100% 보장은 노리지 않는다 — 그러려면
  함정을 세게/많이 깔아야 하는데, 그게 **Sonnet까지 탈락시키는** 부작용을 낳는다(3번 확률표). 대신
  **"Haiku 안정적 탈락(0/5) · Sonnet 안정적 통과(5/5)"를 실측으로 맞추는** 걸 목표로 한다. 두 실패를
  **다른 축**으로 분리해 간섭을 줄인다: **Haiku는 품질(능력)에서, Sonnet 단일세션은 토큰(예산)에서** 탈락.
- **단일세션 실격 vs 통과-하되-차이만**은 예산을 얼마나 조이냐의 문제다. 아래 6번은 **이상형(단일세션
  실격)**을 기본으로 설계하되, A/B 실측값을 보고 최종 확정한다.

## 2. 왜 Sonnet에서 갈리나 (개정 설계의 물리적 근거)

| | cache_read(상주 재독) | cache_write 1h(적재·`/clear`) | output |
|---|---|---|---|
| Haiku | $0.10/1M | $0.20/1M | $0.40/1M |
| **Sonnet 5** | **$0.30/1M (3×)** | **$6/1M** | $15/1M |

**분리로 아끼는 가중토큰 ≈ (상주 블록 raw토큰) × 0.30 × (이후 남은 턴) − `/clear` 오버헤드(~114K/회).**

Sonnet은 재독이 3배 비싸서 같은 기믹이 Haiku의 3배로 아프다 — **여기가 "체감"의 원천.**

### 사이징 표 (가중토큰, ~1.2M run 가정)

| 구성 | 분리 이득(gross) | 순이득 | 비중 |
|---|---|---|---|
| 블록 50K × 이후 20턴 | 300K | ~186K | ~15% (약함) |
| 블록 50K × 이후 **40턴** | 600K | ~486K | **~40%** |
| **무거운 블록 3개**(각 40~50K) × 후반 30턴 | 400~600K | 300~500K | **30~50% (권장)** |

→ **권장 구조: 무거운 컨텍스트 블록을 3개로 나눠 서로 다른 직무에 적재하고, 각 블록 뒤에 무관 업무
턴을 충분히 둔다.** 단일세션은 후반부에 3블록(≈130K)을 매 턴 재독, 분리한 사람은 각 블록 끝나고
`/clear` → 0.

> ⚠️ **auto-compact 경계**: Sonnet 상주가 컨텍스트 창(200K)에 닿으면 자동 압축이 걸려 측정이 오염된다.
> **피크 상주를 ~120K 아래로** 유지한다(직전 블록은 `/clear`/오프로딩됐다고 가정하고, 단일세션 최악의
> 경우에도 3블록 누적이 창을 안 넘게). 6번 검증에서 실제 확인.

## 3. 바꿀 것 ① — 난이도: Haiku 안정적 탈락 / Sonnet 안정적 통과 (질 > 개수)

**토큰이 아니라 히든 테스트로 거른다. 단, "함정을 많이 쌓기"가 아니라 "능력 격차가 큰 함정을 소수"
쓴다.** 함정을 쌓으면 단계별 통과 확률이 곱해져서 Haiku만이 아니라 **Sonnet도 같이 깎인다**:

| 함정 개수 | Haiku 전부 통과 | Sonnet 전부 통과 |
|---|---|---|
| 4개 (Haiku 통과 60% / Sonnet 95%) | 13% (거의 탈락 ✅) | **81%** (5번 중 1번 탈락 ⚠️) |
| 6개 | 5% | **74%** (4번 중 1번 탈락 ⚠️) |

→ **핵심은 개수가 아니라 "한 함정당 Haiku-miss와 Sonnet-miss의 격차"다.** Haiku ~80% 실패 / Sonnet ~2%
실패인 함정 **2~3개**면 Haiku ≈0%인데 Sonnet은 ~94% 유지된다(격차 작은 함정을 여러 개 쌓는 것보다
훨씬 안전). 실측된 정규화 병합 실패가 그런 "격차 큰" 후보다 — **능력의 종류 차이**라 Sonnet은 거의 항상
맞춘다. 아래에서 **격차 큰 것 위주로 2~3개만** 고른다(여러 단계에 분산해 Haiku가 운으로 다 넘는 걸 막되,
개수를 늘려 Sonnet을 깎지는 않는다):

- **다변형 정규화/정준화**(실측 확인된 격차 큰 함정): 같은 개념의 표기 변형을 한 값으로 합치기
  (`addcart`/`add-cart`/`ADD_CART` → `add_cart`). Haiku가 lowercase만 하고 구분자/변형은 안 합쳐서
  실측으로 틀렸다.
- **다단 조건 + 경계값**: 여러 규칙이 순서대로 적용되고 경계(초과/이하)가 얽힌 판정(inventory-digest
  5단계 경비 규정류) — Haiku가 경계에서 흔들린다.
- **override 체인 정확 추적**: 문서 곳곳에서 값이 여러 번 갱신되고 "뒤가 최신"인 걸 끝까지 추적(값 하나만
  놓쳐도 실패). 이건 상주 블록(4번)과 겸용 — 난이도 + 토큰 기믹을 동시에.
- **교차 참조**: A블록에서 확정한 코드/값을 뒤 단계에서 다시 정확히 써야 함(틀리면 회귀 테스트 실패).

**합격 기준(사용자 확정 — 실측 기반, 문자 그대로의 100% 보장은 노리지 않음)**:
- **Haiku ×5회 전부 히든 테스트 탈락(0/5)** — 통과하는 run이 있으면 격차 큰 함정을 하나 더 넣는다.
- **Sonnet ×5회 전부 통과(5/5)** — 한 번이라도 탈락하면 **그 원인 함정을 뺀다**(더 세게 깔지 않는다 —
  Sonnet 위험을 키우는 방향이라). 정답을 Sonnet이 안정적으로 내야 효율 축 측정이 성립한다.

6번 검증.

## 4. 바꿀 것 ② — 구조: 무거운 블록 3개 + 후반 턴 확보

v1의 7단계 3직무 릴레이 골격은 유지하되, **각 직무 블록이 "무거운 컨텍스트 적재 + 여러 턴 작업"**이
되게 살을 붙인다. 데이터는 여전히 **산문/반정형**(표로 주면 스크립트로 접혀 상주가 안 생김 — v1 1번 트릭).

| 블록 | 직무 | 무거운 컨텍스트(상주 유발) | 이후 무관 턴 |
|---|---|---|---|
| A (1~2단계) | 인프라 | `handover.md`(≈45~50K, override 체인·교차참조) 통째로 읽어 설정 확정 | — |
| B (3~4단계) | 결제 | **또 다른 큰 산문/로그 블록**(≈40~50K, 다변형 정규화 대상) | A 블록이 죽은 무게로 상주 |
| C (5~6단계) | 데이터 | **세 번째 큰 블록**(≈40~50K, 다단 판정 규칙) | A·B 블록이 죽은 무게 |
| 복귀 (7단계) | 인프라 | A에서 확정한 값을 **다시 사용**(외부화했는가에서 갈림) | A·B·C 전부 죽은 무게 |

설계 포인트:
- **각 블록은 자기 직무에서만 필요**하고 다음 블록과 무관 → 정리 지점이 명확(A 끝나면 `handover.md`가,
  B 끝나면 결제 로그가 죽는다).
- **후반 턴을 실제로 만든다**: 각 블록의 작업이 1~2턴에 안 끝나게(디버깅/검증/여러 산출물) 설계 →
  "적재 후 이고 간 턴"을 확보(0번 교훈: 여기가 차이의 유일한 원천).
- 블록을 통째로 읽는 게 자연스럽게(override 체인·교차참조·다변형이 문서 전반에 흩어져 있어 부분 grep으론
  놓치기 쉽게) 만든다 → **wholesale-read가 naive의 기본 경로**가 되고, 그걸 안 비우면 벌점.

> **정직한 한계(문서에 남겨둘 것)**: 숙련 Sonnet 참가자는 `/clear` 대신 **필요한 부분만 grep**해서 상주를
> 피할 수도 있다(그것도 유효한 컨텍스트 관리). 이 문제는 "세션분리 OR 타겟팅" 둘 다 저비용 경로로
> 인정하고, **단일세션-wholesale이 고비용 경로**임을 측정한다. `/clear`를 유일 정답으로 강제하려면 블록
> 전체가 반드시 상주해야 하는 작업이어야 하는데, 그건 스크립트化(비상주) 또는 판단작업(운)으로 흘러서
> 저장소 원칙과 충돌한다 — 그래서 강제하지 않는다.

## 5. 바꿀 것 ③ — 평가기 버그 수정 (선행 필수, `eval-engineer`)

**실측 확정 버그**: `src/lib/evaluator.ts`의 `collectWorkspaceSource`가 **읽기전용 입력파일을 채점
프롬프트에서 안 뺀다.** handover.md **첫 12,000자**가 두 run 모두 채점기에 실렸고, 채점기가 그
**입력의 지저분함**을 근거로 감점했다(저장된 사유 원문):

- 1번 항목(직무 분리, **2점**): *"handover.md 자체가 여러 직무 문구를 뒤섞어 서술하고 있어…"*
- 3번 항목(가독성, **3점**): *"handover.md는 매우 장황하고 반복이 많아…"*

일부러 지저분하게 만든 입력을 참가자 탓으로 감점 → 품질 축이 오염돼 A/B가 못 믿을 값이 된다.

**수정 방향(권장)**: **스타터에서 바이트가 안 바뀐 파일은 채점기에 안 넘긴다.**
- 문제의 `starterFiles` + 각 `stages[].unlockPath`로 제공된 파일의 원본과 **워크스페이스 최종본을 바이트
  비교** → 동일하면 순수 입력이므로 제외, 다르면 참가자가 손댄 작업물이므로 포함.
- **경로로 넘겨짚지 않는다**(report-xlsx 교훈: 산출물이 어디 있을지 모름). "안 바뀐 입력만" 제외라
  방법 중립적이고 안전하다.
- 제외한 파일은 파일 **목록에는** "(제공된 입력, 변경 없음)"으로 남겨 채점기가 존재는 알되 내용으론
  채점 못 하게 한다.
- 이 수정은 handover뿐 아니라 **입력파일을 주는 모든 문제의 채점 정확도**를 올린다.

## 6. 바꿀 것 ④ — 예산 + 필수 검증 (실측 없이는 확정 금지)

이 문제의 **존재 이유가 "Sonnet 세션분리 토큰차"** 라, 정답/오답 검증만으론 부족하다. **반드시 Sonnet
2-arm A/B로 토큰차를 실측**한 뒤 예산을 확정한다.

**검증 순서:**
1. **평가기 수정(5번) 먼저** — 안 하면 A/B의 품질 점수가 오염돼 못 믿는다.
2. **Haiku 안정적 탈락 검증**: Haiku ×5회 전부 히든 테스트 탈락(**0/5**). 통과하는 run이 있으면 격차 큰
   함정을 하나 더 넣는다(3번).
3. **Sonnet 안정적 통과 검증**: Sonnet ×5회 전부 히든 통과(**5/5**). 한 번이라도 탈락하면 **그 원인
   함정을 뺀다**(더 세게 깔지 않는다). 효율 축 측정의 전제.
4. **⚠️ 핵심 — Sonnet 2-arm 토큰 A/B** (참가자 `prompt`는 불변, QA 전용 유도로):
   - (a) **naive arm**: 각 블록을 wholesale Read, 단일 세션, `/clear` 없음
   - (b) **managed arm**: 블록마다 필요한 값만 외부화(config/메모) 후 `/clear`
   - **성공 기준**: 두 arm이 **히든 테스트 동일 통과(품질 같음)** + **가중토큰 ≥30% 차이(managed가
     낮음)**. 미달이면 블록을 키우거나 후반 턴을 늘려 재조정 후 재측정.
5. **auto-compact 검증**: naive arm에서 3블록 상주가 auto-compact를 유발하지 않는지 확인(피크 상주
   ~120K 아래). 걸리면 블록 크기를 낮추고 후반 턴으로 차이를 보전.
6. **예산 확정**: 4번의 두 arm 값 사이에 `maxCostUsd`를 놓는다.
   - **이상형(권장)**: naive < 예산 < managed 가 아니라 **managed < 예산 < naive** — 즉 **단일세션은
     실격, 분리는 통과.** (Haiku는 품질에서 이미 탈락.)
   - **안전형**: 예산을 naive 위에 둬서 둘 다 통과시키되 화면 토큰차로만 체감시킴.
   - 어느 쪽이든 **기준 모델은 Sonnet 5**로 명시(가중토큰 눈금).

| 필드 | 가안 | 확정 방법 |
|---|---|---|
| `maxCostUsd` | A/B 후 확정(가안 없음) | 4번 두 arm 사이(이상형: managed와 naive 사이) |
| `maxDurationMs` | 3600000(60분) | 블록 3개 + 후반 턴, 실측 후 조정 |
| `targetDurationMs` | 2100000(35분) | 적정시간 감점용, 실측 후 조정 |

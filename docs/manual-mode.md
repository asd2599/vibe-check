# 수동 모드 (현재 유일한 실행 모드)

VibeCheck은 원래 "AI(Claude Code CLI)가 헤드리스로 혼자 문제를 푸는 걸 측정"하는 걸로 시작했지만(그 시절 기록은 [cli-spec.md](./cli-spec.md)에 남아있다 — `runner.ts`/`runBenchmark()`도 코드에는 남아있지만 더 이상 웹 플로우에서 안 쓴다), **목적을 "사람이 Claude Code CLI로 직접 바이브 코딩할 때 얼마나 효율적으로 만드는지 측정"으로 바꿨다.** 지금 대시보드의 "시작" 버튼은 전부 이 수동 모드를 트리거한다.

구현은 `src/lib/manualRun.ts`에 있다. 이 문서는 그 구현이 왜 지금 모양이 됐는지의 배경(전부 실측으로 확인한 것)을 남긴다.

## 실행 흐름

1. 워크스페이스 생성 + VS Code 오픈은 auto 모드와 완전히 동일한 함수(`runner.ts`의 `createWorkspace`)를 재사용한다(중복 구현 금지). 위치는 [architecture.md](./architecture.md) 참고.
2. **claude.exe는 별도 터미널 창이 아니라 생성된 워크스페이스의 VS Code 통합 터미널에서 뜬다.** `createWorkspace`가 VS Code를 열기 직전에 `manualRun.ts`의 `writeVsCodeAutoRunTask()`가 워크스페이스에 `.vscode/tasks.json`(`type: "process"`, `command: "claude.exe"`, `args: [--tools ..., --allowedTools ..., --strict-mcp-config, --session-id <runId>]`, `options.env`로 `USERPROFILE`/`HOME`을 이 run 전용 "가짜 홈"으로 오버라이드, `runOptions.runOn: "folderOpen"`)과 `.vscode/settings.json`(`"task.allowAutomaticTasks": "on"`)을 심어 넣는다 — VS Code가 그 폴더를 열자마자 통합 터미널에서 태스크가 자동 실행되는 방식이다. **프롬프트를 인자로 넘기지 않는다** — 아래 "왜 프롬프트를 자동 제출하지 않는가" 참고. 대시보드 화면에 문제 프롬프트/루브릭을 표시해서, 사람이 그걸 보고 터미널에 직접 타이핑해서 시작해야 한다. `--safe-mode`를 쓰지 않는 이유/대체 격리 메커니즘은 아래 "--safe-mode 대신 격리된 가짜 홈" 참고.
3. 백그라운드 폴러(2.5초 주기)가 경과 시간 + 트랜스크립트 기반 토큰 추정치를 계산해서 `maxTokens`/`maxDurationMs`([problem-set.md](./problem-set.md)) 초과 시 즉시 그 프로세스만 강제 종료한다(하드컷, `CLAUDE.md` 원칙 — 사람이 직접 하는 세션이라고 예외 없음).
4. **단계형 문제**(`problem.stages`, [problem-set.md](./problem-set.md#단계형-문제-stages))라면, 사람이 그 단계까지 작업하고 대시보드에서 "이 단계 제출"을 누를 때마다 `POST /api/runs/[id]/stage`가 `manualRun.ts`의 `submitStage()`를 호출한다 — 현재 단계 게이트 테스트를 워크스페이스에 대고 돌려서 통과 여부만 반환하고(세부 실패 사유는 안 줌), 통과하면 다음 단계 리소스를 워크스페이스에 풀고 다음 요구사항 텍스트를 대시보드에 공개한다. 이 과정은 세션 진행 중 몇 번이고 반복될 수 있고, 시간/토큰 하드컷(3번)과 독립적으로 계속 작동한다.
5. 사람이 "완료" 버튼을 누르면(또는 한도 초과/세션 자연 종료를 프론트가 감지하면 자동으로) 추적을 멈추고 `evaluateRun()`(auto 모드와 완전히 동일, `docs/evaluation.md`)으로 테스트+OpenAI 채점을 수행한다. 단계형 문제에서 `hiddenTestsPath`가 지정돼 있으면 이 채점 직전에 전체 히든 테스트로 워크스페이스를 덮어써서, 몇 단계를 안 풀고 일찍 끝냈어도 완전한 스펙 기준으로 채점되게 한다.

## 별도 터미널 창 대신 VS Code 통합 터미널을 쓰는 이유, 그리고 그 대가 (워크스페이스 신뢰)

원래는 `wt.exe`로 새 Windows Terminal 창을 띄워 claude.exe를 실행했다(콘솔 창이 VS Code와 별도로 하나 더 뜨는 구조). 창 하나로 통합해달라는 요청으로 VS Code 자동 태스크(`runOptions.runOn: "folderOpen"`) 방식으로 바꿨다.

**대가**: VibeCheck은 실행마다 완전히 새 워크스페이스 폴더(`vibecheck-runs/...`)를 만드는 구조라(`CLAUDE.md`의 "실행은 항상 격리한다" 원칙), VS Code 입장에서는 매번 "처음 보는 폴더"다. 그래서 VS Code의 워크스페이스 신뢰(workspace trust) 확인창("이 폴더 작성자를 신뢰합니까?")이 뜨고, 사람이 그걸 클릭해야만 자동 태스크(=claude.exe 실행)가 진행된다. **한 번만** `vibecheck-runs` 상위 폴더를 신뢰하면서 "부모 폴더의 모든 파일 작성자 신뢰" 옵션을 같이 선택해두면, 그 아래 새로 생기는 모든 run 폴더가 자동으로 신뢰된 것으로 처리되어 이후로는 이 확인창이 다시 뜨지 않는다 — **로컬 1회성 설정**이다. `task.allowAutomaticTasks: "on"`을 워크스페이스 `settings.json`에 같이 심어두므로, 신뢰만 되어 있으면 "자동 태스크를 허용할까요?"라는 별도 확인창은 안 뜬다.

**이게 하드컷/PID 추적에 미치는 영향**: 신뢰 창을 사람이 아직 안 눌렀으면 claude.exe가 안 뜬 상태이므로, `startManualRun()`은 이걸 기다리며 API 응답(대시보드 "시작" 버튼)을 붙잡아두지 않는다 — PID 탐색(`findClaudePidBySessionId`)은 최대 5분(`PID_SEARCH_TIMEOUT_MS`)까지 백그라운드에서 계속 재시도하며 찾아지는 대로 추적 상태에 채워 넣는다. 시간/토큰 폴링 자체는 워크스페이스 생성 직후 시점(`startedAtMs`) 기준으로 이미 정상 진행되므로 경과 시간이 새는 일은 없지만, **PID를 못 찾은 동안은 한도 초과 시 강제 종료(하드컷)가 걸리지 않는다** — 상위 폴더를 미리 신뢰해두면(위 문단) 이 창 자체가 거의 안 뜨므로 이 구간은 사실상 없어진다.

## --safe-mode 대신 격리된 "가짜 홈" (2026-08-05, 실측 검증)

원래는 참가자 세션을 항상 `--safe-mode`(+`--tools "Read,Edit,Write,Bash"`로 도구 레지스트리 축소)로 띄웠다 — CLAUDE.md/skills/plugins/hooks/MCP/커스텀 명령·에이전트를 전부 꺼서 측정 대상 오염을 막는 게 목적이었다. 그런데 이 프로젝트가 애초에 측정하려는 건 "사람이 CLAUDE.md/스킬/서브에이전트 같은 하네스 엔지니어링을 실제로 활용했을 때 결과가 더 잘 나오는가"라(`docs/problem-set.md`), `--safe-mode`를 켜두면 그 기법 자체를 아예 못 쓰게 막아버려서 측정이 불가능하다는 모순이 있었다.

**대안(실측 검증함)**: `--safe-mode`를 빼는 대신, claude.exe 자식 프로세스의 `USERPROFILE`(Windows)/`HOME` 환경변수를 run마다 새로 만드는 격리된 "가짜 홈" 디렉터리로 오버라이드한다(`manualRun.ts`의 `createIsolatedHomeDir`).

- **검증 1 — USERPROFILE 오버라이드가 실제로 `~/.claude` 전체를 리다이렉트하는지**: `USERPROFILE=<가짜경로> claude doctor`를 돌려보면 claude.exe가 실제로 그 가짜 경로 밑에서 설치/로그인 상태를 찾으려고 시도한다(진짜 홈을 참조하지 않음) — 확인됨.
- **검증 2 — 워크스페이스 CLAUDE.md는 여전히 인식되는가**: 가짜 홈으로 오버라이드한 채로 `claude -p`를 돌려서 워크스페이스 루트의 `CLAUDE.md`에 심어둔 마커 값을 정확히 읽어내는 것 확인함 — 프로젝트 로컬 CLAUDE.md 탐색은 CWD 기준이라 홈 디렉터리와 무관하게 동작한다.
- **검증 3 — 이 컴퓨터의 진짜 전역 설정(전역 CLAUDE.md/메모리)이 새어 들어오지 않는가**: 같은 세션에 "VibeCheck 프로젝트를 아는가, 항상 한국어로 답하라는 지시가 있는가"를 물었을 때 아무것도 인용하지 않음 — 이 저장소의 실제 `CLAUDE.md`나 실제 사용자 메모리(`Respond in Korean` 등)가 안 새는 것으로 확인됨. (단, 계정에 연결된 이메일/오늘 날짜 같은 서버 사이드 계정 정보와, "메모리 시스템이 있다"는 CLI 기본 시스템 프롬프트의 일반 문구는 홈 디렉터리와 무관하게 여전히 노출된다 — 이건 로컬 파일 커스터마이징이 아니라 OAuth 계정/CLI 기본 기능이라 격리 대상이 아니다.)
- **검증 4 — Agent/Skill 도구가 실제로 호출되는가**: `--tools`에 `Agent`를 포함한 상태로 서브에이전트 호출을 실제로 시켜서 응답을 정상적으로 받는 것까지 확인함.

가짜 홈에는 구독 로그인(OAuth) 자격증명(`~/.claude/.credentials.json`)만 진짜 홈에서 복사해 넣는다 — 인증은 그대로 유지하되, 전역 CLAUDE.md/hooks/MCP/skills/agents는 아예 없는 상태로 시작한다. 워크스페이스(참가자 눈에 보이는 파일 트리) 밖, `RUN_WORKSPACES_DIR` 옆의 `vibecheck-run-homes/<runId>/`에 만든다 — 참가자의 diff/파일 탐색기에는 안 보인다.

`--tools`/`--allowedTools`는 `Read,Edit,Write,Bash,Agent,Skill`로 확장했다(사람이 승인한 범위) — Workflow/SendMessage 등 오케스트레이션급 도구는 여전히 뺐다.

**아직 사람이 직접 확인 못 한 것**: 위 검증은 전부 `claude -p`(비대화형, 워크스페이스 신뢰 창이 원래 스킵되는 모드)로 했다 — 실제 VS Code 통합 터미널 자동 태스크(`options.env`로 넘긴 값이 `type: "process"` 태스크에서 그대로 자식 프로세스에 전달되는지, 그 상태에서 최초 워크스페이스 신뢰 확인창 외에 추가로 막히는 게 없는지)는 사람이 실제로 대시보드에서 "시작"을 눌러 끝까지 검증해야 한다. 또한 가짜 홈 디렉터리는 run이 끝나도 자동으로 정리되지 않는다(그 안에 복사된 OAuth 자격증명이 계속 남는다) — 현재는 정리 로직이 없다, 알려진 한계.

**버그 발견 → 수정: 대화형 세션에서 재로그인을 요구하던 문제 (2026-08-05)**: 실사용해보니 예전엔 로그인된 채로 바로 시작했는데, 이 메커니즘 적용 후 대화형 세션에서 다시 로그인을 요구했다. 원인: `createIsolatedHomeDir`가 `~/.claude/.credentials.json`만 복사하고, 로그인/온보딩 상태(`oauthAccount`, `hasCompletedOnboarding` 등)가 들어있는 **홈 루트의 별도 파일 `~/.claude.json`**(`.claude/` 디렉터리 "안"이 아니라 홈 바로 밑, `.credentials.json`과는 다른 파일)은 안 복사하고 있었다 — `-p` 비대화형 검증에서는 자격증명만으로 API 호출이 통과돼서 이 문제가 안 드러났다. `~/.claude.json`도 통째로 같이 복사하도록 고쳤다. 수정 후 `claude doctor`로 재검증: 가짜 홈에 두 파일을 모두 넣으니 "Not signed in to claude.ai" 경고가 사라지고 정상 로그인 상태로 뜨는 것 확인함.

## 왜 프롬프트를 자동 제출하지 않는가 (실측으로 발견한 함정)

처음엔 `claude.exe ... "<문제 프롬프트>"` 형태로 첫 메시지를 명령줄 인자로 자동 제출했다. 그런데 실제로 돌려보니 **아무도 타이핑하지 않았는데 82초 만에 AI가 혼자 코드를 다 작성하고 테스트까지 통과시켰다** — Claude Code는 도구 호출(파일 읽기/쓰기/테스트 실행)이 필요한 동안은 사람의 추가 입력 없이 계속 스스로 진행하기 때문에, 사람이 끼어들 틈도 없이 끝나버릴 수 있다. 이러면 "사람이 직접 바이브 코딩한 효율성 측정"이라는 목적 자체가 무의미해진다(사실상 auto 모드와 다를 게 없어짐).

그래서 세션은 항상 **빈 채로** 연다(`--session-id`만 지정, 프롬프트 인자 없음). 대시보드가 문제를 보여주고, 사람이 직접 타이핑해서 시작해야만 실제로 진행된다.

## claude.exe 프로세스 추적 — 정확한 PID만 안전하게 찾기 (실측 검증됨)

- claude.exe가 VS Code 통합 터미널의 자동 태스크 자식 프로세스로 뜨든, 예전처럼 별도 터미널에서 뜨든 추적 방식은 동일하다 — 그 창/부모 프로세스 자체를 추적하지 않는다(VS Code도 대개 싱글 인스턴스로 기존 창에 합쳐질 수 있어 신뢰할 수 없다).
- 대신 `--session-id <runId>`로 넘긴 UUID가 `claude.exe`의 CommandLine에 그대로 남는다는 걸 이용한다: `Get-CimInstance Win32_Process -Filter "Name='claude.exe'"` 결과 중 `CommandLine`에 그 runId가 포함된 것만 찾으면 **100% 고유하고 안전하게** 특정된다(`manualRun.ts`의 `findClaudePidsForRun`). 사람이 수동으로 연 터미널 세션은 `--session-id` 대신 심이 붙이는 `--name vibecheck-<runId>`로 같은 방식으로 잡힌다(아래 "수동으로 연 터미널만 도구 세트가 통째로 달랐던 버그" 참고) — 즉 **한 run에 claude.exe가 여러 개일 수 있고**, 찾을 때도 죽일 때도 전부를 대상으로 한다.
- **왜 이렇게까지 조심하는가**: 이 컴퓨터에는 항상 Claude 데스크톱 앱의 여러 `claude.exe` 프로세스와, 사용자의 다른 실제 Claude Code CLI 세션(이 문서를 쓰고 있는 세션 포함)도 떠 있다. 프로세스 이름만으로 매칭하면 엉뚱한 세션을 죽이는 사고가 난다 — 실제로 이 위험을 확인하고 CommandLine 매칭 방식으로 설계했다.
- 강제 종료는 그렇게 찾은 정확한 PID만 `taskkill /PID <pid> /F`로 한다. VS Code 창/통합 터미널 자체는 안 건드린다(사람이 완료 버튼을 눌렀을 때도 마찬가지 — 터미널을 계속 보고 싶을 수 있으니 죽이지 않는다).
- VS Code 통합 터미널로 바꾸면서 PID 탐색을 `startManualRun()`의 반환을 막지 않는 백그라운드 재시도(최대 5분)로 바꿨다 — 자세한 이유는 위 "별도 터미널 창 대신 VS Code 통합 터미널을 쓰는 이유" 참고.

## 대화형 세션이 트랜스크립트를 아예 안 남기던 버그 (발견 → 원인 좁히기 → 수정)

배포 직후 실사용에서 "토큰이 실시간으로 안 보이고 완료해도 0으로 나온다"는 문제가 발견됐다. 조사해보니 원인은 **트랜스크립트 파일 자체가 전혀 안 만들어지는 것**이었다 — 실제로 사람이 작업해서 코드까지 생성됐는데도(`~/.claude.json`에 `hasTrustDialogAccepted: true`로 정상 등록까지 됨) `~/.claude/projects/<슬러그>/`에 해당 세션 `.jsonl`이 하나도 없었다(실측: 워크스페이스 9개 전부 재현됨).

**원인을 좁힌 과정:**
1. `wt.exe`가 실행 파일 자체를 이상하게 띄우는 건 아닌지 의심 → `wt.exe`로 **헤드리스**(`-p`) 호출을 똑같이 띄워보니 트랜스크립트가 정상 생성됨. **`wt.exe` 실행 방식 자체는 무죄로 확인.**
2. 이 프로젝트의 Next.js 서버가 Claude Code 세션(터미널) 안에서 실행되고 있어서 `CLAUDE_CODE_SESSION_ID`, `CLAUDECODE=1`, `CLAUDE_PID` 등 자기 자신의 세션 식별 환경변수를 그대로 물려주고 있다는 걸 발견 → 새로 띄우는 대화형 `claude.exe`가 "나는 독립된 최상위 세션이 아니라 기존 세션 밑에 있는 무언가"로 오인했을 가능성을 의심.
3. 그런데 1번과 같은 방식(같은 오염된 환경)의 헤드리스 호출은 멀쩡히 동작했다 — 그래서 환경변수 오염이 **유일한** 원인은 아니라는 것도 같이 확인됨. 즉 진짜 차이는 "환경변수"도 "wt.exe로 띄우는 것"도 아니라 **"진짜 대화형 모드(`-p` 없음) 자체"**로 좁혀졌다.
4. 여기서부터는 사람의 실제 키 입력이 있어야 재현되는 영역이라(OS 레벨 키 입력 자동화는 안전상 스스로 막았다), 사용자에게 직접 짧게 테스트해달라고 요청했다.
5. 그 전에 방어적으로 `manualRun.ts`의 `wt.exe` spawn에서 `CLAUDE_CODE_*`/`CLAUDECODE*`/`CLAUDE_PID`/`CLAUDE_EFFORT` 환경변수를 제거하는 수정을 미리 적용해뒀다(대화형 세션은 항상 완전히 독립적인 최상위 세션이어야 하므로, 3번에서 "유일한 원인은 아님"이 확인됐어도 여전히 옳은 방어 조치라 유지). VS Code 통합 터미널 방식으로 바꾸면서 이 제거 로직은 `runner.ts`의 `sanitizeClaudeSessionEnv()`로 옮겨서 `code` 프로세스 spawn(`tryOpenVsCode`)에도 그대로 적용한다 — VS Code가 아직 안 떠 있는 상태에서 `code` CLI가 새 VS Code 프로세스를 직접 띄우는 경우, 그 오염된 env가 통합 터미널의 자식 프로세스(claude.exe)에까지 전달될 수 있기 때문이다.
6. **사용자가 실제로 대시보드에서 시작 → 한 마디 타이핑 → 엔터를 처봤고, 이번엔 트랜스크립트가 정상 생성되고 실시간 토큰(13,093)까지 정확히 잡혔다.**

**정직하게 남겨야 할 부분**: 5번 수정 이후 첫 실제 테스트가 성공한 것이지, "수정 전 vs 수정 후"를 사람이 직접 타이핑하는 동일 조건에서 A/B로 비교한 건 아니다(그러려면 매번 사람이 실제로 타이핑해야 해서 못 함). 그래서 이 환경변수 수정이 **진짜 원인**이었는지, 아니면 다른 요인(예: 우연히 이번엔 사람이 trust 프롬프트에 정상적으로 응답했다든가)이 같이 작용했는지는 100% 확정은 아니다. 다만 이후에도 계속 재현되는지는 지켜봐야 한다 — 만약 나중에 또 0으로 나오는 사례가 생기면 이 섹션부터 다시 봐야 한다.

## 토큰/시간 하드컷의 정확도 (실측 검증됨 — 처음엔 의심했지만 신뢰할 만하다고 결론)

대화형 모드는 `--output-format stream-json`을 못 쓰므로(그 옵션은 `--print` 전용) 세션 트랜스크립트 파일(`~/.claude/projects/<슬러그>/<session_id>.jsonl`, [cli-spec.md](./cli-spec.md) 참고)을 폴링해서 토큰을 추정한다. 집계 로직은 `message.id` 기준으로 턴 하나를 딱 한 번만 집계한다(트랜스크립트는 한 턴이 콘텐츠 블록마다 여러 줄로 쪼개져 나오고 usage가 반복되기 때문 — `cli-spec.md`의 경고와 동일한 함정).

처음엔 이 방식이 "CLI 공식 값보다 37% 적게 나온다"는 의심이 있었지만, **그건 착오였다** — 완료된 run 여러 건(88,003 / 106,791 / 77,366 토큰)으로 교차검증한 결과 트랜스크립트 재계산 합계가 **CLI 공식 usage 합계와 정확히 일치**했다(착오의 실제 원인은 별개로 존재하던 auto 모드 실시간 진행률 표시 쪽의 사소한 버그였다). 그래도 대화형 세션은 애초에 공식 구조화 출력(`--output-format json`류) 자체가 없으므로, 화면/DB에는 계속 "하네스 추정치"로 표시한다(`harnessEstimateTokens`/`harnessEstimateElapsedMs`, `CLAUDE.md`의 "비용은 추정치다" 원칙과 같은 맥락).

## 토큰 하나로만 재던 걸 "토큰 + 비용" 두 축으로 분리 (2026-08-07, 실측 검증됨)

실사용 중 "Fable로 하는 거랑 Sonnet으로 하는 거랑 토큰이 똑같이 올라가는데, 모델마다 단가가 다르지 않냐"는 지적이 나왔다. 확인해보니 **집계가 모델도 토큰 종류도 전혀 구분하지 않고 있었다** — `input + output + cache_creation + cache_read`를 1:1로 더한 숫자 하나가 하드컷·대시보드·점수 전부의 유일한 근거였다.

먼저 짚어둘 사실: **토큰 개수가 모델마다 다른 게 아니다.** Fable 5 / Opus 5 / Sonnet 5는 전부 Opus 4.7에서 도입된 같은 토크나이저 계열이라 같은 텍스트면 토큰 수가 거의 같다. "토큰이 똑같이 올라간다"는 관찰은 버그가 아니라 정상이다. 실제로 벌어지는 건 **토큰당 단가**다:

| | input $/1M | output $/1M | Sonnet 5 대비 |
|---|---|---|---|
| Fable 5 / Mythos 5 | $10 | $50 | 3.33배 |
| Opus 5 (fast mode) | $10 | $50 | 3.33배 |
| Opus 5 / 4.8 / 4.7 / 4.6 | $5 | $25 | 1.67배 |
| Sonnet 5 / 4.6 / 4.5 | $3 | $15 | 1배(기준) |
| Haiku 4.5 | $1 | $5 | 0.33배 |

여기에 토큰 종류별 배수가 또 곱해진다: 캐시 읽기 = input×0.1, 5분 TTL 캐시 쓰기 = input×1.25, **1시간 TTL 캐시 쓰기 = input×2**. 즉 같은 모델 안에서도 종류를 뭉뚱그리면 최대 20배 차이가 뭉개진다.

**다행히 필요한 정보가 트랜스크립트에 전부 있었다**(실측 확인): assistant 줄의 `message.model`, `usage.speed`(`"fast"`면 fast mode 프리미엄 단가), 그리고 `usage.cache_creation.{ephemeral_5m_input_tokens, ephemeral_1h_input_tokens}`로 TTL까지 분리돼 나온다. 실측상 Claude Code CLI는 **1시간 TTL**을 쓰고 있었다 — 5분(1.25배)으로 뭉뚱그렸으면 캐시 쓰기 비용을 60% 과소평가했을 것이다.

**구현**: `parseTranscriptUsage`/`sumWorkspaceUsage`(이전 이름: `parseTranscriptTokenUsage`/`sumWorkspaceTokenUsage`)가 이제 `{ totalTokens, byModel, compactApproxTokens }`를 돌려준다. `byModel`의 키는 모델 id이며 fast mode 구간은 `<model>:fast`라는 별도 키로 잡힌다. 단가 테이블과 환산 로직은 `src/lib/pricing.ts`에 따로 뒀다.

**결정된 적용 범위**(사용자 판단, 2026-08-07):

- **하드컷은 토큰 그대로.** `maxTokens`는 실제로 4단계를 끝까지 돌려 실측으로 잡은 값이라, 기준을 비용으로 바꾸면 `problems/*.json`을 전부 재산정해야 하고 과거 run과의 비교도 끊긴다. `totalTokens` 계산식은 **한 글자도 안 바꿨다**.
- **표시는 두 축 병기.** 대시보드 실시간 진행률/이력 표/상세 페이지 전부 토큰 옆에 비용과 모델 요약(`opus-5 + sonnet-5`)을 같이 보여준다.
- **점수는 비용 정규화.** 종합 점수의 토큰효율 30%는 이제 `실제 토큰 × 비용 배율`을 기준선과 비교한다([evaluation.md](./evaluation.md) 참고).

**저장 형태**: `Run.harnessEstimateUsageByModel`(Json)이 원자료이고 `harnessEstimateCostUsd`는 스냅샷이다. 화면에서는 원자료에 **현재** 단가 테이블을 다시 곱하므로, `pricing.ts`에 새 모델을 추가하면 과거 run도 소급해서 제대로 계산된다. 단가 테이블에 없는 모델이 섞이면 조용히 0원 처리하지 않고 `unpricedModels`로 표시해서 "그 비용은 하한값"임을 화면에 밝힌다.

**비용은 실청구액이 아니다.** 구독 로그인(OAuth)으로 돌리므로 실제 청구는 발생하지 않는다 — 이 USD는 "같은 작업을 API 종량제로 돌렸다면"의 정가 환산치이며, 모델 간 소비를 공정하게 비교하기 위한 척도다. Sonnet 5의 인트로 단가($2/$10, 2026-08-31까지)는 일부러 안 쓴다: 날짜에 따라 단가가 바뀌면 러너가 시계를 보고 분기해야 하고("러너는 멍청하게" 위배) 같은 run을 나중에 다시 열었을 때 값이 달라진다.

**실측 검증**: 트랜스크립트가 남아있는 과거 manual run 14건에 대해 옛 계산식과 새 계산식을 **같은 파일에 나란히** 돌려 비교했다 — 14건 전부 `옛 계산식 == 새 계산식 == 모델별 분해의 합`으로 정확히 일치했다(하드컷 기준 불변 + TTL 분배에서 토큰이 새거나 중복되지 않음이 확인됨). 참고로 DB에 저장된 값과는 2건이 달랐는데 둘 다 이 변경과 무관한 기존 현상이다: 하나는 "완료" 후에도 사람이 세션을 계속 써서 트랜스크립트가 더 자란 경우(`completeManualRun`은 claude.exe를 안 죽인다), 다른 하나는 차이가 정확히 `compactApproxTokens`(41,690)여서 `/compact` 가산 기능(2026-08-06) 이전에 저장된 run이다.

**남은 한계**: `/compact`의 `preTokens` 근사치는 모델 정보가 없어서 **직전 assistant turn의 모델에 귀속**시키고, **캐시 읽기 단가**(input×0.1)로 환산한다. `/compact`는 직전까지의 대화를 다시 읽는 호출이고 그 대화는 이미 캐시에 올라가 있다는 근거지만(실측상 이 세션들은 cache_read가 cache_creation을 압도한다), 추정 위에 얹은 또 하나의 가정이다. 정가 input으로 쳤다면 비용이 10배 부풀어서, 하필 "컨텍스트 관리를 잘 하면 이득"을 측정하려는 `inventory-digest-staged`에서 `/compact`를 쓰는 게 손해처럼 보이는 정반대 왜곡이 생긴다. 이 값이 집계에 얼마나 섞였는지는 `compactApproxTokens`로 따로 노출해서 상세 화면에 밝힌다.

## `/clear`를 쓰면 토큰 집계가 멈추던 버그 (실측으로 발견 → 수정)

실사용 중 "`/clear`를 하고 나면 더 이상 토큰이 안 늘어난다"는 문제가 보고됐다. 원인을 실제 트랜스크립트 디렉터리로 확인했다: 사람이 세션 중 `/clear`를 입력하면 Claude Code CLI는 **기존 세션 파일에 이어쓰지 않고, 같은 프로젝트 디렉터리 안에 `--session-id`로 지정한 원래 runId와 무관한 새 sessionId로 완전히 새 `.jsonl` 파일을 만든다.** 실측: 워크스페이스 하나의 프로젝트 디렉터리 안에 서로 다른 sessionId의 `.jsonl` 3개(최초 세션 1개 + `/clear` 2번)가 순서대로 쌓여 있었다.

기존 구현(`computeTranscriptPath`)은 시작 시점에 `runId`로 계산한 파일 **하나만** 계속 폴링했다 — 그래서 `/clear` 이후 새로 생기는 파일의 사용량은 전혀 안 잡히고, 집계값이 `/clear` 시점에서 그대로 멈춰버렸다. 실측 수치로 확인: 첫 파일 143,616 토큰에서 멈췄지만, 그 뒤 `/clear` 두 번을 거치며 실제로는 140,684 + 166,531 = 307,215 토큰을 더 썼다(전체 450,831 토큰 중 68%가 안 잡히고 있었다).

이건 단순 부정확함이 아니라 `/clear`로 `maxTokens` 하드컷 자체를 우회할 수 있다는 뜻이라 `CLAUDE.md`의 "토큰/시간 한도는 하드컷이다... 유예 없음" 원칙에 정면으로 위배되는 버그였다.

**수정**: 파일 하나가 아니라 **워크스페이스에 대응하는 프로젝트 디렉터리 전체**(그 안의 `.jsonl` 전부)를 폴링마다 다시 나열해서 합산하도록 바꿨다(`manualRun.ts`의 `sumWorkspaceUsage`, `computeTranscriptPath`는 제거). 워크스페이스 경로 자체가 실행마다 새로 생성되는 고유 디렉터리라서(`CLAUDE.md`의 "실행은 항상 격리한다"), 그 프로젝트 디렉터리에 생기는 `.jsonl`은 `/clear`를 몇 번 하든 전부 이 run에 속한다고 안전하게 볼 수 있다. 파일마다 `message.id`가 독립적인 랜덤 uuid라 파일 간 충돌 없이 그냥 더하면 된다. 위 실측 데이터(3개 파일, 450,831 토큰)로 수정 후 값이 정확히 일치하는 것까지 확인했다.

이 수정은 `inventory-digest-staged` 문제([problem-set.md](./problem-set.md)의 "컨텍스트 관리 트랩" 섹션)의 측정 전제와도 직결된다 — `/clear`가 토큰 집계를 멈춰버리면 그 문제의 하드컷 트랩 자체가 무력화되기 때문이다.

## 새 터미널을 수동으로 열면 가짜 홈이 안 먹히던 버그 (실측으로 발견 → 수정)

실사용 중 "터미널을 하나 더 만들어서 명령하니깐 토큰 소모가 안 올라갔어"라는 증상이 보고됐다. 원인: `writeVsCodeAutoRunTask()`가 심는 `options.env`(USERPROFILE/HOME을 가짜 홈으로 오버라이드)는 그 특정 태스크 인스턴스(자동 태스크 터미널)에만 적용된다 — 사람이 VS Code에서 자동 태스크 터미널 말고 새 터미널을 하나 더 열어서 거기서 `claude`를 실행하면, 그 터미널은 이 오버라이드를 상속받지 않고 이 컴퓨터의 진짜 `USERPROFILE`/`HOME`으로 뜬다. 그러면 (1) 그 세션의 트랜스크립트가 진짜 홈 밑 `~/.claude/projects/<slug>/`에 쌓이는데 `sumWorkspaceUsage`는 가짜 홈 기준 디렉터리만 보므로 그 세션의 토큰이 전혀 집계되지 않고, (2) 그 세션이 이 컴퓨터의 진짜 전역 CLAUDE.md/hooks/MCP/skills/agents를 그대로 읽어버려서 원래 막으려던 오염이 새 터미널을 통해 우회된다.

**수정**: `.vscode/settings.json`에 `"terminal.integrated.env.windows"`를 같이 심어서, 이 워크스페이스 폴더 안에서 뜨는 모든 터미널(자동 태스크든 사람이 수동으로 연 터미널이든)이 같은 가짜 홈을 상속받게 했다(`manualRun.ts`의 `writeVsCodeAutoRunTask`). cwd가 같으므로 slug도 같고, 홈도 같은 가짜 홈이라 `sumWorkspaceUsage`가 두 세션의 `.jsonl`을 전부 찾아서 합산한다(파일별 `message.id`가 독립적이라 그냥 더하면 된다는 기존 근거가 여러 세션 동시 실행에도 그대로 유효하다). 태스크의 `options.env`와 값이 완전히 동일해서 두 설정이 동시에 적용돼도 충돌은 없다.

## 수동으로 연 터미널만 도구 세트가 통째로 달랐던 버그 (2026-08-14, 실측으로 발견 → 수정)

바로 위 "가짜 홈" 버그와 **같은 뿌리의 두 번째 누출**이다. 가짜 홈/텔레메트리는 `terminal.integrated.env.windows`로 새 터미널까지 덮었지만, **도구 제한은 env가 아니라 CLI 플래그로 걸려 있었다** — `tasks.json`이 붙이는 `--tools/--allowedTools/--strict-mcp-config`는 자동 태스크 세션에만 적용되고, 사람이 새 터미널을 열어 `claude`를 그냥 치면 그 플래그가 하나도 안 붙는다.

- **증상(실사용자 보고)**: 세션을 분리했더니 `/context`의 tools가 자동 시작 세션에서는 9.4k인데 수동으로 연 터미널에서는 30k.
- **실측 확인**: 같은 빈 프롬프트(`-p "say ok"`, 가짜 홈 격리 동일)를 두 조건으로 돌려 프롬프트 프리픽스 크기를 쟀다 — 제한 세트 **16,326토큰** vs 기본 세트 **29,504토큰**. 같은 문제를 푸는데 세션마다 **시작 컨텍스트가 1.8배** 차이 난다. 게다가 `--strict-mcp-config`도 빠지니 워크스페이스 `.mcp.json` 경로도 열린다.
- **왜 심각한가**: 세션을 나누는 것 자체가 이 벤치마크가 측정하려는 숙련 행동이다(`handover-relay-staged`는 아예 그걸 재려고 만든 문제다). "나누면 조건이 바뀐다"면 효율 축 비교가 성립하지 않는다 — 나눈 사람만 매 턴 13k 토큰의 도구 정의를 더 이고 다니게 되므로, 측정 대상이 아닌 이유로 결과가 갈린다.

**수정: run 전용 PATH 심(shim)** (`manualRun.ts`의 `createClaudeShimDir` / `workspaceSessionEnv`). 가짜 홈 밑(`<fakeHome>/bin`, 워크스페이스 **밖**이라 참가자 파일 트리·채점 diff에 안 섞인다)에 `claude.cmd`(cmd/PowerShell용)와 `claude`(확장자 없음, Git Bash는 PATHEXT를 안 쓴다)를 만들어 자동 태스크와 **완전히 같은 플래그**로 진짜 `claude.exe`를 대신 실행하게 하고, `terminal.integrated.env.windows`의 `PATH`를 `<shimDir>;${env:PATH}`로 심어 이 폴더의 모든 터미널이 심을 먼저 잡게 했다.

- `--session-id`는 심에 **일부러 안 넣는다** — 자동 태스크 세션이 이미 그 UUID를 점유하고 있어 충돌한다. 대신 `--name vibecheck-<runId>`로 runId를 CommandLine에 남긴다(프로세스 매칭은 원래 CommandLine의 runId 포함 여부라 그대로 동작한다).
- ⚠️ **PATH는 `terminal.integrated.env.windows`에만 넣고 tasks.json의 `options.env`에는 절대 넣지 마라(첫 시도에서 실행 자체가 깨졌다).** `${env:PATH}` 치환은 두 자리에서 동작이 다르다 — 터미널 설정에서는 정상 치환되지만 tasks.json의 `options.env`에서는 치환되지 않아 PATH가 리터럴 `"...;${env:PATH}"`로 굳는다. 그러면 태스크가 `claude.exe`를 PATH에서 못 찾아 워크스페이스 상대경로로 떨어지고 `Path to shell executable "...\<workspace>\claude.exe" does not exist`로 세션이 아예 안 뜬다. 애초에 자동 태스크는 심이 필요 없다(플래그를 직접 다 붙인다) — 그래서 태스크 env에는 PATH를 안 주고, `command`를 진짜 exe **절대경로**(`resolveRealClaudeExe()`)로 박아 PATH 의존 자체를 없앴다.
- **실측 검증**: ① 심으로 띄운 세션의 프롬프트 프리픽스가 제한 세트 세션과 **캐시 히트로 정확히 일치**(cache_read 16,326 = 제한 세트 쪽 cache_creation) → 바이트 단위로 같은 조건. ② 심을 통해 뜬 `claude.exe`의 CommandLine에 `vibecheck-<runId>`가 남는 것 확인. ③ `${env:PATH}`가 VS Code 터미널에서 실제로 치환되는지 확인(실제 VS Code 창에서 folderOpen 태스크로 `$env:PATH`를 덤프 — 심 디렉터리가 맨 앞, 기존 20개 엔트리 전부 보존, 리터럴 `${env:PATH}` 잔존 없음). ④ 생성 파일 정합성 20개 체크(`scripts/verify-terminal-shim.ts`). ⑤ **실제 VS Code 창을 열어 자동 태스크가 진짜로 claude.exe를 띄우는 것까지 확인**(`scripts/verify-autotask-launch.ts`) — 위 PATH 사고를 ④가 못 잡았기 때문에 추가한 검증이다. 생성 파일이 그럴듯해도 VS Code가 실제로 실행에 성공하는지는 띄워봐야만 안다.

**같이 고친 것 — 세션을 나누면 추적이 아예 끊기던 문제.** 위 조사 중 발견했다. `pollOnce`가 "추적하던 PID가 죽음 = 세션 종료"로 보고 그 자리에서 폴링을 멈추고 값을 얼렸다. 그런데 세션 분리는 "1번 세션 종료 → 새 터미널 → 2번 세션 시작"이라, 그 공백에서 run이 끝난 것으로 확정돼 **이후 세션의 사용량이 진행률에도 하드컷에도 전혀 안 잡혔다**(`/clear` 버그와 같은 종류의 하드컷 누출).

- 이제 추적 PID가 사라지면 먼저 같은 run의 다른 `claude.exe`(CommandLine에 runId)로 **추적을 넘기고**, 아무것도 없으면 `EXIT_GRACE_MS`(3분) 동안 새 세션이 뜨는지 기다린다. 유예가 끝나면 **사라진 그 시점의 스냅샷으로** 얼린다 — 기다린 시간이 소요 시간에 섞이면 시간 감점이 왜곡되기 때문. 유예 중에는 하드컷 판정을 건너뛴다(멈춰 있는 시간으로 시간 한도에 걸리게 하면 안 된다).
- 강제 종료도 추적 중인 하나가 아니라 **이 run에 속한 전부**를 죽인다(`killAllClaudeProcessesForRun`). 하나만 죽이면 하드컷 발동 후에도 나머지 세션이 계속 예산을 태운다. 매칭 기준은 여전히 CommandLine의 runId라 사람의 다른 claude.exe는 절대 안 건드린다.

## `/compact` 비용이 트랜스크립트에 안 잡히던 문제 → 근사치 가산으로 결정 (2026-08-06)

`/clear`와 별개로 `/compact`도 실측해보니 다른 방식으로 새는 게 확인됐다. 오늘 실사용된 `inventory-digest-staged` run의 진짜 트랜스크립트(사람이 `/compact`를 실행한 세션)를 직접 열어보면 다음 순서로 기록된다:

1. `{"type":"user","message":{"content":"/compact"}}`
2. `{"type":"system","subtype":"compact_boundary","compactMetadata":{"trigger":"manual","preTokens":41690,"postTokens":5686,"cumulativeDroppedTokens":36004,"durationMs":81769,...}}` — **필드명은 camelCase**(온디스크 트랜스크립트 실측 기준).
3. `{"type":"user","isCompactSummary":true,"message":{"content":"<요약문>"}}` (usage 필드 없음)

이 셋 중 어디에도 `message.usage`가 있는 `type: "assistant"` 줄이 없다 — 즉 압축 자체가 실제로 소비한 API 호출 비용(입력/출력/캐시 토큰)이 기존 assistant 집계 로직으로는 전혀 안 잡혔다.

별도의 통제된 라이브 실험(`claude -p "/compact" --resume <sessionId> --output-format stream-json --verbose`, 헤드리스 모드, 임시 격리 홈)으로 공식 값의 존재 자체는 확인했다 — 최종 `result` 줄의 `modelUsage`에 진짜 API 호출 결과가 찍힌다: `{"claude-haiku-4-5":{"inputTokens":2096,"outputTokens":1166,"cacheReadInputTokens":28868,"cacheCreationInputTokens":600,"costUSD":0.0116}}`(합계 32,730). 하지만 이 값은 **`--print` 모드에서만 stdout에 한 번 찍히고 사라지며, 온디스크 세션 트랜스크립트(.jsonl)에는 전혀 저장되지 않는다**(grep으로 직접 확인, 0건). 우리 하네스는 대화형(`--print` 아님) 세션의 온디스크 트랜스크립트만 폴링하므로 이 공식 값 자체에는 접근할 방법이 원천적으로 없다.

같은 헤드리스 실험에서 `compact_boundary` 이벤트도 관찰됐는데(단 `--output-format stream-json` 변환을 거쳐 필드명이 snake_case: `compact_metadata.pre_tokens=30468`), 그 값을 실제 `modelUsage` 합계(32,730)와 비교하면 **약 7% 낮게(93% 수준으로) 근사한다** — 완벽하진 않지만 근거 있는 근사치임을 확인했다.

**사용자 결정**: "① 이 갭을 문서화만 하고 둘지 ② `preTokens`를 근사치로 추정 합계에 더할지" 확인한 결과 ②를 선택했다 — 완전히 안 잡는 것보단 근사치라도 반영하는 게 낫다는 판단. `CLAUDE.md`의 "러너는 멍청하게 — 휴리스틱 넣지 마라" 원칙에서 벗어나는 의도적 예외이지만, 공식 값이 온디스크로는 원천적으로 접근 불가능하다는 게 실측으로 확인된 상황이라 예외를 뒀다.

**구현**(`manualRun.ts`의 `parseTranscriptTokenUsage`): `type === "system" && subtype === "compact_boundary"`인 줄의 `event.compactMetadata?.preTokens`(camelCase — `--print` 모드의 snake_case 변환형과 헷갈리지 말 것)를 assistant usage 합계에 그대로 가산한다. `system` 타입이라 기존 `message.id` dedup과 안 겹치므로 그냥 더한다 — 같은 파일에 `/compact`가 여러 번 있으면 그때마다의 `preTokens`를 전부 더한다(각 압축 시점의 컨텍스트 크기이므로 중복 아님). 값이 없거나 숫자가 아니면 0으로 방어.

**검증**: 위 실사용 run의 실제 트랜스크립트로 직접 계산해서 확인함 — 수정 전(assistant-only) 합계 718,601 + `compact_boundary`의 `preTokens`(41,690) = 760,291, 수정된 `parseTranscriptTokenUsage()`가 반환한 값과 정확히 일치.

종류별(input/output/`ephemeral_1h` 캐시쓰기/캐시읽기)로도 전부 일치했다. 즉 `pricing.ts`의 단가표·캐시 배수(읽기 0.1배, 1시간 쓰기 2배)가 **CLI 자체 계산식과 동일**하다는 게 확인됐다. (부수 확인: CLI도 Sonnet 5를 인트로가 $2/$10가 아니라 정가 $3/$15로 계산한다 — 정가를 쓰기로 한 기존 결정과 일치.)

콘텍스트 누적도 정확히 반영된다. Opus run의 턴별 실측: `cacheRead`가 20,587 → 33,971로 매 턴 커지고 그 전액이 매 턴 다시 과금되며, 대화 자체는 34k인데 10턴 누적이 320,180이 된다. 우리 집계가 턴마다 전부 더하므로 실제 과금 방식과 같다.

### 그런데 트랜스크립트에 아예 안 남는 호출이 있다

같은 세션의 CLI 공식 `modelUsage`에는 **`claude-haiku-4-5-20251001`이 588 in / 15 out, $0.000663**으로 잡히는데, 온디스크 `.jsonl`에는 결과 텍스트(`type:"ai-title"`)만 남고 `usage`가 없다. `system:away_summary`(자리 비움 리캡)도 마찬가지 — 크기조차 알 수 없다. `/compact`도 같은 종류의 문제로 위 섹션처럼 근사치를 쓰고 있었다.

규모는 짧은 세션에서 토큰 0.2% / 비용 0.35% 수준이라 하드컷을 뒤집을 정도는 아니지만, 방향이 항상 **과소집계**라 하드컷을 느슨하게 만드는 쪽이다.

### 해결: CLI가 스스로 보고하게 한다

Claude Code는 OpenTelemetry로 자기가 계산한 사용량을 내보낸다([monitoring-usage 문서](https://code.claude.com/docs/en/monitoring-usage)). 이걸 대시보드 서버가 직접 받는다.

**실측으로 확인한 프로토콜 세부사항** (`src/lib/telemetry.ts`가 의존하는 전제들):

1. `OTEL_EXPORTER_OTLP_PROTOCOL=http/json`이면 `OTEL_EXPORTER_OTLP_ENDPOINT` 뒤에 **`/v1/metrics`를 스스로 붙여** POST한다 → 라우트를 `src/app/api/otel/v1/metrics/route.ts`에 두고 엔드포인트로는 `.../api/otel`만 준다.
2. **`aggregationTemporality: 1` = DELTA.** 각 페이로드는 직전 export 이후의 증분만 담는다 — **전부 더해야** 총합이 된다. (마지막 페이로드만 쓰면 87,838 / 실제 253,746. 여기서 틀리면 조용히 3배 과소집계된다.)
3. run 귀속은 `OTEL_RESOURCE_ATTRIBUTES=vibecheck.run_id=<runId>`로 넘긴 커스텀 리소스 속성이 그대로 실려온다. `--session-id`와 무관하게 동작하므로 **사람이 `/clear`를 해도 귀속이 안 깨진다** — 트랜스크립트 폴링이 `/clear`로 겪었던 함정(아래 섹션)을 구조적으로 피한다.
4. 모델 ID는 날짜가 붙어 올 수 있다(실측: `claude-haiku-4-5-20251001`). 비용은 CLI가 계산해서 보내주므로 우리 단가표를 다시 곱하지 않는다 — **단가표에 없는 신모델이 0원으로 새어나가는 사고가 구조적으로 불가능**해진다.
5. 토큰 종류는 `input`/`output`/`cacheRead`/`cacheCreation` 네 가지. **`cacheCreation`은 5분/1시간 TTL로 쪼개져 오지 않는다** — 비용을 우리가 곱하지 않으므로 영향은 없고, 화면 분해 표시용으로만 1시간 버킷에 넣는다.
6. 기본 export 주기는 60초라 하드컷이 최대 1분 늦게 발동한다 → `OTEL_METRIC_EXPORT_INTERVAL=5000`으로 줄였다.

**검증 결과**: 같은 헤드리스 세션에서 OTel 합계와 CLI 공식 `result` JSON이 **모델별로 토큰 0 차이, 비용 0 차이**로 일치했고, 트랜스크립트가 놓치던 haiku 배경 호출(603토큰/$0.000663)도 그대로 잡혔다. 실제로 claude.exe가 보낸 페이로드 7개를 그대로 `telemetry.ts`에 흘려 재검증했고(토큰 0 차이, 비용 차이 2.8e-17), 그 페이로드를 실제 dev 서버의 `/api/otel/v1/metrics`에 POST해서 7건 전부 200을 확인했다. `startManualRun()`이 생성하는 `.vscode/tasks.json`과 `settings.json` 양쪽에 필요한 env가 전부 박히는 것도 실제 생성물로 확인했다.

**폴백**: 텔레메트리가 안 붙으면(구버전 CLI, 포트 불일치 등) 기존 트랜스크립트 집계로 자동 폴백한다. 둘 다 계산해서 **비용이 큰 쪽을 통째로** 쓴다 — 텔레메트리가 정상이면 배경 호출까지 포함하므로 항상 크거나 같고, 트랜스크립트가 더 크게 나오는 경우는 export 주기(5초)만큼 뒤처졌거나 텔레메트리가 끊긴 것뿐이다. 작은 쪽을 쓰면 하드컷이 느슨해지므로(=`/clear` 버그와 같은 종류의 실수) 큰 쪽을 쓴다. 항목별 max가 아니라 통째로 고르는 이유는 소스를 섞으면 화면에 앞뒤 안 맞는 숫자 조합이 나오기 때문. 어느 쪽을 썼는지는 `Run.harnessEstimateSource`에 저장하고 화면에도 밝힌다. (비교 축이 토큰이 아니라 비용인 이유는 아래 "폴백 선택 축..." 섹션 참고 — 2026-08-12에 고쳤다.)

**아직 검증 못 한 것(정직하게)**: 위 검증은 전부 헤드리스 세션과 실제 생성된 설정 파일 기준이다. **VS Code 통합 터미널로 뜬 대화형 세션에서 실제로 메트릭이 도착하는지, 비용 하드컷이 라이브에서 발동하는지는 아직 안 봤다** — 사람이 실제로 타이핑을 해야 토큰이 발생하기 때문이다(세션은 빈 채로 열리므로 아무도 안 건드리면 API 호출 자체가 없다). 다음 실사용 run에서 대시보드에 "CLI가 직접 보고한 값"이라고 표시되는지 확인할 것.

## 폴백 선택 축과 캐시 TTL 가정 — 하드컷을 느슨하게 만들던 것 2건 (2026-08-12, 소급 검증됨)

"KV 캐시 히트 할인까지 반영돼 있나"를 점검하다가 나왔다. **할인 자체는 두 경로 모두 정확했다** — 텔레메트리 경로는 비용을 CLI가 계산해서 보내므로 애초에 우리가 곱할 게 없고, 트랜스크립트 폴백의 배수(캐시 읽기 0.1배 / 5분 쓰기 1.25배 / 1시간 쓰기 2배)도 공식 단가 체계와 일치했다. 롱컨텍스트 프리미엄도 확인했는데 **현행 모델은 1M 컨텍스트가 표준 단가라 200K 초과 배수가 없다** — 안 넣은 게 맞다. 문제는 그 주변 두 곳이었고, 둘 다 하드컷이 **느슨해지는** 방향이었다.

**① 폴백 선택 축이 하드컷 축과 달랐다** (`manualRun.ts`의 `collectUsage`). 하드컷은 비용(`maxCostUsd`)으로 거는데 텔레메트리/트랜스크립트 선택은 `totalTokens`로 하고 있었다. 이 둘은 같은 축이 아니다 — **캐시 읽기는 토큰당 비용이 input의 0.1배**라, 캐시 히트가 많은 쪽은 토큰이 더 큰데 비용은 더 작을 수 있다. 즉 "토큰이 큰 쪽"을 고르면서 실제로는 "비용이 작은 쪽"을 집어드는 조합이 성립했고, 그 순간 원래 막으려던 상황이 그대로 벌어진다. 실제로 성립하는 경로가 셋 있었다: (a) 텔레메트리가 export 주기(5초)만큼 뒤처진 순간, (b) 트랜스크립트 쪽에만 더해지는 `/compact` 근사치(`preTokens`)는 토큰을 크게 밀어올리면서 비용은 캐시 읽기 단가로 환산돼 거의 안 올린다, (c) Sonnet 5처럼 CLI가 인트로 단가를 쓰는 모델이면 두 경로의 단가 자체가 다르다. **비용 기준 비교로 바꿨다**(동점이면 텔레메트리 — CLI 공식 값이고 배경 호출까지 포함하므로).

**② 캐시 쓰기 TTL 미분류 잔여분을 싼 쪽으로 넣고 있었다** (`parseTranscriptUsage`). `cache_creation` 객체가 없거나 TTL별 합이 총계와 안 맞을 때 남는 만큼을 5분 버킷(1.25배)에 넣으면서 주석에는 "비용을 과대평가하지 않는다"고 적어놨는데, **이 값은 하드컷의 입력이라 위험한 방향은 과대평가가 아니라 과소평가다.** 게다가 실측상 CLI는 1시간 TTL을 쓰므로 근거도 없이 37.5% 싸게 잡는 것이었다. **1시간 버킷(2배)으로 바꿨다** — TTL을 모를 때 비싼 쪽으로 가정하는 게 하드컷 원칙에도 맞고 실측 기준으로도 정확하다.

**소급 검증**(`scripts/verify-2026-08-12-cost-axis.ts`): 저장된 manual run 57건 중 모델별 원자료가 있는 18건에 새 계산식을 돌렸다. ②는 저장된 `cacheWrite5mTokens`가 **이미 옛 규칙으로 잔여분이 합쳐진 값**이라 사후에 "진짜 5분 토큰"과 "잔여분"을 구분할 수 없어서, **최악 가정**(저장된 5분 토큰이 전부 잔여분이었다고 보고 통째로 1시간 단가로 재계산)으로 상한을 잡았다. 결과는 **하드컷 판정이 뒤집힌 run 0건**. 그리고 부수적으로 확인된 사실 하나 — **18건 전부 5분 캐시 쓰기 토큰이 0이었다.** "CLI는 1h TTL을 쓴다"는 기존 실측이 저장 데이터로도 재확인됐고, 동시에 ②의 실제 소급 영향이 정확히 0이라는 뜻이다(영향 대상인 transcript 출처 run은 18건 중 2건뿐이기도 하다).

**①은 원리상 사후 재현이 불가능하다** — 저장된 run에는 채택된 한쪽만 남아있고 탈락한 쪽은 기록이 없다. 그래서 "과거에 실제로 잘못 골랐는가"는 확인할 수 없고, 확인한 건 "새 규칙으로 바꿔도 저장된 값과 판정이 안 바뀐다"까지다.

**검증 중 발견한 별개 사안(미수정)**: `completeManualRun()`은 최종 사용량을 freeze만 하고 **한도를 다시 검사하지 않는다.** 상태는 폴링이 이미 `disqualifyReason`을 세팅해둔 경우에만 `disqualified`가 된다. 즉 마지막 폴링(2.5초 간격, 텔레메트리는 5초 배치) 이후 "완료" 클릭 사이에 한도를 넘으면 초과분이 `completed`로 기록될 수 있다. 저장된 run 중에 이 경로로 새어나간 게 실제로 있는지는 확인 못 했다 — 현재 한도를 넘긴 채 `completed`인 `inventory-digest-staged` run이 몇 건 있지만, 전부 그 문제의 한도를 $0.7로 조이기 전(2026-08-10~11)에 돌아간 것들이고 오히려 **그 실측이 $0.7이라는 숫자의 근거였다**(`df1bb1c7` = $0.6171 ≈ CLAUDE.md의 "약 600,000 가중 토큰"). 과거 한도 값이 기록에 안 남아있어 당시 판정이 옳았는지는 사후 확인이 불가능하다.

## 세션을 끝내는 방법 — 자동 완료 / 포기 (2026-08-12)

예전에는 끝내는 길이 **"완료" 버튼 하나**였다. 단계형 문제에서 마지막 단계를 통과한 뒤에도 화면은
"이제 완료를 눌러라"라고 안내만 했고, 그 사이에도 세션은 계속 살아 있어서 토큰과 시간이 쌓였다
(안 누르고 두면 한도에 걸려 실격까지 갈 수 있었다). 그래서 둘로 나눴다:

| 경로 | 언제 | `Run.abandoned` |
|---|---|---|
| **자동 완료** | 단계형 문제에서 **마지막 단계를 통과한 순간** 프론트가 바로 complete를 호출 | `false` |
| **포기** | 사람이 "포기하기"를 누름 (단계형에서 사람이 누를 수 있는 유일한 종료 버튼) | `true` |
| **완료** | 단계가 없는 문제에서 사람이 "완료"를 누름 — 완료를 판정할 게이트가 없으므로 버튼을 남긴다 | `false` |
| 실격/자연 종료 | 폴링이 감지해 자동 호출(기존 그대로) | `false` |

**포기는 실격이 아니다.** `status`는 `completed` 그대로이고 **채점도 정상 수행한다** — 어디까지
갔는지가 점수로 남아야 하기 때문이다(못 푼 단계는 `hiddenTestsPath`가 이식하는 히든 테스트가 이미
실패시키므로, 일찍 그만두는 게 점수상 이득이 되지 않는다는 기존 설계가 그대로 작동한다).

**왜 `disqualifyReason`에 값을 추가하지 않았나**: 그 필드는 "`status`가 `disqualified`일 때만 값이
있다"는 불변식으로 쓰이고 있어서(`StatusBadge`의 렌더 조건 포함), `completed`인 run에 값을 넣으면
그 전제가 깨진다. 포기는 실격의 한 종류가 아니라 정상 종료의 한 종류라, `Run.abandoned` 불리언
칼럼을 따로 뒀다. 이력 표와 상세 화면에서는 "완료" 대신 중립 톤의 **"포기"** 배지로 구분한다.

> ⚠️ **이 칼럼은 `prisma migrate`가 아니라 `db push`로 넣었다.** `harnessEstimateSource`가 예전에
> 마이그레이션 없이 추가돼 있어서 마이그레이션 이력과 실제 DB 사이에 드리프트가 있고, 그 상태에서
> `prisma migrate dev`를 돌리면 **DB를 리셋해야 한다고 요구한다**(저장된 run 전부 소실). 추가 전용
> 변경이라 `db push`로 안전하게 넣었고, 실행 전에 `prisma/dev.db.bak-20260812`로 백업해뒀다.
> 앞으로도 이 DB에 스키마를 바꿀 때는 같은 이유로 `migrate dev`를 그냥 돌리면 안 된다.

## 단계 게이트에서 반복해서 막히던 것들 (2026-08-12, 실측)

게이트를 "결과물이 있으면 통과"까지 완화했는데도 실사용에서 두 번 더 막혔다. 둘 다 **산출물 내용은
맞는데 껍데기 때문에** 막힌 경우라, 이 문제가 재려는 축(컨텍스트 관리)과 아무 상관이 없었다.

| 증상 | 원인 | 조치 |
|---|---|---|
| 5단계에서 "결과물이 있는데 차단" | 산출물에 **UTF-8 BOM**(`EF BB BF`). Windows에서 PowerShell 리다이렉션/`Out-File`로 쓰면 기본으로 붙는다. `JSON.parse`가 내용을 보기도 전에 `SyntaxError`로 죽어서, 완화한 검사에 **도달조차 못 했다** | `_helpers.js`의 `readJson`/`runReport`에서 BOM을 벗겨낸다(`stripBom`) |
| 5단계에서 또 차단 | 산출물이 `{"violations": [...]}`로 **한 겹 감싸여** 있었다(프롬프트는 "id 배열로"). id 목록 자체는 정답과 완전히 일치했는데 "배열이 아니다"로 차단 | 게이트에서만 키가 하나뿐인 객체를 벗겨본다(`unwrapSingleKey`). 히든(채점)은 규격대로 본다 |

둘 다 회귀 테스트로 고정했다(`scripts/verify-inventory-gate-leniency.ts`, 64개 체크). 실제로 막혔던
워크스페이스 복사본에 수정본을 적용해 `차단 → 통과`로 바뀌는 것까지 확인했다.

**교훈**: 게이트를 "정확도를 안 본다"로 만들어도, **파싱/형태 단계에서 먼저 죽으면 완화가 무의미하다.**
새 문제의 게이트를 짤 때는 인코딩(BOM), 껍데기, 줄바꿈처럼 측정 축과 무관한 표현 차이를 먼저
흡수하고 나서 형태를 확인해라.

## 단계 건너뛰기 (2026-08-12)

위와 같은 일이 반복되자 **게이트를 아예 건너뛰는 버튼**을 넣었다(`manualRun.ts`의 `skipStage`,
`POST /api/runs/[id]/stage`에 `{ skip: true }`). 게이트 테스트를 돌리지 않고 다음 단계 리소스를 풀고
`currentStageIndex`만 올린다. 대시보드에서는 되돌릴 수 없는 동작이라 **페이지 안에서 확인을 한 번 받고**
(브라우저 기본 `confirm`은 세션 화면을 가려서 안 쓴다), 건너뛴 단계는 탭에 주황색 `!`로 표시된다.

**점수 우회 경로가 아니다.** 완료 시점에 `hiddenTestsPath`가 워크스페이스의 `tests/`를 전부 히든(정확도
검사)으로 덮어쓰고 그걸로 채점하므로, 건너뛴 단계의 산출물이 없거나 틀리면 `testPassed=false`가 되어
종합 점수가 79점 이하로 캡된다. 건너뛰기는 **진행만** 열어준다.

> **아직 안 한 것**: 건너뛴 단계 수를 DB에 기록하지는 않는다(`Run.abandoned`처럼 칼럼을 하나 더 두는
> 방식). 지금은 화면에서만 보이고 이력에는 안 남는다 — 점수에는 이미 반영되므로 급하진 않지만,
> "몇 단계를 건너뛰고 받은 점수인가"를 나중에 비교하려면 필요해진다.

## "다시 하기" (재시도)

실격되거나 만족스럽지 않게 끝난 run 뒤에, 대시보드의 "다시 하기" 버튼(`FinishedSummary`, `src/app/page.tsx`)을 누르면 **같은 문제**를 새 workspace로 다시 시작한다. 두 가지를 자동으로 처리한다:

- **이전 run의 claude.exe만 정확한 PID로 죽인다** — `manualRun.ts`의 `killClaudeProcessForRun(oldRunId)`. `completeManualRun()`은 원래 claude.exe를 안 죽이는데(사람이 터미널을 계속 보고 싶을 수 있어서), "다시 하기"는 사람이 명시적으로 "이건 이제 필요 없다"고 표시한 것이므로 여기서는 죽인다. best-effort라 이미 죽어있거나 PID를 못 찾았어도 재시도 자체를 막지 않는다.
- **VS Code는 새 창을 또 안 띄우고 `code -r`(마지막 활성 창 재사용)로 연다.** VS Code 창 자체를 프로세스로 찾아서 강제 종료하는 방식은 의도적으로 안 썼다 — 이 컴퓨터에서 VS Code는 대개 싱글 인스턴스로 여러 창이 하나의 백그라운드 프로세스에 묶여 있어서(위 "별도 터미널 창 대신..." 섹션 참고), 이름/커맨드라인 매칭으로 강제 종료하면 사람의 다른 무관한 VS Code 창까지 같이 죽을 위험이 있다. `-r`은 VS Code CLI가 공식 지원하는 플래그라 그 위험이 없다 — 마지막으로 활성화됐던 창의 내용만 새 워크스페이스로 바뀐다.

`POST /api/runs`에 `retryFromRunId`를 실어 보내면 이 두 동작이 트리거된다(`reuseWindow: true`가 `startManualRun`까지 그대로 전달됨). 일반 "시작" 버튼은 이 필드를 안 보내므로 항상 새 창을 띄우는 기존 동작 그대로다.

# 평가 기준

## run의 3가지 종료 상태

평가를 논하기 전에, run은 항상 다음 셋 중 하나로 끝난다:

| 상태 | 조건 | 평가 수행 여부 |
|---|---|---|
| **완료(completed)** | CLI가 정상적으로 끝까지 실행되고 `result`를 반환 | 자동 테스트 + LLM 채점 모두 수행 |
| **실격(disqualified)** | 문제별 `maxTokens`/`maxCostUsd`/`maxDurationMs`([problem-set.md](./problem-set.md)) 중 하나를 실행 도중 초과해서 러너가 강제 종료함 ([cli-spec.md](./cli-spec.md#실시간-토큰시간-한도-집행)) | **생략**. 미완성 코드로 테스트/채점을 돌려봐야 의미가 없다 |
| **실패(failed)** | 한도 초과가 아닌 다른 이유로 CLI가 비정상 종료(크래시, non-zero exit 등) | 생략(완료되지 않았으므로) |

실격과 실패는 둘 다 "완주하지 못함"이지만 원인이 다르므로 구분해서 기록한다: 실격은 우리가 정한 예산을 넘어서 우리가 죽인 것, 실패는 CLI/환경 쪽 문제다. 어느 쪽이든 그 시점까지의 워크스페이스 diff와 실행 로그는 디버깅용으로 보관한다([`benchmark-debugger`](../.claude/agents/benchmark-debugger.md), [`/check-run`](../.claude/skills/check-run/SKILL.md) 참고).

## 완료된 run의 평가

측정값은 두 축을 분리해서 기록한다 (하나의 점수로 뭉뚱그리지 않음):

- **효율성**: 소요 시간(wall-clock), 토큰 사용량(input/output/cache), 비용(`total_cost_usd`), 턴 수. 출처는 [cli-spec.md](./cli-spec.md)의 결과 JSON.
- **품질**:
  - **자동 테스트**: 문제에 정의된 테스트 명령(`problems/*.json`의 `testCommand`)을 워크스페이스에서 실행해 pass/fail, 통과율 계산.
  - **LLM 채점**: **OpenAI API**(벤치마크 대상 CLI 실행과는 완전히 별개 벤더/호출)로 최종 코드/diff + 문제별 루브릭(`problems/*.json`의 `rubric`)을 보내 품질 점수 산출 — 가독성, 요구사항 충족도, 엣지 케이스 처리 등 항목별 1~5점.

**단계형 문제(`problems/*.json`의 `stages`, [problem-set.md](./problem-set.md#단계형-문제-stages) 참고)의 자동 테스트**: 사람이 마지막 단계를 안 풀고 일찍 "완료"를 눌러도, 못 푼 단계의 테스트까지 전부 포함된 완전한 스펙 기준으로 채점되도록 `hiddenTestsPath`가 지정된 문제는 `testCommand` 실행 직전에 그 디렉터리 내용을 워크스페이스로 덮어쓴다(`evaluator.ts`의 `evaluateRun()`). 그렇지 않으면 일부러 쉬운 단계에서 멈추는 게 자동 테스트 통과율 점수상 이득이 돼버린다.

**채점자를 Claude가 아니라 OpenAI로 정한 이유:** 벤치마크 대상이 Claude Code CLI(Claude 모델)이므로, 채점자도 Claude면 "Claude가 Claude 결과를 채점"하는 구조가 된다 — self-preferencing bias(같은 계열 모델이 자기 계열 결과물을 더 후하게 평가하는 경향)가 알려진 문제라, 채점자는 벤치마크 대상과 다른 벤더로 분리한다. 이 결정 때문에 `.env`에 `OPENAI_API_KEY`가 별도로 필요하다.

대시보드에서는 두 축을 같이 보여주고, 필요하면 사용자가 가중치를 조정해 종합 순위를 볼 수 있게 한다(초기 버전에서는 필수 아님).

### 채점은 "어떻게 풀었는가"에 중립이어야 한다 (2026-08-11)

**원칙**: 하네스 기법(스킬/서브에이전트/문서/훅)은 이 프로젝트가 **측정하려는 대상**이지 **채점 항목**이 아니다. 문제를 스킬로 풀든, 라이브러리를 직접 다루든, 다른 언어를 쓰든 **결과가 같으면 점수도 같아야** 한다. 방법의 차이는 품질 축이 아니라 효율 축(시간/가중 토큰)에서 자연스럽게 드러나고, "실제로 어떤 방법을 썼는지"는 트랜스크립트/워크스페이스 diff로 **채점과 분리해서** 사후 관찰한다. 그래서 rubric 항목에 "스킬을 활용했는가" 같은 문구를 절대 넣지 않는다 — 넣는 순간 참가자에게 간접 힌트가 되기도 하고, 방법 자체에 점수를 주는 게 돼버린다.

#### 채점자 소스 수집이 방법에 따라 유불리를 만들던 문제 → 실사용 run으로 원인을 확정하고 수정

`report-xlsx-staged`를 실제로 두 번 돌린 결과(스킬 사용 / 미사용) **둘 다 히든 테스트를 전부 통과했는데 LLM 점수만 크게 갈렸다**(스킬 쪽이 6항목 중 4개에서 1점). 원인을 파보니 채점 품질 문제가 아니라 **채점자에게 무엇을 보여주느냐의 버그 3개**였다.

| # | 버그 | 실측 증상 |
|---|---|---|
| 1 | **바이너리를 텍스트로 덤프** — `readFileSync(f, "utf8")`는 바이너리에 예외를 안 던지고 깨진 문자열을 돌려준다. "바이너리는 건너뛴다"던 주석과 달리 산출물 `output/report.xlsx`가 통째로 실렸다 | 채점자가 *"결과 파일은 바이너리로만 첨부되어 있어 검증이 불가능합니다"* 라고 판단 |
| 2 | **덩치 큰 참고 자료가 예산을 독차지** — 순회 순서(경로순)대로 60,000자를 채운다 | 스킬을 설치하면 OOXML 스키마가 딸려온다(`sml.xsd` 246KB, `dml-main.xsd` 155KB, `.xsd` 총 25개) |
| 3 | **채점자가 이미 확정된 사실을 소스만 보고 다시 추측** | 히든 테스트 20/20 통과한 run인데 "수식 셀에 캐시값이 있는가"에 **1점**("셀 타입 처리가 불완전해 보인다") |

> **여기서 내가 한 번 잘못 고쳤다(기록용).** 2번을 보고 `.claude`를 `EXCLUDED_DIRS`에 넣었는데, 실제 run을 열어보니 **참가자의 산출물 자체가 거기 있었다** — `npx skills add`가 `.claude/skills/xlsx/`를 만들고 에이전트가 리포트 생성 스크립트(`build_report_step1~4.py`, 712~1,770바이트)를 그 스킬의 `scripts/` 옆에 썼다. 제외해버리니 채점자가 *"xlsx를 생성하는 실제 로직이 없고 결과물만 있습니다"*라며 1점을 줬다. **참가자가 산출물을 어디에 두는지는 방법마다 다르므로 경로로 넘겨짚으면 안 된다** — `.claude` 제외는 되돌렸다.

**최종 수정** (`src/lib/evaluator.ts`):

1. **바이너리 실제로 걸러내기** — 앞 8KB에 NUL 바이트가 있으면 건너뛰고 목록에만 "(바이너리)"로 남긴다.
2. **작은 파일부터 예산 채우기** — 경로가 아니라 크기순으로 담는다. 손으로 쓴 산출물은 작고 딸려온 자료는 크므로, **어디에 뒀든** 산출물이 먼저 들어간다(방법 중립적).
3. **파일 목록 전체를 맨 앞에 붙이기** — 내용이 잘려도 목록은 보이므로 "코드가 아예 없다"는 오판이 안 난다. 시스템 프롬프트에도 명시.
4. **`.xsd`/`.dtd`/`.pyc`/`.pyo`/`.map`/`.lock` 확장자 제외 + `__pycache__` 디렉터리 제외** — 어떤 문제에서도 참가자 산출물일 수 없다. 스키마는 작은 것도 수십 개라 크기순만으로는 개수로 예산을 갉아먹는다.
5. **파일당 상한 12,000자** — 한 파일이 예산을 독차지하지 못하게.
6. **자동 테스트 결과를 채점자에게 알려준다**(`judgeWithOpenAI`의 `testOutcome` 인자). 테스트를 통과했으면 "**테스트가 실제로 실행한 부분**은 확정된 사실이니 다시 의심하지 말고, 테스트가 안 닿는 영역은 직접 확인해서 판단해라"라고 지시한다(범위를 좁힌 이유는 바로 아래 2026-08-14 사고 참고).
7. 시스템 프롬프트에 **"언어/라이브러리/접근 방식 선택 자체는 채점 대상이 아니다 — 특정 스택을 선호하지 마라"** 추가.

**수정 효과(같은 워크스페이스에 실제 채점을 다시 돌려 확인)**: 스킬 미사용 4.00/5, 스킬 사용 3.25/5. 점수 차이가 **근거 있는 실질 차이**로 바뀌었다 — 스킬 쪽이 요약 시트의 카테고리 목록/정렬을 `CATEGORY_ORDER`에 하드코딩해서 "csv가 바뀌어도 다시 돌릴 수 있는가" 항목에서 감점됐고(테스트는 고정 csv를 쓰므로 못 잡는 진짜 결함이다), 미사용 쪽에 붙었던 근거 없는 1점은 사라졌다.

**여기서 얻은 규칙**: **rubric에는 자동 테스트가 이미 결정론적으로 검증하는 항목을 넣지 마라.** 겹치면 (a) 신호가 안 늘고 (b) 채점자가 확정된 사실을 뒤집는 오판만 는다. rubric은 테스트가 못 재는 것(재현성, 하드코딩 의존, 구조/가독성, 예외 처리)만 담는다 — `report-xlsx-staged`의 rubric도 그 기준으로 6개 → 4개로 다시 썼다.

> 이 변경은 저장된 과거 채점 결과를 자동으로 다시 계산하지 않는다(채점 결과는 run별로 저장된 값이다).

#### 반대 방향의 사고 — "테스트 통과"를 너무 넓게 말해서 채점자가 화면을 통과한 셈 쳤다 (2026-08-14)

위 6번 안내가 **"결과물이 사양대로 나온 건 확정된 사실"**이라고 산출물 **전체**를 가리키게 쓰여 있었다.
그런데 자동 테스트가 산출물의 **일부만** 실행하는 문제가 있다 — `calculator-web-staged`의 히든은
`calc.js`의 `evaluate()`만 돌리고 화면(`index.html`/UI 스크립트)은 한 줄도 실행하지 않는다.

**실측 사고(run c3f5bfff, 90점)**: 참가자 산출물의 이벤트 리스너 셀렉터가 `#pad`만 덮어서 `#sciPad`에
있던 **괄호·루트·로그·나머지 버튼이 전부 클릭 무반응**이었다. 그런데 `calc.js`는 정말 정확해서 히든
7/7 통과 → 채점자는 "테스트 전부 통과 = 사양대로 나옴"이라는 안내를 받고 화면 코드까지 통과한 셈 쳐서
관련 항목에 4점을 줬다. 최종 90점.

**수정**: 안내의 범위를 좁혔다 — "**테스트가 실제로 실행한 부분**만 확정이고, 루브릭 항목이 테스트가
안 닿는 영역(화면/DOM 상호작용, 이벤트 배선, 문서, 재현성)을 묻고 있다면 **소스에서 직접 확인해서**
판단하라". 같은 워크스페이스 재채점: rubric 평균 **86.7% → 80.0%**(점수로는 90 → 약 87).

**하지만 그걸로 충분하지 않다 — LLM 채점자는 이 종류의 버그를 못 잡는다(2회 실측).** rubric에
"이벤트 리스너 셀렉터가 화면의 모든 버튼을 덮는지 대조하라, 셀렉터 밖 버튼이 있으면 낮은 점수"라고
콕 집어 넣고 다시 채점해봤는데도 못 잡았고, 오히려 "괄호/루트/로그를 화면에서 입력 가능한가"에
**5점**을 줬다(사실은 전부 죽어있었다). 그래서 그 rubric 확장은 되돌렸다.

**결론: 화면이 실제로 동작하는지는 소스 읽기로 못 잰다 — 실행해서 재야 한다.** `calculator-web-staged`는
히든 테스트가 **설치된 Chrome(없으면 Edge)을 헤드리스로 띄워 버튼을 진짜로 클릭**하고 결과를 읽도록
바꿨다(`tests/chrome.js`, 의존성 0 — Node 24 내장 `fetch`/`WebSocket`으로 CDP를 직접 말한다).
전제 조건은 채점 머신에 Chrome/Edge가 있어야 한다는 것이고, 없으면 그 테스트는 조용히 넘어가지 않고
**명시적으로 실패**한다(조용히 건너뛰면 깨진 화면이 만점으로 통과해버린다).

> 이 방식은 **"어디를 눌러 어디를 읽는가"를 규약으로 못박아야** 성립한다(결과는 `#result`, 버튼은
> `data-key`). 마크업 구조·프레임워크·라벨·디자인은 여전히 자유다 — `evaluate()` 시그니처를 못박은
> 것과 같은 종류의 계약이고, 채팅 질문 안에 업무 언어로 넣는다.

#### 손도 안 댄 입력 파일이 참가자 점수를 깎던 문제 (2026-08-13)

위 수정으로도 안 잡힌 게 하나 더 있었다. **채점기가 참가자가 손도 안 댄 입력 파일을 읽고, 그 입력의 지저분함을 참가자 탓으로 감점했다.**

`handover-relay-staged`를 실제로 두 번 돌린 run에서 확인된 것 — 두 run 모두 `handover.md`(문제가 **일부러 뒤죽박죽으로 만든** 인수인계 문서) 앞부분 12,000자가 채점 프롬프트에 실렸고, 저장된 감점 사유가 그대로 남아 있다:

| rubric 항목 | 점수 | 저장된 사유 |
|---|---|---|
| 직무 분리 | **2** | *"handover.md 자체가 여러 직무 문구를 뒤섞어 서술하고 있어…"* |
| 가독성 | **3** | *"handover.md는 매우 장황하고 반복이 많아…"* |

입력의 성격이 참가자 점수가 되면 품질 축이 오염되고, **그 위에서 돌린 A/B는 믿을 수 없는 값이 된다.**

**수정**: `collectProvidedInputHashes(problem)` — `starterFiles` + 모든 `stages[].unlockPath` + `hiddenTestsPath`가 제공한 파일들의 sha256을 모아두고, 워크스페이스 파일이 **바이트 단위로 그것과 같으면** 채점 프롬프트에서 내용을 뺀다. 목록에는 `(제공된 입력, 변경 없음)`으로 남겨서 채점기가 존재는 알되 내용으론 채점하지 못하게 한다.

왜 이 규칙이 안전한가:

- **경로로 넘겨짚지 않는다** — 위 `.claude` 사고의 교훈 그대로다. "우리가 준 그대로인 파일"만 빼므로 방법에 중립적이다.
- **참가자 작업물은 원리상 안 빠진다** — 빠지려면 그 작업물이 우리가 준 파일과 바이트가 완전히 같아야 하는데, 그건 곧 "아무것도 안 고쳤다"는 뜻이라 채점에서 빠져도 잃는 정보가 없다(오히려 "변경 없음" 표기가 더 정확한 신호다).
- **히든 테스트도 뺀다** — `hiddenTestsPath`는 채점 직전에 워크스페이스를 덮어쓰므로 거기 있는 `tests/`는 참가자가 쓴 게 아니라 우리 파일이다. 실어봐야 기대값만 새어나가고 예산만 먹는다.

**회귀 확인** (`scripts/verify-judge-input-exclusion.mjs`, 저장된 워크스페이스 80개 전부):

- 제공한 적 없는 파일이 제외된 경우: **0건**
- **예산(60,000자)을 넘겨서 참가자 산출물이 잘리던 워크스페이스 30개가 예산 안으로 들어왔다** — 즉 이 버그는 감점 사유를 만들어냈을 뿐 아니라, 그동안 상당수 run에서 **산출물이 채점기에 아예 도달하지 못하게** 하고 있었다.
- 산출물처럼 보이는 파일이 제외된 3건(`game-tactics`의 `index.html`/`server.js`)은 확인 결과 **스타터가 준 파일과 해시가 같았다** — 참가자가 화면 쪽을 안 건드린 것이라 제외가 맞다.

이 수정은 `handover-relay-staged`만이 아니라 **입력 파일을 주는 모든 문제**의 채점 정확도를 올린다.

### 종합 점수(100점 만점, 80점 통과) — CLAUDE.md 예외 조항 발동

위 원칙("효율성/품질은 하나로 합치지 않는다")은 "사용자가 명시적으로 요청하기 전까지"라는 단서가 있다 — 2026-08-06 사용자가 정확히 그 요청을 해서(`src/lib/runDisplay.ts`의 `computeOverallScore`) 상세 페이지에 추가했다. `run.status === "completed"`이고 `evaluation`이 있을 때만 계산한다:

1. **품질 서브점수(0~100)**: 테스트 컴포넌트(통과=100/실패=0, `testCommand` 없으면 제외)와 채점 컴포넌트(`평균 LLM 점수 / 5 * 100`, 채점 실패면 제외)를 있는 것만 가중 평균(테스트 0.4, 채점 0.6). 둘 다 없으면 종합 점수 자체를 표시하지 않는다.
2. **토큰효율 서브점수(0~100)**: `Problem.referenceWeightedTokens` 대비 **가중 토큰** 비율로 연속 계산 — 기준 이하면 100점, **0점 도달 배율**(`Problem.tokenScoreZeroAtRatio`, 기본 2) 이상이면 0점, 그 사이는 선형 보간. 기준선이나 사용량 값이 없으면 이 컴포넌트는 제외된다. **2026-08-10부터 하드컷과 완전히 같은 축(가중 토큰)을 쓴다** — 아래 참고. 0점 도달 배율은 2026-08-12에 문제별 knob으로 열었다 — 아래 "기준선 초과 감점의 기울기는 문제마다 다르다" 절 참고.
3. **가중 평균**: 품질과 토큰효율을 7:3으로 합산(둘 다 있을 때). 토큰효율이 없으면 품질 서브점수 그대로 사용.
4. **하드 캡**: 테스트가 있었는데 실패했으면 서브점수를 79점 이하로 강제 캡한다 — 토큰효율이 좋아도 정답이 아닌 결과를 상쇄해서 통과시키지 못하게 하기 위함.
5. 반올림 후 0~100 clamp, 80점 이상이면 통과.

**시간은 6번 항목으로 별도 차감한다 (2026-08-11 도입 — 그 전까지는 0%였다).**

6. **시간 감점**: `Problem.targetDurationMs`(적정 시간)를 넘긴 순간부터 `maxDurationMs`(하드컷)까지 **선형으로 최대 20점**을 위 점수에서 뺀다. 적정 시간 안에 끝내면 감점 0이고, 빨리 끝냈다고 가산점을 주지는 않는다 — 그러면 품질을 희생해 서두르는 게 이득이 되기 때문이다. `targetDurationMs`가 없는 문제는 감점이 전혀 없어 예전과 동일하게 동작한다.

```
감점 = 20 × min(1, (소요시간 − 적정시간) / (하드컷 − 적정시간))     // 적정시간 이하면 0
```

**왜 뒤집었나**: 원래 근거는 "`maxDurationMs` 하드컷이 시간 초과를 이미 실격으로 배제하니, 점수에서 또 깎으면 이중 벌점"이었다(2026-08-06). **실측이 그 전제를 무너뜨렸다** — 저장된 완료 run 33건의 소요 시간이 전부 **1~14분**인데 하드컷은 40~120분이라, 하드컷은 **단 한 번도 작동한 적이 없다.** 즉 이중 벌점이 아니라 애초에 벌점이 하나도 없었고, 시간은 사실상 무제한이었다. "넘으면 실격 / 안 넘으면 무차별"이라는 계단식 대신 적정선부터 완만히 깎는 방식으로 바꿨다(2026-08-11 사용자 요청).

**감점 폭을 20점으로 잡은 이유**: 통과 기준이 80점이라, 다른 게 완벽한 100점짜리 run이 하드컷 직전까지 끌면 정확히 통과선(80점)에 걸친다 — 시간이 결과를 뒤집을 만큼은 무겁고 품질·토큰을 압도하지는 않는 지점이다. 조정하려면 `runDisplay.ts`의 `MAX_TIME_PENALTY` 상수만 바꾸면 된다. 실제 곡선(적정 10분 / 하드컷 15분, 본점수 100 기준): 10분 100점 · 11분 96점 · 12.5분 90점 · 14분 84점 · 14.9분 80점.

**문제별 시간 기준도 실측에 맞춰 다시 잡았다.** 기존 값은 "사람이 읽고 생각하는 시간"을 보수적으로 크게 잡은 것이었는데, 실제 세션이 그보다 훨씬 짧아서 감점 구간이 너무 넓으면 기울기가 완만해 사실상 작동하지 않는다.

| 문제 | 실측 완료 시간 | 적정 | 하드컷 (이전) |
|---|---|---|---|
| `report-xlsx-staged` | 6.8, 8.3분 | 10분 | 15분 (40분) |
| `csv-summarizer-staged` | 1.3~13.1분 | 15분 | 25분 (40분) |
| `inventory-digest-staged` | 4.3~11.1분 | 15분 | 25분 (90분) |
| `access-audit-staged` | 1.6~10.1분 | 15분 | 25분 (90분) |
| `game-tactics-staged` | 데이터 부족 | 30분 | 50분 (120분) |

**소급 안전성 확인**: 저장된 완료 run 33건에 새 계산식을 그대로 돌려 **점수가 변한 run 0건, 새 하드컷을 넘겼을 run 0건**임을 확인했다(전부 적정 시간 안에 끝났다). 즉 이번 변경은 앞으로의 run에만 실질적으로 작동한다.

**진행 중에도 보인다**: 사람이 관리할 수 없는 기준으로 감점하면 안 되므로, 대시보드 진행 막대에 적정 시간 위치를 세로선으로 표시하고 넘어가면 막대가 주황색으로 바뀌면서 "지금부터 종합 점수가 깎입니다"라고 알린다. run 상세의 "소요 시간" 지표에도 적정 시간 이내/초과를 같이 적는다.

효율성/품질 섹션은 그대로 분리 유지되고, 종합 점수는 그 위에 "추가"되는 요약일 뿐이다.

#### 기준선 초과 감점의 기울기는 문제마다 다르다 (`tokenScoreZeroAtRatio`, 2026-08-12)

2026-08-11까지 토큰효율 곡선은 **기준선의 2배에서 0점**으로 전 문제 고정이었다. 실사용에서 이게 무력한 케이스가 나왔다: `inventory-digest-staged`를 **Haiku로, 컨텍스트 분리 없이 그냥** 푼 run이 552,101 가중 토큰(기준선 500,000의 **1.104배**)을 쓰고도 **92점**을 받았다. 완만한 기본 곡선에서 1.1배는 토큰효율 90점이라 총점을 2점밖에 못 깎기 때문이다.

이건 곡선의 기울기가 아니라 **문제마다 "기준선을 넘겼다"의 의미가 다르다는 걸 표현할 방법이 없던 게** 문제였다:

- 대부분의 문제에서 기준선은 **넉넉한 참고선**이다. 조금 넘겼다고 크게 깎을 이유가 없고, 2배까지 완만히 깎는 게 맞다.
- 그런데 `inventory-digest-staged`가 재려는 건 **정확히 "컨텍스트를 정리했는가"** 하나다([problem-set.md](./problem-set.md)). 정리를 안 한 실패는 "기준선을 조금 넘는" 형태로 나타나지, 2배로 폭주하는 형태로 나타나지 않는다. 즉 이 문제에서는 **기준선 초과 자체가 측정 대상의 실패**인데, 기본 곡선은 그걸 거의 표현하지 못했다.

그래서 0점 도달 배율을 문제별 knob(`Problem.tokenScoreZeroAtRatio`, 기본값 2)으로 열고, 이 문제만 **1.1**로 잡았다 — **기준선을 10% 넘기면 토큰효율 0점**. 곡선을 전역으로 가파르게 만드는 선택지도 있었지만, 그러면 기준선이 사실상 모든 문제의 통과 요건이 돼버려서(어떤 문제든 10% 초과 시 품질 만점이어도 70점) 나머지 4개 문제의 기존 점수 체계가 통째로 흔들린다. 다른 문제도 같은 성격이라고 판단되면 그 문제 파일에 값을 넣으면 된다.

실제 곡선(품질 92.80 = 위 실측 run 기준):

| 가중 토큰 | 배율 | 총점 |
|---|---|---|
| ~500,000 | ≤1.00 | 95 (통과) |
| 510,000 | 1.02 | 89 (통과) |
| 525,000 | 1.05 | 80 (통과) |
| 540,000 | 1.08 | 71 |
| 552,101 (실측 run) | 1.10 | **65** |
| 600,000 이상 | ≥1.20 | 65 |

**소급 영향**: 저장된 완료 run 전체에 옛/새 계산식을 나란히 돌린 결과 **점수가 바뀐 run 6건, 전부 `inventory-digest-staged`**(다른 문제는 배율이 기본값 2라 변화 0건). 그중 통과선(80점)을 넘나든 건 2건이고 둘 다 의도한 방향이다 — 552,101(1.104배) 92→65, 589,958(1.180배) 85→60. 기준선을 0.4%만 넘긴 run(502,108)은 97→95로 거의 그대로다. 즉 **아슬아슬하게 넘긴 것은 벌하지 않고, 정리를 안 해서 10% 이상 넘긴 것만 통과선 아래로 떨어뜨린다.**

**알고 받아들인 대가**: 배율 1.1 이상은 전부 0점이라 550,000~하드컷(700,000) 구간에서 토큰 축의 변별력이 사라진다(552,101과 690,000이 같은 65점). 이 구간은 품질 축으로만 갈린다. 요구된 두 조건("55만이면 70점 미만 / 50만 미만이면 80점 이상")을 동시에 만족시키려면 기울기가 이 정도로 가팔라야 해서 감수한 것이다.

#### 토큰효율의 비용 정규화 (2026-08-07)

토큰 **개수**만 비교하면 모델을 바꾼 효과가 점수에 전혀 안 잡힌다. Fable 5 / Opus 5 / Sonnet 5는 같은 토크나이저 계열이라 같은 작업이면 토큰 수가 거의 같게 나오는데, 토큰당 단가는 최대 3.3배까지 차이나기 때문이다([manual-mode.md](./manual-mode.md)의 "토큰 하나로만 재던 걸 토큰 + 비용 두 축으로 분리" 참고). 그래서 토큰효율 서브점수는 이제 다음을 기준선과 비교한다:

```
비용 정규화 토큰 = 실제 토큰 × 비용 배율
비용 배율 = (모델별 단가로 환산한 이 run의 비용) / (같은 토큰 구성을 기준 모델로 돌렸을 때의 비용)
```

기준 모델은 `claude-sonnet-5`다(`src/lib/pricing.ts`의 `BASELINE_MODEL`). 이 선택 덕분에 **기존 `referenceTokens` 값을 하나도 안 건드려도 된다** — Sonnet 5로만 푼 run은 배율이 1.00이라 예전과 완전히 같은 점수가 나오고, 더 비싼 모델을 쓴 run만 정확히 단가 비율만큼 불리해진다(Opus 5 약 1.67배, Fable 5 약 3.33배). 모델을 섞어 썼으면 사용량 가중 평균 배율이 나온다. 배율 정보가 없는 run(이 기능 이전에 저장돼 모델 분해가 없는 경우, 또는 auto 모드)은 배율 1로 취급해 예전 계산식과 동일하게 채점된다.

#### 가중 토큰 단일 축으로 통합 (2026-08-10) — 구독 한도 소모에 맞추기

2026-08-07 시점에는 하드컷을 토큰 수 기준으로만 뒀다("실격 판정은 토큰, 점수는 비용"). 그 뒤 **"이 프로그램이 재는 수치가 Claude Max 구독의 사용 한도 소모와 같았으면 좋겠다"**는 요구가 나와서 공식 문서를 확인한 결과, 구독 한도는 토큰 1:1 합으로 소모되지 않는다:

- 캐시 읽기는 **캐시 토큰 요율(할인가)**로 한도에 잡힌다 — Claude Code 비용 문서의 "왜 긴 세션에서 사용량이 오르나" 절이 명시한다
- 어떤 모델인지, effort 레벨이 얼마인지가 사용량에 영향을 준다
- 세션/주간 한도는 전 모델 공유지만 그 위에 **Opus 전용 캡**이 따로 있다

즉 한도 소모는 "가중치 붙은 토큰"이고, 그건 사실상 비용에 비례한다. 저장된 run 17건을 다시 계산해보니 실제로 크게 어긋났다 — **raw 토큰 1M당 비용이 $0.62~$1.58로 2.5배까지 벌어졌고**, `inventory-digest-staged`에서는 **raw 토큰이 30% 적은 run이 한도는 49% 더 소모한** 순위 역전까지 나왔다(1,510,852토큰 $0.9362 vs 1,060,992토큰 $1.3941).

##### 두 축을 하나로 — "가중 토큰"

처음에는 토큰 하드컷 옆에 비용 하드컷을 나란히 뒀는데, 화면에 막대가 두 개 뜨고 "실격은 어느 쪽으로 나는 거냐"가 헷갈렸다. 사용자 판단으로 **제한은 비용으로 걸고, 표시는 그 비용에 가중치가 반영된 "토큰"으로** 하나로 합쳤다.

**가중 토큰 = 비용 × 100만** (즉 100만 가중 토큰 = $1, `src/lib/pricing.ts`의 `USD_PER_WEIGHTED_TOKEN`).

왜 하필 이 눈금인가 — 저장된 run 17건에서 **raw 토큰 1M당 비용의 중앙값이 $1.001**이었다. 그래서 이 눈금에서는 "전형적인 run이면 가중 토큰 ≈ raw 토큰"이 성립한다. 덕분에:

- 하드컷 $2.00이 **정확히 2,000,000 가중 토큰** — 기존 `maxTokens` 숫자와 같아서 감각이 그대로 유지된다
- 기준선(`referenceWeightedTokens`) 900,000 / 1,100,000도 값을 안 바꾸고 그대로 옮겼다
- 그러면서 가중치는 온전히 살아있다: 실측에서 가중/실제 비율이 0.62~1.58배로 갈렸다(Opus를 쓰면 늘고, 캐시를 잘 태우면 준다)

정리하면:

| 필드 | 역할 |
|---|---|
| `maxCostUsd` (필수) | **유일한 실질 하드컷.** 화면에는 가중 토큰으로 환산해 표시 |
| `maxTokens` (선택) | 폭주 백스톱 — 텔레메트리가 끊긴 채 단가 미등록 모델이 섞여 비용이 낮게 잡히는 경우에만 걸린다. 실질 예산의 2배쯤으로 잡음 |
| `referenceWeightedTokens` | 점수용 기준선(가중 토큰 단위). 하드컷과 같은 축이라 "실격은 토큰, 점수는 비용" 식의 축 불일치가 없어졌다 |

값 산정 근거: 두 문제 모두 기존 `maxTokens: 2,000,000` × 실측 중앙값 $1.001/1M ≈ **$2.00**. 실사용 데이터가 쌓이면 재조정할 수 있는 **잠정치**다.

**검증**: 저장된 manual run 30건에 새 코드 경로(`getEfficiencyDisplay`/`computeOverallScore`)를 그대로 돌려서 **예전(raw 2M) 대비 하드컷 판정이 뒤집힌 run은 0건**임을 확인했다.

비용 데이터가 없는 옛 run(2026-08-07 이전 저장분)은 가중치를 계산할 방법이 없어서 **raw 토큰을 근사치로** 쓴다 — 눈금이 위처럼 잡혀 있어서 가장 덜 왜곡된 선택이고, 화면에는 "근사"라고 표시한다. 이 폴백이 없으면 옛 run의 종합 점수가 전부 품질 점수만으로 재계산돼 이력 비교가 무너진다.

이 변경의 의도된 부작용: **같은 문제라도 Opus로 풀면 예산을 더 빨리 소모한다.** 버그가 아니라 목적 그 자체다 — 실제로 Opus를 쓰면 구독 한도를 그만큼 더 쓰기 때문이다.

한계(정직하게): **"내 주간 한도의 몇 %"라는 진짜 수치는 못 가져온다.** 그 값은 `/usage`가 읽는 서버 엔드포인트에만 있고 공개 API가 없다. 우리가 만들 수 있는 건 "한도 소모에 비례하는 양"이지 비율 자체가 아니다. Opus 전용 캡이 별도로 존재하는 것도 스칼라 하나로는 표현이 안 되므로 모델별 분해를 계속 병기한다.

LLM 채점 호출의 토큰/비용은 별도 필드로 기록해서, 벤치마크 대상인 CLI 실행 비용(구독 로그인 경로에서는 애초에 별도 청구도 아님, [cli-spec.md](./cli-spec.md) 참고)과 섞이지 않게 한다.

## 실격 run의 기록

실격 run도 값을 기록하긴 하지만, 완료된 run과 출처가 다르다는 걸 명확히 구분한다:

- 토큰/시간 수치는 CLI의 최종 `result`가 아니라 러너가 스트림을 읽으며 직접 누적한 값이다 — "하네스 추정치"로 별도 표시한다([cli-spec.md](./cli-spec.md#실시간-토큰시간-한도-집행)).
- 실격 사유(`token_limit` | `cost_limit` | `time_limit`)를 함께 기록한다.
- 순위/통계에서 완료 run과 같은 목록에 섞어서 "낮은 품질 점수"처럼 보이게 하지 않는다 — 애초에 품질을 측정하지 않았으므로 별도 카테고리로 취급한다.

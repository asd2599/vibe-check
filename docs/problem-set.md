# 문제 세트 포맷

`problems/*.json` 파일 하나당 문제 하나. 필드:

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | string | 고유 슬러그 (파일명과 일치 권장) |
| `title` | string | 문제 제목 |
| `difficulty` | `"easy" \| "medium" \| "hard"` | 난이도 |
| `category` | string | 예: `api`, `cli-tool`, `algorithm`, `refactor` |
| `listOrder` | number (optional) | 대시보드 문제 목록의 정렬 순서(작을수록 위). 없으면 기본 순위(100)로 취급되고 동점이면 `id` 사전순이다. 이 필드를 안 쓰는 문제들끼리는 예전 순서가 그대로다. **목록의 첫 문제가 대시보드의 기본 선택값**이므로(`src/app/page.tsx`), 처음 온 사람이 밟았으면 하는 워밍업 문제를 맨 위에 둘 때 쓴다(`calculator-web-staged`가 `1`) |
| `prompt` | string | 사람이 대시보드에서 읽고 시작할 **시나리오**. 아래 "프롬프트를 쓰는 방식" 참고 |
| `starterFiles` | string (경로, optional) | starter 코드 및/또는 **참고 문서** 디렉터리. 없으면 빈 워크스페이스에서 시작. 아래 참고 |
| `autoStartCommand` | string (optional) | 워크스페이스를 열 때 자동으로 같이 실행할 명령. VS Code 자동 태스크로 **조용히**(포커스를 안 뺏고) 뜬다 — 사람이 타이핑해야 하는 곳은 어디까지나 claude 세션 터미널이다. 웹 문제에서 "열자마자 페이지가 이미 떠 있는" 상태를 만들려고 쓴다(`calculator-web-staged`가 `npm start`). 서버 띄우는 절차를 배우게 하는 건 이 벤치마크의 측정 대상이 아니다 |
| `testCommand` | string (optional) | 워크스페이스 루트에서 실행할 테스트 명령. 없으면 자동 테스트 평가는 건너뛰고 LLM 채점만 수행 |
| `rubric` | string[] | LLM 채점 시 평가할 항목 목록 (예: "요구사항 충족", "에러 처리", "가독성") |
| `maxCostUsd` | number (필수) | **유일한 실질 사용량 하드컷.** 초과 시 러너가 즉시 세션을 종료하고 "실격" 처리한다. 화면에는 이 값을 **가중 토큰**으로 환산해서 보여준다(100만 가중 토큰 = $1) — 사람이 보는 축과 러너가 자르는 축이 같은 하나의 숫자다([evaluation.md](./evaluation.md)의 "가중 토큰 단일 축으로 통합" 절에 실측 근거) |
| `maxTokens` | number (optional) | **폭주 백스톱.** 실질 하드컷은 위 `maxCostUsd`이고, 이건 그게 무력화된 경우(텔레메트리가 끊겨 트랜스크립트로 폴백했는데 단가 테이블에 없는 신모델이 섞여 비용이 낮게 잡히는 경우)에만 걸리는 안전장치다. 정상 동작에서 먼저 걸리지 않도록 실질 예산의 2배쯤으로 넉넉히 잡는다. 빼면 백스톱 없이 동작 |
| `maxDurationMs` | number (필수) | 이 문제에 허용된 벽시계 시간 상한(ms). **사람이 읽고 생각하고 타이핑하는 시간까지 전부 포함된다** — 아래 "시간 한도" 참고. 초과 시 마찬가지로 즉시 종료+실격 |
| `targetDurationMs` | number (optional) | **적정 시간.** 넘겨도 실격은 아니지만, 이 시점부터 `maxDurationMs`까지 종합 점수가 선형으로 최대 20점 깎인다([evaluation.md](./evaluation.md)의 시간 감점 절). `maxDurationMs`보다 작아야 한다(`loadProblem`이 검증). 없으면 시간이 점수에 반영되지 않는다 |
| `referenceWeightedTokens` | number (optional) | 참고용 **합리적 기준선**(가중 토큰, `maxCostUsd`와 같은 눈금). 하드컷과 무관하며 종합 점수의 토큰효율 항목 계산에만 쓰인다. 없으면 토큰효율 컴포넌트가 빠진다 |
| `tokenScoreZeroAtRatio` | number (optional) | 위 기준선을 넘겼을 때 토큰효율 점수가 **0에 도달하는 배율**. 기본값 2(=기준선의 2배에서 0점). 1보다 커야 하고 `referenceWeightedTokens`가 있어야 한다(`loadProblem`이 검증). **기준선 초과 자체가 측정 대상의 실패인 문제에서만 낮춘다** — 예: `inventory-digest-staged`는 1.1(기준선 10% 초과 시 0점). 근거와 소급 영향은 [evaluation.md](./evaluation.md)의 "기준선 초과 감점의 기울기는 문제마다 다르다" 절 |
| `stages` | array (optional) | 단계형 문제일 때만. 아래 "단계형 문제(stages)" 참고 |
| `hiddenTestsPath` | string (경로, optional) | "완료" 시점에 워크스페이스로 덮어써 넣을 전체 히든 테스트 디렉터리. 아래 "단계형 문제(stages)" 참고 |

> VibeCheck은 원래 "AI가 헤드리스로 혼자 푼다"는 전제로 시작했다가, "사람이 Claude Code CLI로 직접 바이브 코딩하는 효율성을 측정한다"로 방향을 바꿨다(`CLAUDE.md`). 문제 설계 철학도 그에 맞춰 바뀌었다 — 아래 내용은 전부 그 이후 기준이다.

## 프롬프트를 쓰는 방식 — "복붙하면 바로 통과"는 안 된다

문제의 `prompt`를 그대로 Claude Code에 붙여넣기만 해도 통과하는 문제는 "바이브 코딩 효율"을 측정하지 못한다 — 그냥 "누가 복붙을 더 빨리 하나"를 측정해버린다. 그래서:

- **`prompt`는 완결된 기술 스펙이 아니라 실무에서 받을 법한 캐주얼한 요청(카톡/슬랙 톤)에 더 가깝게 쓴다.** 요구사항이 흐릿하고 빠진 게 있는 편이 낫다 — 실제 업무 요청이 원래 그렇다.
- **정확한 규칙/제약사항은 `starterFiles` 디렉터리 안의 참고 문서(SPEC.md, API_CONVENTIONS.md ...)에 넣는다.** 채점(테스트)은 반드시 그 문서를 실제로 읽고 반영해야만 통과하는 항목을 포함해야 한다 — 예: 정확한 에러 코드 문자열, 특정 응답 헤더, 경계값 규칙처럼 채팅 텍스트만 봐서는 알 수 없는 디테일.
- 목적은 "사람이 Claude Code에게 그 문서들을 얼마나 잘 활용하게 만드는가"(먼저 읽게 지시하기, 워크스페이스에 CLAUDE.md를 써서 방향을 잡아주기, 스킬/훅을 구성하기 — 이 저장소에선 이런 걸 통칭해서 "프롬프트 엔지니어링"이라고 부른다)를 측정 대상에 두는 것이다. 이걸 대놓고 요구하는 필드/체크리스트를 만들지 마라 — **그냥 문서를 안 읽으면 테스트가 자연스럽게 실패하게끔 설계하면 된다.** 방법(CLAUDE.md를 만들든, 그냥 프롬프트에 "SPEC.md 먼저 읽어"라고 하든)은 사람 자유다.

### 예시 (실제로 만든 문제, `url-shortener-api`)

```json
{
  "id": "url-shortener-api",
  "prompt": "[카톡 - 박PM]\n안녕하세요! 마케팅쪽에서 요청 온 건인데, 링크 줄여주는 사내 툴 하나 급하게 필요하다고 하네요 🙏\n간단하게 짧은 URL 만들고 접속하면 원래 주소로 이동하는 정도면 될 것 같아요\n자세한 기능 스펙이랑 저희 사내 API 규칙은 문서로 정리해서 워크스페이스에 같이 넣어놨어요\n(SPEC.md, API_CONVENTIONS.md 참고해주세요 — 특히 에러 응답 포맷은 꼭 그 문서 형식 그대로 맞춰주셔야 다른 팀 시스템이랑 연동이 돼요!)\n일단 프로토타입 레벨로 오늘 중으로 부탁드려요!",
  "starterFiles": "problems/starters/url-shortener-api"
}
```

`problems/starters/url-shortener-api/`에는 코드는 없고 `SPEC.md`(단축 코드 6자리, 24시간 만료 후 410 등 기능 규칙)와 `API_CONVENTIONS.md`(사내 표준 에러 응답 JSON 형식, 정확한 에러 코드 문자열, 필수 응답 헤더)만 들어있다. 이 문서를 안 읽고 채팅 내용만으로 대충 만들면 CRUD는 되지만 에러 응답 형식/헤더 관련 테스트에서 떨어진다.

## 문서 트랩 설계 원칙 — "스펙 대신 써줘"로 뚫리면 실패작이다

실사용으로 발견한 우회: 사람이 참고 문서를 아예 안 읽고 Claude Code에게 "여기 상황 보고 spec 문서 하나 만들어서 그대로 구현해줘"라고만 시켜도 테스트가 통과하는 경우가 있었다. 원인은 문서에 박아둔 "고정" 값이 사실 **관습적으로 자연스럽게 나올 법한 값**이었기 때문이다 — Claude가 문서를 한 번도 안 읽고 스스로 지어낸 스펙이 컨벤션과 비슷한 값을 고르면 우연히 맞아버린다. 그러면 측정 대상이 "사람이 문서를 읽고 Claude에게 정확히 반영시켰는가"가 아니라 "Claude가 그럴듯한 구현을 하는가"로 바뀌어버린다.

그래서 문서 기반 트랩을 설계할 때 다음을 지킨다:

- **고정 값은 비관습적으로 고른다.** "합리적인 개발자라면 이렇게 했을 것"과 다른 값이어야 한다 — 그럴듯한 선택지가 여러 개 있고 정답은 그중 문서에만 적힌 하나여야 우연히 맞을 확률이 떨어진다. (예: 흔한 HTTP 상태 코드 대신 사내 규칙으로 지정된 비표준 코드, `error`가 아니라 `errorCode`처럼 이름부터 다른 필드 등)
- **요구사항 중 최소 하나는 문서에도 안 적어놓고 대화 맥락에서 판단해야 하게 만든다.** 예: 두 사람이 살짝 상충하는 요청을 했거나, 우선순위만 명시돼 있고 나머지는 어느 쪽을 따를지 스스로 판단해야 하는 경우. 그래야 "문서를 다 긁어서 spec 하나로 정리해줘" 패턴으로는 못 채워진다 — 문서에 없는 정보이기 때문이다.
- **결과물이 문서 하나 · 구현 하나의 원샷으로 안 나오게 만든다.** 산출물을 결정하는 요소가 여러 개(예: API 스펙 + 마이그레이션 절차 + 롤백 시나리오)에 걸치게 하거나, 초기 요청 이후 추가 조건이 뒤늦게 들어오는 구조로 설계해서, "스펙 문서 하나 뽑아놓고 그대로 구현"으로는 해결이 안 되게 한다.
- **검증할 때 "AI에게 스펙을 대신 만들라고 시키는" 우회도 반드시 같이 돌려본다.** 기존 naive-vs-정답 구현 비교(아래 problem-author 작업 순서)에 더해서, "참고 문서를 안 보여주고 프롬프트만 준 뒤 Claude에게 알아서 스펙까지 만들어서 구현하게 시키는" 시나리오를 스크래치에서 한 번 돌려보고 테스트가 떨어지는지 확인한다. 이 경로로도 통과하면 그 문제는 실패작이다.

## 단계형 문제(`stages`) — 왜 생겼는가, 그리고 스키마

**계기**: `csv-summarizer-staged`를 "요구사항 4개를 대화 하나에 전부 노출 + SPEC.md를 처음부터 starterFiles에 넣어두는" 방식(방식 B, 위 `csv-summarizer-staged` 문서 참고)으로 만들었더니, 실사용에서 "spec대로 자동화 구현해줘" 한 마디로 다 풀려버렸다 — 사람이 문서를 실제로 읽고 활용했는지와 무관하게, Claude Code가 이미 워크스페이스에 있는 SPEC.md를 스스로 찾아 읽고 한 번에 끝까지 구현해버릴 수 있기 때문이다. 이러면 "사람이 하네스 엔지니어링(문서/스킬/hook 활용)을 했을 때 결과가 더 잘 나오는가"를 측정한다는 목적 자체가 무의미해진다(`CLAUDE.md`).

그래서 **진짜 단계별 제출/게이트 방식(방식 A)**으로 바꿨다:

- 처음엔 1단계에 필요한 리소스(데이터/문서)만 워크스페이스에 있다. SPEC 같은 규칙 문서는 **아직 없거나 최소한**만 있다.
- 대시보드의 "이 단계 제출" 버튼(`POST /api/runs/[id]/stage`)을 누르면 그 단계의 게이트 테스트만 워크스페이스에 대고 돌려서 통과 여부만 알려준다(어떤 assert가 깨졌는지는 절대 안 알려준다 — 위 "문서 트랩 설계 원칙"과 동일한 이유).
- 통과해야만 다음 단계의 리소스(새 데이터/갱신된 규칙 문서)가 워크스페이스에 자동으로 풀리고, 그제서야 다음 요구사항 텍스트가 대시보드에 이어붙는다. 못 풀면 계속 그 단계에 머문다.
- 이러면 "지금까지 공개된 정보만으로 지금 당장 뭘 요구받았는지"만 갖고 작업해야 해서, 미리 전체 SPEC을 스스로 찾아 한 번에 끝내는 경로 자체가 없다 — 정보가 물리적으로 아직 워크스페이스에 없기 때문이다.

### 스키마

**단계 수는 문제마다 다르다 — 2~10개.** 처음 만든 문제들이 전부 4단계였던 건 우연이고 규칙이 아니었는데, 문서와 공략집이 "4단계"를 전제처럼 서술하는 바람에 새 문제도 4단계에 맞추게 되는 부작용이 있었다(2026-08-11 지적). 러너와 대시보드는 원래 `stages.length` 기반이라 N단계를 그대로 처리한다. `loadProblem`이 범위를 검증한다:

- **하한 2** — 1단계짜리는 `stages`를 쓸 이유가 없다. `stages[0]`의 `promptAddition`/`unlockPath`는 애초에 읽히지 않으므로(그 역할은 `prompt`/`starterFiles`가 한다), 게이트 하나만 있는 셈이라 단계형이 아닌 문제와 다를 바가 없다.
- **상한 10** — 사람이 한 세션에서 실제로 밟을 수 있는 현실적인 상한이자, 오타로 단계가 폭증하는 걸 막는 안전장치다. 넘겨야 할 이유가 생기면 근거와 함께 올린다.

**단계 수는 문제의 성격이 정한다.** 규칙이 층층이 쌓이는 걸 재려면 여러 단계가 필요하고(`game-tactics-staged`), 곁다리 하나로 컨텍스트를 불리는 게 전부면 3단계로도 충분하다. 다른 문제가 4단계라는 이유로 단계를 채우지 마라 — 의미 없는 단계는 측정 초점을 흐린다.

`stages`는 배열이고, 각 원소(`ProblemStage`, `src/lib/problems.ts`)는:

| 필드 | 설명 |
|---|---|
| `index` | 1부터 시작, 배열 순서와 반드시 일치해야 한다(`loadProblem`이 검증) |
| `title` | 대시보드에 보여줄 짧은 라벨 |
| `promptAddition` | **이전** 단계 게이트를 통과했을 때 추가로 공개되는 대화 톤 텍스트 |
| `unlockPath` | PROJECT_ROOT 기준 경로. **이전** 단계가 통과할 때 워크스페이스로 복사되는 디렉터리(데이터/문서 등). 마지막 단계는 더 풀어줄 게 없으므로 `null` 가능 |
| `gateTestCommand` | 이 단계를 통과했는지 판정하는 명령 |

**헷갈리기 쉬운 부분**: `stages[i]`의 `title`/`promptAddition`/`unlockPath`는 **stages[i-1]의 게이트가 통과할 때** 공개/복사된다(`gateTestCommand`만 `stages[i]` 자기 자신의 게이트). 즉 배열의 **첫 번째 원소**(index 1)의 `title`/`promptAddition`/`unlockPath`는 절대 읽히지 않는다(1단계 자체는 `prompt` 필드 + `starterFiles`로 이미 시작 시점에 주어지므로) — 이 원소들은 채워도 무해하지만 실질적으로 안 쓰인다. 새 단계형 문제를 만들 때 이 오프셋을 헷갈리면 "1단계를 통과했는데 3단계 내용이 튀어나오고 2단계 리소스는 영영 안 풀리는" 버그가 난다(실제로 최초 스캐폴딩 때 이 실수를 했었다 — 반드시 스캐폴딩 후 각 단계를 실제로 순서대로 통과시켜보는 통합 테스트로 검증할 것).

**게이트는 "진행해도 되는가"만 판정하고, 정확도는 채점으로 넘겨라 (2026-08-12).** 게이트 테스트와 히든 테스트는 파일명이 같아서(`hiddenTestsPath`가 완료 시점에 `tests/`를 통째로 덮어쓴다) **서로 다른 기준을 넣을 수 있다.** 이걸 이용해 두 역할을 분리하는 게 기본형이다:

- **게이트(단계 통과)**: 산출물이 **존재하고 형태가 맞는지**만 본다. 없거나 비었거나 타입이 아니면 막고, 그게 아니면 통과시킨다.
- **채점(완료 시점 히든)**: 정확한 값을 본다. 미흡하면 `testPassed=false`가 되어 종합 점수가 79점 이하로 캡된다.

왜 이렇게 하나 — 게이트에서 정확도를 보면 **앞 단계에서 막혀 뒤 단계를 아예 못 밟는다.** 단계형 문제의 측정 대상은 대개 뒤쪽 단계에서 드러나므로(`inventory-digest-staged`라면 5·7단계), 앞에서 막히면 측정이 시작도 못 하고 끝난다. "진행은 시키고 부정확함은 점수로 받는다"가 낫다. 부수 효과도 크다: **게이트 파일은 참가자 워크스페이스로 복사되므로, 거기에 기대값을 적으면 정답이 그대로 노출된다.** 형태 검사만 두면 정답은 히든에만 남는다.

**게이트 테스트는 누적으로 짜라.** `gateTestCommand`가 이전 단계 테스트까지 다시 포함하도록(예: `node --test tests/stage1.test.js tests/stage2.test.js`) 짜면, 뒤 단계 작업 중에 앞 단계 동작을 실수로 깨뜨렸을 때(브리프 문서가 말하는 "단계 간 결합" 트랩) 그 자리에서 바로 잡아낸다 — 최종 완료 시점까지 안 잡히고 넘어가는 걸 방지한다.

**`hiddenTestsPath`로 "일찍 완료" 우회를 막는다.** 단계형 문제는 대부분 `hiddenTestsPath`(전체 단계 테스트 + 전체 데이터를 담은 디렉터리)도 같이 지정한다 — 안 그러면 사람이 몇 단계 안 풀고 일찍 "완료"를 눌렀을 때, 워크스페이스에 그 단계 테스트 파일 자체가 없어서 `npm test`가 "있는 것만" 통과해버려 점수가 실제보다 좋게 나온다. `hiddenTestsPath`가 있으면 "완료" 시점에 이 디렉터리 내용이 덮어써져서 항상 완전한 스펙 기준으로 채점된다([evaluation.md](./evaluation.md) 참고).

**단계형이 아닌 기존 문제는 전혀 안 건드려도 된다** — `stages`/`hiddenTestsPath`는 둘 다 optional이고, 없으면 지금까지처럼 `prompt` 하나로 끝나는 단일 문제로 동작한다.

## 게이트를 일부러 없애는 변형 — "안전망 없는 스펙 누적" (`calculator-web-staged`, 2026-08-14)

위의 게이트 설계는 **뒤 단계가 앞 단계를 깨면 그 자리에서 잡는다**는 게 핵심이다. 그런데 **잡아주지
않는 것 자체가 측정 축**인 경우가 있다. 바이브 코딩의 가장 흔한 실패 모드가 "방금 요청받은 것만 고치고
앞 기능을 회귀시키는 것"인데, 누적 게이트는 그걸 매 단계 대신 잡아줘서 **측정할 기회를 없앤다.**

그래서 `calculator-web-staged`는 기존 스키마를 그대로 쓰되 **게이트를 무력화**했다(스키마 변경 없음):

- 모든 단계의 `gateTestCommand`가 `node -e ""` — 워크스페이스 상태와 **무관하게 무조건 통과**한다.
  "이 단계 제출"은 게이트가 아니라 **손님이 확인만 하고 넘어가는 넛지**가 된다.
- `unlockPath`는 전부 `null`. 요구사항은 오직 `promptAddition`(손님이 슬쩍 물어보는 확인 질문 톤)으로만
  도착한다 — "괄호 넣은 식도 계산돼요?" 같은 식으로.
- `hiddenTestsPath`가 **완료 시점에 딱 한 번, 1~6단계 요구를 동시에** 검사한다. 이게 유일한 채점이자
  조기 완료 backstop이다.

**결과적으로 재는 게 달라진다**: 꼼꼼한 사람은 새 요청마다 전체를 다시 확인하고, 대충 하는 사람은
마지막에 우수수 떨어진다. 게이트가 있는 문제에서는 이 차이가 "재시도 루프 = 토큰"으로 나타나지만
여기서는 **품질 축에 그대로 나타난다.**

이 변형에는 두 가지 주의가 따른다:

1. **기대값을 채팅 질문 안에 못박아야 한다.** 게이트가 없으니 중간에 "그거 아니에요" 하고 바로잡아 줄
   기회도 없다 — 표기(`7%3`/`sqrt(9)`/`log(100)`), 에러 문자열(`"Error"`), 표시 규칙(`2.0`이 아니라 `2`)
   같은 규약이 질문 문장에 안 들어 있으면 **측정 축이 아닌 곳(표기 취향)에서 결과가 갈린다.**
2. **이 문제로는 하네스 엔지니어링이 안 갈린다.** 계산기는 프롬프트 한 방으로 풀리므로 문서/스킬의
   효과가 드러나지 않는다. 결함이 아니라 의도다 — 이 문제의 나머지 절반은 **온보딩과 기준선**이다
   (처음 온 사람이 실행 흐름을 익히고, 쉬운 과제에서의 시간·토큰을 재둬서 어려운 문제와 비교할 잣대를
   만든다). 그래서 `listOrder: 1`로 목록 맨 위에 두고 예산도 넉넉하게(실격을 유도하지 않게) 잡았다.

**화면이 있는 문제는 화면도 실행해서 재라 (2026-08-14, 실사용 사고 후).** 이 문제는 처음에 화면을
rubric으로만 봤다가 무너졌다 — 계산 함수는 완벽한데 이벤트 리스너 셀렉터가 일부 버튼을 빠뜨려
**클릭해도 아무 일이 없는** 산출물이 히든 7/7 통과 + 90점을 받았고, 소스를 읽는 LLM 채점자는 rubric을
콕 집어 고쳐도 두 번 다 못 잡았다. 지금은 히든이 **설치된 Chrome을 헤드리스로 띄워 버튼을 진짜로
클릭**한다(의존성 0, `tests/chrome.js`). 성립 조건은 **"어디를 눌러 어디를 읽는가"를 채팅에서 규약으로
못박는 것**(결과는 `#result`, 버튼은 `data-key`) — `evaluate()` 시그니처를 못박은 것과 같은 종류의
계약이고 마크업/프레임워크/디자인은 그대로 자유다. 버튼은 `data-key`가 없으면 라벨 텍스트로도 찾으므로
속성 이름을 안 지켰다고 떨어지지는 않는다. 자세한 경위는 [evaluation.md](./evaluation.md).

검증은 `scripts/verify-calculator-web-staged.mjs`(18개 체크). 이 변형에서 가장 중요한 체크는 **"빈
디렉터리로도 6단계 전부 통과하는가"**(게이트가 정말 무력한가)와 **"한 군데만 깬 구현이 정확히 그
test만 실패하는가"**(히든이 정말 회귀를 잡는가) 둘이다. 정답/기대값은 [공략집](./guides/calculator-web-staged.md).

## 컨텍스트 관리 트랩 — compact/clear를 안 쓰면 실패하게 만들기

**계기**: 사용자가 "토큰을 아끼려면 중간에 `/compact`나 `/clear`를 잘 쓰는 게 중요한 하네스 스킬"이라고 판단해서, 이 스킬 자체를 측정 대상으로 삼는 문제(`inventory-digest-staged`)를 만들었다. 기존 "문서 트랩"이 "문서를 읽었는가"를 측정한다면, 이건 "컨텍스트를 정리했는가"를 측정한다.

### 7단계 · 3개 직무 릴레이로 전면 재설계 (2026-08-11)

**계기**: 실사용자가 두 가지를 지적했다. ① 곁다리 요청(후기 필터링)을 **판단 작업**으로 만들었더니 통과와 실패가 실행마다 갈렸다 — 그러면 재는 게 컨텍스트 관리가 아니라 **"분류 운"**이 된다. ② 곁다리가 하나뿐이라 **컨텍스트를 안 나눠도 차이가 크게 안 난다.**

**여기서 나온 일반 원칙**: **측정하려는 축이 아닌 곳에서 결과가 흔들리면 그 문제는 목적을 잃는다.** 트랩을 무장시키겠다고 판정을 어렵게 만들면 그 흔들림 자체가 소음이 되어 측정을 망친다.

**바뀐 구조** — 서로 완전히 무관한 **직무 세 개**를 블록으로 끼운 7단계:

| 단계 | 직무 | 요구 | 데이터 |
|---|---|---|---|
| 1~2 | 물류팀 | 재고 집계 → 카테고리별 집계 + 재고 부족 | `inventory.csv` (0.7KB) |
| 3~4 | CS팀 | 환불/교환 후기 추출 → 후기 통계 | `reviews.json` (**44KB**) |
| 5~6 | 회계팀 | 경비 규정 위반 검출 → 부서별 집계 | `expenses.json` (**52KB**) |
| 7 | 물류팀 복귀 | 재주문 리포트 (1·2단계 규칙 재사용) | — |

설계 포인트 셋:

1. **직무가 블록으로 묶여 있어 정리 지점이 명확하다.** 3단계로 넘어가면 물류 데이터는 죽고, 5단계로 넘어가면 후기 데이터도 죽는다.
2. **정리 안 하면 죽은 데이터를 이고 다닌다.** 7단계 즈음이면 후기 44KB + 경비 52KB = **96KB(약 3만 토큰)**가 매 턴 캐시 재독 비용으로 나간다. 이전 버전은 44KB × 이후 2단계였는데 지금은 96KB × 이후 최대 4단계다.
3. **7단계가 첫 직무로 돌아온다.** 1·2단계 규칙(카테고리 코드, 카테고리별 재고 부족 기준)은 **채팅으로만** 줬으므로, 컨텍스트를 지운 사람은 그걸 **파일/CLAUDE.md로 외부화해뒀는가**에서 갈린다. 안 했으면 대시보드를 다시 보고 직접 챙겨야 한다(가능하지만 공짜는 아니다).

**모든 단계의 판정은 기계적으로 확정된다.** 오답 유도는 판단이 아니라 **경계값**으로만 준다:

- 3단계: 별점 2점 이하 **AND** 본문에 `환불`/`교환` 포함 → 정답 23건. 별점만 보면 143건, 단어만 보면 41건.
- 4단계: 평균 별점은 **버림**(반올림하면 값이 달라진다), `refundMentionCount`(41)는 3단계 정답(23)과 **의도적으로 다른 수** — 3단계 결과를 재사용하면 걸린다.
- 5단계: 식대는 **1인당** 초과, 교통비는 20,000원 **이하면 영수증 면제**, 접대비는 **총액** 초과, 비품은 예외. 경계값(15,000/20,000/30,000)에 데이터를 얹었다. 정답 35건인데 흔한 오답은 84/54/25/62건이 나온다.

**스크립트로 접을 수 있게 된 건 의도적으로 받아들인 대가다.** 원본이 컨텍스트에 안 올라가고 처리될 수도 있는데, **그건 실패가 아니라 좋은 결과다** — 큰 데이터를 대화에 안 올리고 처리하는 것 자체가 이 문제가 재려는 컨텍스트 관리의 정답 중 하나다. 나쁜 결과는 "올려놓고 끝까지 들고 가는" 쪽 하나뿐이고 그건 토큰 축에 그대로 드러난다.

**검증 완료(27개 체크 전부 통과)**: 정석 구현이 1→7단계 게이트를 순서대로 전부 통과 + 히든 통과 / 오답 9종이 **정확히 의도한 단계에서만** 처음 실패(2단계 2종, 3단계 2종, 4단계 2종, 5단계 3종) / 1단계·4단계 조기 완료 모두 히든이 차단.

**게이트는 오탈자 심판이 아니다 (2026-08-11 완화).** 3·5단계처럼 **id 목록을 열거하는** 단계는 누락/오검출을 각각 **2건까지 허용**한다(`tests/_helpers.js`의 `assertIdSet`). 실사용에서 3단계 실패가 잦았는데, 원인이 "규칙을 잘못 이해함"이 아니라 400건에서 손으로 추리다 한두 개를 흘리는 **단순 누락**이었기 때문이다 — 그걸로 갈리면 측정 축(컨텍스트 관리)이 아닌 곳에서 결과가 갈린다(위 "분류 운" 문제와 같은 종류). 규칙 자체를 잘못 읽으면 오차가 훨씬 커서 이 허용치로는 못 넘는다. 실측으로 2건 누락은 통과 / 3건 누락은 차단 / 별점만(143건)·단어만(41건)·식대 총액(84건)·소액면제 무시(54건)·접대비 1인당(25건) 등 규칙 오해 5종은 전부 차단됨을 확인했다. **집계 숫자를 내는 단계(1·2·4·6·7)에는 허용치가 전혀 없다** — 거기서 값이 틀리면 그건 규칙을 잘못 읽은 것이지 흘린 게 아니다.

**예산은 Haiku 실측 기준이다 (2026-08-11).** 실사용자가 Haiku로 한 세션 완주해서 약 **600,000 가중 토큰**이 나왔고, 거기 맞춰 하드컷 **$0.7(=700,000 가중 토큰)** / 기준선 **500,000**으로 잡았다. ⚠️ **부작용: 이 문제는 사실상 Haiku 전용이다.** 단가가 Sonnet 5는 Haiku의 3배, Opus 5는 5배라 같은 작업이 각각 약 1,800,000 / 3,000,000 가중 토큰이 되어 **하드컷을 넘긴다.** 가중 토큰 설계의 의도된 성질이지만(비싼 모델은 예산을 더 빨리 쓴다), 예산을 가장 싼 모델에 딱 맞추면 다른 모델 선택지 자체가 사라진다는 걸 알고 써야 한다 — 여러 모델을 비교하려면 `maxCostUsd`를 올려야 한다(Sonnet까지 허용하려면 $2.0 이상).

**미검증**: 시간(적정 25분 → 하드컷 45분)은 **실측이 아니라 외삽**이다 — 이전 4단계 버전 실측(4.3~11.1분)과 턴당 $0.0423 기준으로 늘려 잡았다. 이 프로젝트에선 예산을 감으로 잡았을 때 트랩이 아니라 버그가 된 전례가 있으므로(바로 아래 `maxTokens` A/B 절), **첫 실사용 run 이후 반드시 재조정할 것.** "컨텍스트를 안 나누면 자연히 차이 난다"는 가설도 재설계 후 A/B를 아직 안 돌렸다 — 구조적으로 이전보다 강한 건 분명하지만(죽은 데이터 44KB→96KB, 이후 단계 2개→최대 4개) 수치로는 확인이 필요하다.

### 이전 4단계 버전의 기록 (참고 — 위 재설계 전)

**`maxTokens` A/B 실측 (2026-08-05, 4단계 시절)**: 실제 프로덕션 플래그로 2단계 후 `/clear`를 쓰고 "정상 진행"(Run A)과 안 쓰고 "그대로 들고 감"(Run B)을 각각 4단계 전부 실제로 돌려봤다. 둘 다 게이트 4/4 + 히든테스트 통과(정답 자체는 동일 — 의도대로 여기서 "정답 여부"가 아니라 "토큰 비용"만 갈림): Run A 누적 83,013 → 264,374 → 416,937 → **636,461**, Run B 누적 79,685 → 261,045 → 535,018 → **946,341**. 즉 최초 추정치인 `maxTokens: 420,000`은 컨텍스트를 정리한 쪽(Run A)조차 51% 초과해서 **아무도 못 끝내는 값**이었다 — 이건 트랩이 아니라 그냥 버그였다. Run A가 여유 있게 통과하고(사람이 실제로 타이핑/읽는 시간까지 감안한 변동폭 안전하게 636,461 대비 25.7% 여유) Run B는 확실히 초과하는 지점을 찾아 `maxTokens`를 **800,000**으로 재조정함 — 이 값에서도 Run B는 약 18.3% 초과해서 4단계 도중 하드컷에 걸리므로, "컨텍스트 정리를 안 하면 못 끝낸다"는 트랩의 판별력 자체는 유지된다.

## `maxTokens` 여유 확대 (2026-08-06)

실사용자가 두 문제 다 한도가 빡빡하다고 느껴서, 요청에 따라 `maxTokens`를 각각 1.5배로 올렸다:

- **`csv-summarizer-staged`**: 900,000 → 1,350,000. 이미 실측(정석 구현으로 4단계 전부 완료 시 609,042토큰) 기반으로 한 번 900,000까지 올려둔 값이었는데, 여기서 다시 1.5배 올려 실측 대비 2.2배 여유가 됐다 — 단순 여유 확대이고 트랩 설계에는 영향 없다.
- **`inventory-digest-staged`**: 800,000 → 1,200,000. 이 문제는 바로 위 "컨텍스트 관리 트랩" 절에서 설명한 대로 2단계 후 컨텍스트를 정리 안 하면 실격되도록(정리한 Run A 636,461 vs 정리 안 한 Run B 946,341) **의도적으로 타이트하게** 잡아둔 값이었다. 1.5배로 올리면 정리를 안 한 Run B(946,341)조차 예산 안에 들어와서, 이 문제가 측정하려는 "컨텍스트 관리(compact/clear) 트랩"의 판별력이 사실상 사라진다. 그럼에도 사용자가 이 트레이드오프를 설명받고 이해한 상태에서 실사용 편의를 우선해 명시적으로 선택한 값이므로, 트랩으로서의 효과는 약해졌다는 점을 기록해둔다.

### 2차 상향 (2026-08-06, 같은 날)

실사용자가 "예제에 비해 토큰 소모량이 엄청 늘었다"고 보고해서 두 문제 다 `maxTokens`를 **200만(2,000,000)**으로 다시 올렸다(`csv-summarizer-staged` 1,350,000→2,000,000, `inventory-digest-staged` 1,200,000→2,000,000). 사용자 본인 추정으로는 도구 범위 확장(`MANUAL_ALLOWED_TOOLS`에 Agent/Skill 추가, [manual-mode.md](./manual-mode.md))이 원인 — 도구 호출이 늘수록 `cache_read_input_tokens` 재주입 때문에 턴당 비용이 커진다(바로 아래 "`maxTokens` 참고치" 절 참고). 여기에 더해 같은 날 `/compact` 비용 근사치(`compactMetadata.preTokens`)를 집계에 가산하기 시작한 것도 측정값 자체를 이전보다 크게 만드는 요인이다([manual-mode.md](./manual-mode.md)의 "`/compact` 비용이 트랜스크립트에 안 잡히는 문제" 절 참고) — 즉 실제 소비가 늘어난 것과 별개로, 같은 세션이라도 "재는 방식"이 더 정직해지면서 수치 자체가 올라간 부분도 섞여 있다. `referenceTokens`(참고 기준선, 900,000/800,000)는 이번엔 안 건드렸다 — 하드컷만 완화한 것이고, 결과 화면의 "기준 초과" 표시는 그대로 유지된다.

## 스킬 트랩 — 원본을 컨텍스트에 올리면 지게 만들기 (`access-audit-staged`, 2026-08-10)

**계기**: 사용자가 "Skill 사용법 자체를 알려주는 문제, 즉 스킬을 써야 토큰을 아껴서 통과할 수 있는 문제"를 요청했다. 기존 문제들이 "문서를 읽었는가"(`csv-summarizer-staged`)와 "컨텍스트를 정리하는가"(`inventory-digest-staged`)였다면, 이건 **"재사용 가능한 하네스를 워크스페이스에 구축하는가"**를 잰다.

**왜 스킬이 유리한가 (Claude Code 공식 문서 근거)**: `CLAUDE.md`는 세션 시작부터 끝까지 컨텍스트에 들어있지만, 스킬은 **description만 상주하고 본문은 호출될 때만 로드**된다("Move instructions from CLAUDE.md to skills"). 그리고 스킬 폴더에는 스크립트를 같이 둘 수 있어서, **원본 데이터를 대화에 올리지 않고 처리**할 수 있다("Offload processing to hooks and skills"). 결정적으로 스킬은 워크스페이스 파일이라 **`/clear` 이후에도 그대로 발견된다** — 채팅으로만 전달된 규칙은 날아간다.

**메커니즘**:

- 규칙(사내 집계 규칙 5개)은 **오직 채팅으로만** 준다. 워크스페이스에 규칙 문서가 없다 — 위 "컨텍스트 관리 트랩" 절과 같은 이유(파일로 주면 Claude가 알아서 찾아 읽어서 측정이 흐려진다). 규칙은 4단계 내내 계속 필요한데, 대화에만 있으면 컨텍스트를 지우면 사라진다 — **워크스페이스에 하네스로 박아두는 것 외에 안전한 방법이 없다.**
- 규칙은 전부 **비관습적**으로 골랐다(문서 트랩 설계 원칙): 499는 성공으로 치고 **3xx를 실패**로, 봇 판정은 User-Agent가 아니라 **1분에 3회**로(UA에 `curl`/`GoogleBot`이라고 대놓고 적힌 줄을 미끼로 넣어뒀다), 세션 경계는 관습적인 30분이 아니라 **7분 초과**로(6분·9분·7분 딱 경계를 의도적으로 심음), p90은 보간 없는 **nearest-rank + 버림**으로, 성공률은 반올림이 아니라 **버림**으로.
- **로그가 크다** — 4단계 누적 299KB(약 85,000토큰). 순진하게 `Read`로 올리면 그 자체가 비싸고, 한 번 올리면 원본은 이후 매 턴 캐시 재독 비용으로 계속 나간다.

> ⚠️ **이 아래 "스킬을 쓰면 토큰을 아낀다"는 전제는 실측으로 반증됐다.** 아래 "스킬은 토큰 절약 수단이 아니다" 절을 먼저 읽어라. 이 문제는 지금 스킬이 아니라 **"채팅으로만 전달된 비관습 규칙을 정확히·일관되게 반영하는가"**를 측정하며, 그 부분은 정상 작동한다(naive가 1단계에서 탈락).

**예산**: `maxCostUsd` **$2.00(= 2,000,000 가중토큰)** — 다른 네 단계형 문제와 동일하게 맞췄다. 원래 "로그를 컨텍스트에 올리면 96만 가중토큰이 더 든다"는 계산으로 $1.50을 잡았는데, 그 시나리오가 실제로는 성립하지 않는다는 게 실측으로 확인돼서(산출물이 스크립트라 어느 쪽도 로그를 컨텍스트에 안 올린다) 근거가 사라졌다. 지금 값은 4단계 + 스크립트 작성 + 게이트 재시도라는 작업 구조가 기존 네 문제와 같다는 점에 근거한 것이며, 실사용 후 조정 대상이다.

**검증한 것**: 정석 구현(사내 규칙 그대로)이 1~4단계 게이트를 순서대로 전부 통과 + 최종 히든 테스트 통과, 관습적 규칙으로 짠 naive 구현은 **1단계에서 즉시 탈락**(총 요청 549 vs naive 540, 성공률 69.9 vs 75.4 — 모든 단계에서 값이 갈린다), 2단계까지만 풀고 조기 "완료"하면 히든 테스트가 나머지 단계를 정확히 실패시킴. 이 문제는 워크스페이스에 규칙 문서가 아예 없으므로 "AI에게 스펙을 대신 만들라고 시키는 우회"는 곧 naive 경로와 같고, 그게 1단계에서 걸러지는 것으로 함께 확인됐다.

> 스캐폴딩 중 실제로 버그를 하나 밟았다. 이 문제는 **단계마다 로그 파일이 추가돼 누적 데이터가 커진다.** 그래서 누적 게이트(`stage1.test.js stage2.test.js ...`)를 돌릴 때 이전 단계 테스트의 기대값도 같이 바뀌어야 하는데, 처음엔 각 unlock 디렉터리에 "그 단계 테스트"만 넣어서 정석 구현조차 2단계 게이트에서 떨어졌다(1128 !== 549). **unlock 디렉터리마다 그 시점 누적 데이터 기준으로 다시 계산한 stage1..stageN 테스트가 전부 들어 있어 덮어쓰도록** 고쳤다. 데이터가 단계마다 늘어나는 문제를 새로 만들 때 반드시 밟게 되는 함정이다.

## 스킬은 토큰 절약 수단이 아니다 — A/B 실측 (2026-08-10)

위 스킬 트랩 문제를 만든 직후, 실사용자가 **"스킬을 쓴 거랑 그냥 쓴 거랑 토큰이 큰 차이 안 난다"**고 보고했다. 단계/작업량을 늘리자는 쪽 같다는 의견이었지만, 늘리기 전에 전제부터 실측으로 검증했다. **전제가 틀렸다.**

### 먼저: 비용은 바이트가 아니라 턴에서 나온다

실제 저장된 run 8건 · 247턴의 비용을 분해했다:

| | 값 |
|---|---|
| 턴당 평균 | **$0.0423 = 42,300 가중토큰** |
| 비용 구성 | 컨텍스트 재독 42% / 출력 27% / 신규 적재 31% |

SKILL.md 2,000토큰을 CLAUDE.md에 넣어 30턴 내내 들고 다녀도 18,000 가중토큰 = **0.4턴 어치, 예산의 1.2%**다. 프롬프트 캐싱 때문에 "컨텍스트에 뭐가 얼마나 들어있나"는 거의 공짜고, **턴 하나가 그보다 훨씬 비싸다.**

### A/B 실측

스크립트로 접을 수 없는 판단 작업(고객 문의 분류, 비관습 기준 4KB)을 3배치 반복시키고 4개 arm을 헤드리스로 돌렸다(Sonnet 5):

| arm | 총비용 | 가중토큰 | 총턴수 | 정답률 |
|---|---|---|---|---|
| A 스킬없음 / 한 세션 | $0.354 | 354,235 | 12 | 17/18 |
| B **스킬** / 한 세션 | $0.425 | 424,510 | **19** | **18/18** |
| C 스킬없음 / 배치마다 새 세션 | $0.546 | 545,681 | 18 | — |
| D **스킬** / 배치마다 새 세션 | $0.611 | 611,151 | **23** | 16/18 |

**스킬을 쓴 쪽이 한 세션에서 20%, 새 세션 조건에서도 12% 더 비쌌다.** 이유는 명확하다 — 스킬을 호출하려면 스킬을 찾고 SKILL.md를 읽는 도구 호출이 필요해서 **배치당 +2.3턴**이 붙는다. 반면 판단 기준을 프롬프트에 그냥 붙여넣는 건 턴이 안 늘고 입력 토큰만 늘 뿐인데 그게 훨씬 싸다.

**손익분기**: 스킬 오버헤드 2.3턴 = $0.0987. 지시문 재입력분은 1,000토큰당 $0.0060(1시간 캐시 쓰기). 즉 **매번 다시 줘야 하는 지시문이 약 16,450토큰(약 56KB) 이상**이어야 스킬이 본전이다. 그리고 한 세션을 유지하면 재입력 자체가 없으므로 **스킬은 토큰에서 이길 방법이 사실상 없다.**

부수적으로 확인된 것: **컨텍스트를 비우는 쪽(C vs A)이 54% 더 비싸다.** 새 세션마다 시스템 프롬프트와 도구 정의를 캐시 쓰기 가격으로 다시 적재하기 때문이다 — `/clear`가 항상 이득이라는 통념도 이 규모에서는 성립하지 않는다.

### 그래서 스킬의 실제 가치는 어디에 있나

이 실측에서 스킬이 이긴 곳은 비용이 아니라 **정확도**였다(B가 유일하게 18/18 만점). 스킬은 "규칙을 빠뜨리지 않고 일관되게 적용"하게 해주지 토큰을 아껴주지 않는다. 따라서 스킬을 측정하려면 **토큰 축이 아니라 품질 축**에서 갈리게 설계해야 한다.

**아직 미해결**: 그런데 `access-audit-staged`는 산출물이 코드여서, 규칙이 `audit.js`에 박히면 코드 자체가 규칙 저장소 역할을 한다 — 컨텍스트를 비워도 규칙을 안 잃어버리므로 품질 축에서도 스킬이 개입할 여지가 없다. 스킬을 제대로 측정하려면 **코드에 안 박히는 지점**(매번 모델이 판단해야 하는 작업)이 단계에 섞여야 한다(`inventory-digest-staged`의 2단계 같은 형태를 여러 단계에 걸쳐 반복). 이건 아직 반영하지 않았다.

**현재 `access-audit-staged`의 실제 측정 대상**: 스킬이 아니라 **"채팅으로만 전달된 비관습 규칙을 정확히 반영하고, 단계가 쌓여도 앞 규칙을 안 깨뜨리는가"**다. 그 부분은 검증됐고 정상 작동한다.

## 누적 불변 규칙 트랩 — 문서화의 효과를 재는 방식 (`game-tactics-staged`, 2026-08-10)

**계기**: 사용자가 "CLAUDE.md를 만들고 docs 폴더에 플랜/설계나 요구사항을 적었을 때 효율성이나 정확도가 좋아지는 걸 체감할 수 있는 문제"를, 그리고 "웹페이지에서 게임을 만드는 방식"으로 요청했다.

**설계 핵심**: 문서가 이기는 지점은 "규칙을 어디에 적어뒀나"가 아니라 **누적된 불변 규칙이 뒤 단계 작업에서 깨지는가**다. 그래서 이 문제도 규칙을 **채팅으로만** 주고(`access-audit-staged`와 동일한 이유 — 파일로 주면 Claude가 알아서 찾아 읽어버려 측정이 흐려진다), 뒤 단계 기능이 앞 단계 규칙 **위에 얹히게** 만들었다:

- 4단계 궁극기 데미지는 `1단계 공식 → 2단계 지형 보정(대상별로 각각) → ×1.5 버림` 순서를 전부 다시 타야 한다.
- 3단계 독 피해는 **지형 보정을 받지 않고**, **게이지를 채우지 않으며**, **대상을 죽이지 않는다**(hp 1 하한) — 즉 2·4단계 규칙의 예외다.
- 턴 시작 처리 순서(독 → 게이지)까지 고정돼 있다.

하나라도 빠뜨리면 게이트가 앞 단계 테스트부터 다시 실패시키므로, **재시도 루프가 곧 토큰 비용**이 된다. 회귀 검출은 실측 확인했다(4단계 궁극기에서 지형 보정을 건너뛴 구현 시 `stage4` 게이트가 정확히 잡아냄).

**앞 단계 테스트의 불변성이 이 설계의 전제다.** 뒤 단계 기능(게이지 자동 발동 등)이 앞 단계 시나리오의 결과를 바꿔버리면 앞 테스트가 저절로 깨져서 게이트가 신호를 잃는다. 그래서 생성기(`gen.mjs`/`emit.mjs`)가 **모든 시나리오를 자기 단계 레벨과 4레벨에서 각각 돌려 결과가 동일한지 검증한 뒤에만** 테스트를 emit한다. 실제로 처음엔 피격당 게이지 +20이라 1단계 시나리오에서 궁극기가 터져 검증이 실패했고, +10으로 낮춰서 해결됐다.

**웹 게임인 이유**: 로직(`game.js`)은 순수 함수라 `node --test`로 결정론적 채점이 되고, 화면(`index.html`)은 rubric으로만 본다. 화면 쪽은 명시되지 않은 결정(레이아웃/피드백/지형 표현)이 많아서 시각 반복 루프가 자연스럽게 생기는데, 여기가 사전 계획 문서의 값이 나오는 두 번째 지점이다. 의존성에 의존하지 않는 정적 서버(`server.js`, `npm start`)를 넣어 file:// 의 ESM/CORS 문제를 피했다.

**정직하게 밝힐 것 — 메커니즘은 가설이다.** 검증한 것은 게이트 판별력뿐이다(정석 4단계+히든 통과 / 관습적 구현은 1단계 탈락 / 조기 완료는 히든이 차단 / 회귀는 게이트가 검출). **"문서를 쓴 참가자가 실제로 토큰을 덜 쓰는가"는 측정하지 않았다.** 앞선 A/B(위 "스킬은 토큰 절약 수단이 아니다")에서 확인했듯 **한 세션을 유지하면 규칙이 컨텍스트에 그대로 남아 문서가 개입할 여지가 없다** — 문서가 이기려면 컨텍스트가 실제로 소실돼야 한다(compact 발생, `/clear`, 세션 재시작). 이 문제는 분량이 커서 compact가 걸릴 가능성이 높다는 데 기대고 있지만, 그건 라이브 세션 의존적이라 확인이 안 됐다. 실사용 후 재조정이 필요하다.

**예산 근거도 추정치다**: `maxCostUsd: 3.0`(= 3,000,000 가중 토큰), `maxDurationMs: 120분`. 다른 문제(2.0 / 40~90분)보다 크게 잡은 이유는 로직 4단계에 더해 화면 산출물이 크기 때문인데, 실측이 아니라 턴당 $0.0423 기준의 어림이다. 첫 실사용 run 이후 재조정할 것.

## 자발적 하네스 탐색 트랩 — 외부 스킬 생태계를 스스로 찾아 쓰는가 (`report-xlsx-staged`, 2026-08-11)

**계기**: `docs/example/report-xlsx-skill-staged.md` 브리프. 지금까지의 스킬 관련 문제(`access-audit-staged`)가 "규칙을 하네스로 박아두는가"를 쟀다면, 이건 한 발 더 나아가서 **참고 자료의 존재를 아무 힌트도 안 준 상태에서, 공식 스킬 생태계(`anthropics/skills`의 `xlsx` 스킬)가 존재한다는 걸 스스로 떠올려 설치해 쓰는가**를 잰다. 그래서 A/B를 config로 강제하지 않는다 — 문제 파일은 하나뿐이고, 여러 참가자가 자연스럽게 갈리는 행동을 **사후에 트랜스크립트/워크스페이스 diff로 관찰**해서 비교한다(브리프 6장).

**변별축은 문서 독해가 아니라 라이브러리 정확성이다.** xlsx 를 고른 이유는 결과 파일을 다시 열어 셀 값·타입·수식·서식·병합·틀 고정을 스크립트로 결정론적으로 검증할 수 있어서다. 함정은 실무에서 실제로 자주 틀리는 비직관적 지점들로 골랐다.

| 단계 | 요구 | 함정 | 실측 판별 |
|---|---|---|---|
| 1 | `상세` 시트에 원본 나열 | 날짜를 날짜값으로 변환 안 하고 문자열 vs 숫자 | `datetype` → 1단계 탈락 |
| 2 | `요약` 시트 합계를 살아있는 수식으로 | 값 하드코딩 / **수식은 맞는데 캐시값이 없음** | `hardcode`·`nocache` → 2단계 탈락 |
| 3 | 통화 표시 형식, 상품명 열 너비 | 문자열로 포맷해서 박기 / 서식 미지정 / 너비 방치 | `strmoney`(1단계로 승급)·`nofmt`·`nowidth` → 3단계 탈락 |
| 4 | 제목 행 병합 + 틀 고정 | freeze pane 좌표 규칙(상세 2행 / 요약 1행) | `nomerge`·`nofreeze`·`freeze` → 4단계 탈락 |

**2단계의 "캐시값" 요구가 이 문제의 핵심이다.** 요구는 채팅에는 업무 언어로만 적었다("저희는 엑셀 말고 사내 뷰어로 열어봐서, 합계가 빈칸으로 보이면 안 돼요"). 구현으로 번역하면 *수식 문자열과 계산된 값이 둘 다 파일에 들어있어야 한다* 인데, 이게 라이브러리마다 방식이 완전히 다르다 — exceljs 는 `{formula, result}` 로 값을 같이 넘겨야 하고, openpyxl 은 아예 캐시값을 못 쓰기 때문에 LibreOffice 로 재계산을 돌려야 한다. **공식 xlsx 스킬의 SKILL.md 가 정확히 이 두 가지("Use formulas, never hardcoded results" + "Recalculate (mandatory whenever the file contains formulas)")를 맨 앞에서 경고한다.** 스킬을 쓴 참가자는 함정을 밟기 전에 알고 시작하고, 안 쓴 참가자는 실행→빈칸→수정 루프를 돈다. 그 루프가 곧 시간이자 비용이다.

1. **정답 검증 — 두 런타임 모두**: exceljs 구현 20/20 통과, openpyxl 구현도 LibreOffice 재계산 후 20/20 통과(재계산 전에는 "수식 셀을 그냥 열어봐도 계산된 값이 보인다" **하나만** 실패 — 의도한 그 지점에서 정확히 걸린다).

### 브리프에서 의도적으로 벗어난 곳

- **문제 id 를 `report-xlsx-skill-staged` → `report-xlsx-staged` 로 바꿨다.** 브리프가 지정한 파일명에 `skill` 이 들어 있었는데, 워크스페이스 디렉터리 이름이 `${problem.id}_...`(`runner.ts`의 `createWorkspace`)라 참가자의 VS Code 제목 표시줄에 그대로 뜬다 — 브리프 4·8.5장이 금지한 바로 그 노출이다. 브리프의 명시 규칙이 브리프의 파일명보다 우선한다고 봤다.
- **스타터에 데이터만 두라는 브리프 3장에서 `package.json` + `tests/` 를 추가했다.** 단계 게이트를 돌리려면 1단계 테스트가 워크스페이스에 있어야 한다(다른 단계형 문제들과 동일). 대신 **어떤 스택도 요구하지 않도록** 테스트 쪽 의존성을 0으로 만들었다 — `tests/xlsx.js` 가 `zlib` 만으로 zip 을 풀고 XML 을 직접 파싱한다. `package.json` 엔 아무 의존성도 없어서 참가자가 JS 로 가든 Python 으로 가든 열려 있는 상태다.

### 알려진 한계 (정직하게 남김)

- **브리프 8.4의 A/B 가설은 검증을 못 했다.** "스킬을 쓴 쪽이 실제로 더 적은 토큰/더 정확하게 끝낸다"를 헤드리스로 두 조건 돌려 확인하는 항목인데, 실행하지 않았다. 따라서 이 문제가 **판별력 있는 문제라는 것은 검증됐지만, 스킬이 실제로 이긴다는 것은 아직 가설이다.** 특히 이 저장소의 앞선 실측("스킬은 토큰 절약 수단이 아니다")은 스킬 조회가 **배치당 +2.3턴**을 붙인다고 말한다 — 이 문제의 가설은 그와 방향이 다르다("시행착오 루프를 없애서 턴을 줄인다"). 어느 쪽이 큰지 실제로 재봐야 한다.
- **`recalc.py` 는 이 컴퓨터에서 그대로는 실패한다.** LibreOffice 는 설치돼 있지만 `soffice` 가 PATH 에 없어서, 스킬이 제공하는 `scripts/recalc.py` 가 `soffice not found on PATH` 로 죽는다. `soffice.exe` 를 직접 부르면 정상 동작하는 걸 확인했고(위 검증 3), 애초에 재계산이 필요 없는 경로도 있으므로(위 검증 5의 xlsxwriter) **막히는 문제는 아니지만, 스킬 경로가 얕히면 한 번 우회해야 할 수는 있다.** 이건 문제 설계가 아니라 이 머신의 환경 문제이고, 러너가 고쳐 PATH 를 주입하는 건 "새 문제는 파일 하나로 끝나야 한다" 원칙에 어긋나서 하지 않았다.
- **채점에는 "스킬을 썼는가"가 들어가지 않는다 — 이게 의도적이다.** `testCommand`/히든 테스트는 결과 `.xlsx` 파일만 보고(어떤 도구가 만들었는지 알 방법 자체가 없다), rubric 6개 항목 어디에도 스킬·생태계·특정 선택 언급이 없다(브리프 5장). 스킬 사용 여부는 **채점과 완전히 분리해서** 트랜스크립트/워크스페이스 diff로만 사후 관찰한다(브리프 6장). 이 감사 과정에서 채점 쪽 편향이 하나 발견돼 고쳤다 — [evaluation.md](./evaluation.md)의 "채점기 소스 수집이 방법에 따라 유불리를 만들던 문제" 참고.
- **병합 마스킹 함정은 파일 형식에서 판별되지 않는다.** 브리프 1장이 함정으로 꼽은 "병합 범위의 마스터가 아닌 칸에 값 쓰기"는, 실제로는 라이브러리가 알아서 처리해버린다 — exceljs 는 병합 시 나머지 셀 값을 지우고, openpyxl 은 `MergedCell.value` 가 읽기 전용이라 예외를 낸다. 그래서 올바른 xlsx 파일에는 애초에 그런 상태가 존재할 수 없다(실측: `mergeall` 구현이 4단계를 그냥 통과). 해당 assert 는 스펙 서술로서 남겨뒀지만 **판별력은 없다.** 4단계의 실질 판별은 병합 존재 여부와 틀 고정 좌표다.
- **LibreOffice 라운드트립이 열 너비를 바꾼다**(지정 36 → 실제 30.05, 글꼴 기준 환산 차이). 그래서 3단계 열 너비 검증을 "가장 긴 상품명 + 2 이상" 같은 상대 비교가 아니라 **`>= 20` 하한선**으로 잡았다. 기본 너비가 8 남짓이라 "넓혔는지"는 그대로 판별되면서, 재계산 경로가 억울하게 떨어지지는 않는다.
- **예산은 실측이 아니다.** `maxCostUsd: 2.5`(= 2,500,000 가중 토큰), `maxDurationMs` 40분. 다른 4단계 staged 문제(2.0)보다 여유롭게 준 이유는 브리프 7장대로 **직접 구현 경로도 완주 가능해야 비교 데이터가 모이기 때문**이다(한도를 조이면 직접 구현 참가자가 먼저 실격해서 애초에 비교가 성립하지 않는다). 첫 실사용 run 이후 재조정 대상.

## 큰 산문 트랩 — 컨텍스트 관리를 토큰 축에서 실제로 갈리게 만들기 (`handover-relay-staged`, 2026-08-13)

**계기**: `docs/example/handover-relay-staged.md`(v1) 브리프. 위 "컨텍스트 관리 트랩"(`inventory-digest-staged`)이 노렸던 것과 **같은 명제**를 재되, 그 문제가 실패한 원인을 고친 재설계다.

**`inventory-digest-staged`가 이걸 못 보여준 이유**: 데이터를 **표(CSV/JSON)로 줬더니** 참가자가 짧은 스크립트를 짜서 파일을 테스트에서 접었다. 원본 바이트가 애초에 대화창에 안 올라오니 **죽은 무게가 얹히지를 않았다.**

**설계의 근본 딜레마**(두 저장소가 반복해서 부딪힌 지점):

| | 결정론적 채점(운 배제) | 데이터가 대화창에 올라옴 |
|---|---|---|
| 표 데이터 + 집계 | ○ | ✕ 스크립트로 접히면 안 올라옴 |
| 판단/분류 작업 | ✕ "분류 운"으로 목적 상실 | ○ |
| **큰 산문에서 확정값 조회** | ○ | ○ |

**핵심 트릭**: 데이터를 **표가 아니라 산문 업무 문서로** 주고, 정답은 그 안에 박힌 확정값으로 둔다. 산문은 통째로 읽는 게 자연스러우면서도(깔끔히 접을 스크립트를 짜기 어려우면서도) 정답은 기계적으로 확정된다. **naive(통째로 올림)와 숙련(부분만 읽고 끊음)이 똑같이 정답을 내고 토큰만 갈린다** — 채점에는 운이 안 들어가고 측정축에서만 스프레드가 생긴다.

### v1은 실측으로 반증됐다 → v2 개정 (2026-08-13, run cd85075a · de559ff8)

v1을 실제로 두 번 돌린 결과가 **v1의 전제("naive 단일 세션은 비싸서 예산을 터뜨린다")를 반증했다.**

| run | 모델 | 결과 | 가중 토큰 |
|---|---|---|---|
| cd85075a | Haiku | 7단계 완주 | 423,104 = **$1.0 예산의 42%** (근처도 못 감) |
| de559ff8 | Sonnet 5 | 1단계에서 멈춤 | 592,527 (대부분 문서 한 번 적재하는 cache_write) |

기제는 기계적으로 작동했다 — Haiku run은 문서를 통째로 Read해 상주시켰고 turn당 cache_read가 16,669 → 83,848로 **단조 증가**, **raw 토큰의 96%가 상주 재독**이었다. 그런데도 안 아팠다. Haiku의 cache_read 단가가 **$0.10/1M**이기 때문이다. 그리고 Haiku의 탈락 사유는 토큰이 아니라 **품질**이었다 — 문서와 무관한 단계에서 표기 정규화를 틀렸다.

**여기서 나온 일반 결론 둘** (다른 문제를 설계할 때도 그대로 적용된다):

1. **cache_read가 input보다 10배 싸서, 큰 자료를 이고 가는 벌점은 싼 모델에선 거의 안 느껴진다.** "이고 가면 손해"는 **Sonnet 이상에서만 체감된다**(Sonnet cache_read $0.30/1M = Haiku의 3배).
2. **적재 비용(cache_write)은 두 경로가 똑같이 낸다.** 끊어서 아끼는 건 오직 **"적재 후 이고 간 턴"의 cache_read**뿐이다. 차이를 키우려면 **블록 수 × 이후 무관 턴 수**를 키워야 한다. 1단계에서 멈춘 run에 차이가 안 난 이유가 이것이다.

### v2 구조 — 무거운 블록 3개 + 이후 턴 확보

7단계 3직무 릴레이 골격은 유지하고, 각 직무 블록을 "무거운 자료 적재 + 여러 턴 작업"으로 짜맞췄다.

| 블록 | 단계 | 직무 | 자료 | 이후 죽은 무게 |
|---|---|---|---|---|
| A | 1~2 | 인프라 | `handover.md` 약 35,722 토큰 | — |
| B | 3~4 | 결제 | `payments/tickets.md` 약 38,021 토큰 | A |
| C | 5~6 | 데이터 | `data/access-requests.md` 약 40,125 토큰 | A·B |
| 복귀 | 7 | 인프라 | — (A·B 값 교차 참조) | A·B·C 전부 |

**3블록 누적 피크 약 113,868 토큰** — auto-compact 안전선(~120K) 아래로 잡았다. 상주가 컨텍스트 창에 닿아 자동 압축이 걸리면 무게가 강제로 걷혀 측정이 오염되기 때문이다. 생성기가 이 값을 매번 계산해 넘으면 경고한다.

### 함정은 **개수가 아니라 격차**로 고른다

함정을 쌓으면 단계별 통과 확률이 곱해져서 **Haiku만이 아니라 Sonnet도 같이 깎인다** — 함정 4개(Haiku 통과 60%/Sonnet 95%)면 Sonnet 전부통과가 **81%**(5회 중 1회 탈락)로 떨어진다. 효율 축을 보려면 Sonnet은 정답을 안정적으로 내야 하므로, **Haiku-miss와 Sonnet-miss의 격차가 큰 함정 3가족만** 쓰고 4·6단계는 앞 단계 결과를 집계만 하는 **무함정 단계**로 둬서 턴만 늘렸다.

1. **override 체인**(1·2·7단계) — 같은 값이 정확히 3번 나오고 마지막이 최신. 마지막 언급에 "최종/확정" 같은 표식이 없다(표식이 있으면 검색 한 번으로 찾으면 끝난다).
2. **다변형 표기 정규화 병합**(3단계) — 같은 원인이 띄어쓰기·하이픈·밑줄·대소문자만 다른 6가지 표기로 흩어져 있다. **v1 실측에서 Haiku가 정확히 이 지점에서 틀렸다**(대문자화만 하고 구분자는 안 통일). 정식 코드 5개를 채팅으로 주므로 판정은 기계적이다.
3. **다단 조건 + 경계값**(5단계) — 규칙이 순서대로 적용되고 예외가 끼어든다. "초과"와 "이상"의 차이도 섞었다.

**두 실패를 다른 축으로 분리했다**: Haiku는 **품질(함정)**에서, 단일 세션은 **토큰(예산)**에서 탈락시킨다. 같은 축에 몰면 서로 간섭해서 원인이 흐려진다.

### 검증한 것 (74개 체크, `scripts/verify-handover-relay-staged.mjs`)

정석 solver가 상수를 베끼지 않고 **워크스페이스 파일에서 직접 값을 뽑아오도록** 짜서, "데이터가 정답을 유일하게 결정하는가"까지 같이 검증했다. 정석 1→7단계 게이트 전부 통과 + 히든 7/7 / 오답 10종이 **정확히 의도한 단계나 히든에서만** 실패 / 단계 오프셋(블록 B·C가 미리 안 보임) / 게이트가 값 노출을 차단 / 2·4단계 조기 완료 차단 / 말끔함 0건 / 블록 크기·체인 3회·병합 표기 5코드·경계값 분포.

> **검증이 실제로 잡아낸 것 — 문서가 모호했다.** 승인자 이름 안에 `박팀장`이 들어 있는데 직급 어휘와 `팀장`이 문자열로 충돌해서 **정석 구현조차 5·6단계에서 틀렸다.** 사람도 읽으면 헷갈리는 지점이고, 측정 축이 아닌 곳에서 결과가 갈린다. 직급을 `팀장급`/`본부장급`/`임원`으로 바꾸고 이름과 분리해 고쳤다. **산문 데이터를 생성할 때는 어휘 충돌을 반드시 검사하라** — 정석 solver를 문서에서 직접 파싱하게 짜면 이런 게 자동으로 잡힌다.

### ⚠️ 아직 검증 안 한 것 — 합격선이 여기 있다

v2 개정안이 **합격선으로 지정한 것**은 전부 라이브 모델 실행이 필요해서 안 돌렸다.

1. **Sonnet 2-arm 토큰 A/B** — 두 arm이 히든을 똑같이 통과하면서 가중 토큰이 **약 30% 갈려야** 목표를 이룬 것이다.
2. **Haiku ×5 전탈락(0/5) / Sonnet ×5 전통과(5/5)** — Haiku가 통과하면 격차 큰 함정을 하나 더 넣고, Sonnet이 탈락하면 **그 원인인 함정을 뺀다**(둘 다 깔끔히 갈려야 한다).
3. **auto-compact 무발생** — 계산상 안전선 아래지만 실제 확인은 안 했다.

**그래서 예산은 잠정값이다.** 개정안의 이상형은 "단일 세션 실격 / 끊으면 통과"지만, 실측 없이 조이면 정상 시도까지 전원 실격시킨다(`csv-summarizer`·`inventory-digest`에서 두 번 겪은 실패). 지금은 **안전한 $3.0**으로 두고 A/B 후 조인다. 기준 모델은 **Sonnet 5**이고, 이 문제는 사실상 Sonnet 전용이다(`inventory-digest`가 Haiku 전용이었던 것의 정반대).

## `starterFiles`의 두 가지 용도

- **레거시 코드 리팩터링용**(`legacy-user-service-refactor`처럼 기존): 이미 동작하는 코드가 들어있고, 그걸 고치는 게 과제.
- **참고 문서용**(위 예시처럼): 코드는 없거나 최소한만 있고, 사람이 읽어야 하는 스펙/컨벤션 문서가 들어있다.

둘 다 메커니즘은 동일하다 — 워크스페이스 생성 시 이 디렉터리를 통째로 복사한다([manual-mode.md](./manual-mode.md)).

## 시간 한도 — 적정 시간 + 하드컷 두 단계 (2026-08-11 개정)

`maxDurationMs`는 세션이 열린 시간부터(대시보드 "시작" 클릭) 사람이 "완료"를 누르는 시간까지의 전체 벽시계 시간이다 — **문서 읽는 시간, 생각하는 시간, 타이핑하는 시간이 전부 포함된다.**

이전에는 "실측 데이터가 쌓이기 전까지는 보수적으로(너무 타이트해서 정상적인 시도까지 실격하는 것보다 낫다)"는 원칙으로 15~60분 이상 넉넉하게 잡았다. **실제 데이터가 쌓이자 그 값들이 지나치게 느슨하다는 게 드러났다** — 완료된 run 33건이 전부 1~14분인데 한도는 40~120분이라 하드컷이 한 번도 작동하지 않았다. 시간이 사실상 무제한이었던 셈이다.

그래서 값을 두 개로 쪼갰다:

- **`targetDurationMs`(적정 시간)** — 실측 완료 시간에 여유 있는 상한값. 여기까지는 감점 0.
- **`maxDurationMs`(하드컷)** — 적정 시간의 약 1.5~1.7배. 도달하면 즉시 종료+실격.

둘 사이 구간에서 종합 점수가 선형으로 최대 20점 깎인다([evaluation.md](./evaluation.md)). **새 문제를 만들 때는 실측 없이 감으로 잡되, 첫 run 몇 건이 쌓이면 반드시 실측에 맞춰 다시 조인다.** 두 구간이 너무 좁으면 기울기가 가팔라져서 감점이 실질적으로 하드컷처럼 작동한다.

## `maxTokens` 참고치

**실측 참고값**: 도구 호출이 늘어날수록 `cache_read_input_tokens`(직전까지의 컨텍스트/도구 정의를 캐시에서 다시 읽는 비용) 재주입 때문에 **턴당 대략 1만~1.5만 토큰**이 소비된다. 참고 문서를 읽는 턴이 추가되면 그만큼 더 든다. 문제마다 "왕복 몇 턴(문서 읽기+도구 호출 포함)이 걸릴지"를 먼저 가늠하고, 턴당 최소 1만~1.5만 토큰을 곱해 계산하는 게 출발점으로 좋다.
